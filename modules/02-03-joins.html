Глава 2.3. Соединения JOIN

Уровень: J · узел карты тем: T06 · PostgreSQL 17.11

«Выведи книгу вместе с именем автора»

В таблице books хранится только author_id, а имя лежит в authors — нормальная схема из главы 1.1: идентификаторы вместо повторяющихся имён. Но теперь пользователю нужен список «книга — автор», и тут выясняется, что SELECT из одной таблицы этого не умеет. Соединение (JOIN) — операция, которая строит одну таблицу из двух, попарно сопоставляя строки по условию. Вдобавок к механике нас ждут три классических сюрприза: строк становится больше, чем в исходных таблицах; «авторы без книг» бесследно пропадают; и условие в ON ведёт себя не так, как в WHERE.

Чтобы сюрпризы были видны, добавим автора, у которого нет книг:

INSERT INTO authors VALUES (4, 'Иван Крылов');

Теория: соединение — это произведение плюс отбор

В реляционной алгебре соединение определяется через две базовые операции: декартово произведение (все пары строк двух отношений) и селекцию (отбор пар по условию) — θ-соединение; внешнее соединение — расширение, дополняющее непарные строки NULL-значениями (Silberschatz, Database System Concepts, 7-е изд., глава 2, раздел 2.6 «The Relational Algebra» — операции произведения и соединений). Документация PostgreSQL описывает ту же механику приземлённо — через то, сколько и каких строк даёт каждый вид JOIN (раздел 7.2.1.1 «Joined Tables», /docs/17/queries-table-expressions.html). Далее все определения — из этого раздела.

INNER JOIN: только совпавшие пары

«Для каждой строки R1 таблицы T1 соединённая таблица содержит строку для каждой строки T2, удовлетворяющей условию соединения с R1» — определение INNER JOIN из 7.2.1.1. Слова INNER и OUTER необязательны, INNER — умолчание.

SELECT b.title, a.name
FROM books b
JOIN authors a ON a.author_id = b.author_id
ORDER BY b.book_id;
      title       |      name
------------------+------------------
 Евгений Онегин   | Александр Пушкин
 Руслан и Людмила | Александр Пушкин
 Мёртвые души     | Николай Гоголь
 Война и мир      | Лев Толстой
 Анна Каренина    | Лев Толстой
(5 rows)

Что выведено и почему: шесть книг минус «Детектив» без автора = 5 строк; у каждой строки книги ровно один автор, поэтому пары не размножаются. Размножение видно при связи «один-ко-многим» с другой стороны: соедините authors с books по author_id — и Пушкин встретится дважды: строк столько, сколько совпадающих пар, а не «сколько записей в левой таблице». Именно поэтому JOIN при 1:N меняет количество строк — это не ошибка, а определение операции.

LEFT JOIN: не потерять левую таблицу

Определение из 7.2.1.1: «сначала выполняется внутреннее соединение. Затем для каждой строки T1, не удовлетворяющей условию соединения ни с одной строкой T2, добавляется соединённая строка с NULL-значениями в столбцах T2. Таким образом, соединённая таблица всегда имеет минимум одну строку для каждой строки T1». Возвращаем книгу без автора:

SELECT b.title, a.name
FROM books b
LEFT JOIN authors a ON a.author_id = b.author_id
ORDER BY b.book_id;
      title       |      name
------------------+------------------
 Евгений Онегин   | Александр Пушкин
 Руслан и Людмила | Александр Пушкин
 Мёртвые души     | Николай Гоголь
 Война и мир      | Лев Толстой
 Анна Каренина    | Лев Толстой
 Детектив XXI века|
(6 rows)

Что выведено и почему: 6 строк — все книги; у «Детектива» нет пары в authors, и столбцы правой таблицы заполнены NULL. RIGHT JOIN симметричен («обратное левому: у результата всегда есть строка для каждой строки T2»), FULL JOIN сохраняет обе стороны: «строка добавляется с NULL-значениями в столбцах T2 для непарных строк T1 и с NULL в столбцах T1 для непарных строк T2» (определения — там же, 7.2.1.1). На наших данных — все пять пар, плюс «Крылов» без книг, плюс «Детектив» без автора:

SELECT a.name, b.title
FROM authors a
FULL JOIN books b ON b.author_id = a.author_id;
      name       |       title
-----------------+--------------------
 Александр Пушкин | Евгений Онегин
 Александр Пушкин | Руслан и Людмила
 Николай Гоголь  | Мёртвые души
 Лев Толстой     | Война и мир
 Лев Толстой     | Анна Каренина
 Иван Крылов     |
                 | Детектив XXI века
(7 rows)

Что выведено и почему: семь строк — пять совпавших пар, строка «Крылова» с NULL в столбце книг и строка «Детектива» с NULL в столбце авторов; NULL с обеих сторон одновременно — ровно тот случай, который не ловят ни LEFT, ни RIGHT JOIN.

Анти-соединение: «у кого НЕТ книг»

LEFT JOIN + проверка NULL на ключе правой таблицы — стандартный способ искать «непарные» строки:

SELECT a.name
FROM authors a
LEFT JOIN books b ON b.author_id = a.author_id
WHERE b.book_id IS NULL;
    name
--------------
 Иван Крылов
(1 row)

Что выведено и почему: LEFT JOIN дал Крылову строку с NULL в столбцах books; фильтр b.book_id IS NULL оставил только её. Почему проверяем именно book_id (ключ), а не любой столбец: у парной строки book_id NULL-ом быть не может — это PRIMARY KEY.

ON против WHERE: порядок операций

Приём выше работает из-за порядка операций, который документация фиксирует дословно: «ограничение в предложении ON обрабатывается до соединения, а ограничение в предложении WHERE — после соединения. Для внутренних соединений это не имеет значения, но для внешних имеет большое значение» (7.2.1.1, /docs/17/queries-table-expressions.html). Следствие: фильтр по правой таблице в WHERE «убивает» NULL-строки LEFT JOIN и превращает его фактически в INNER. Сравните:

-- фильтр в ON: строки левой таблицы сохраняются (итог — 6 строк):
SELECT b.title, a.name
FROM books b
LEFT JOIN authors a ON a.author_id = b.author_id
   AND a.name = 'Лев Толстой';

-- тот же фильтр в WHERE: NULL-строки отбрасываются (итог — 2 строки):
SELECT b.title, a.name
FROM books b LEFT JOIN authors a ON a.author_id = b.author_id
WHERE a.name = 'Лев Толстой';

Что будет выведено и почему: первый запрос — все 6 книг: у книг Толстого будет имя автора, у остальных NULL в столбце name (пары не нашлись, но левая строка по правилу LEFT JOIN сохранена с NULL-дополнением); второй — только 2 строки, книги Толстого, потому что WHERE отбросил всё, где a.name не равен «Лев Толстой», включая NULL-строку «Детектива». Правило: в ON — условие соединения, в WHERE — фильтр результата.

CROSS JOIN и запятая

«Для каждой возможной комбинации строк T1 и T2 (то есть декартова произведения) соединённая таблица содержит строку из всех столбцов T1, за которыми все столбцы T2. Если в таблицах N и M строк, соединённая таблица будет иметь N * M строк» — определение CROSS JOIN из 7.2.1.1. На наших данных authors CROSS JOIN books даст 4 × 6 = 24 строки. Там же зафиксированы эквивалентности: FROM T1 CROSS JOIN T2 равнозначно FROM T1 INNER JOIN T2 ON TRUE и FROM T1, T2; но «при более чем двух таблицах эта эквивалентность неточна, потому что JOIN связывает крепче запятой» — то есть FROM t1 CROSS JOIN t2, t3 и FROM t1, t2 CROSS JOIN t3 читаются по-разному. На практике CROSS JOIN нужен редко: безусловные пары множатся быстро, и чаще всего это признак забытого ON.

USING и NATURAL JOIN

Если столбцы соединения называются одинаково, есть сокращение. Документация: «USING — сокращение, рассчитанное на ситуацию, когда обе стороны соединения используют одно имя для соединяемых столбцов... Соединение T1 и T2 с USING (a, b) даёт условие ON T1.a = T2.a AND T1.b = T2.b. Кроме того, вывод JOIN USING убирает избыточные столбцы: нет нужды печатать оба совпавших столбца...» (7.2.1.1). Для нашей пары таблиц: books b JOIN authors a USING (author_id) даст один столбец author_id в выводе вместо двух.

NATURAL — «сокращённая форма USING: она образует список USING из всех имён столбцов, встречающихся в обеих входных таблицах» (там же). Звучит удобно, но документация предупреждает: «USING достаточно безопасна относительно изменений столбцов, потому что комбинируются только перечисленные столбцы. NATURAL значительно более рискованна: любое изменение схемы, из-за которого в одной из таблиц появится новое совпадающее имя столбца, приведёт к тому, что соединение включит и этот новый столбец» (примечание в 7.2.1.1). В учебном и рабочем коде пишите явный ON или USING.

Проверь себя

Вопрос 1. В authors 4 строки, в books 6. Сколько строк вернёт authors a JOIN books b ON b.author_id = a.author_id? А authors a LEFT JOIN books b ON b.author_id = a.author_id?

Ответ. INNER — 5: по одной паре на каждую книгу с указанным автором (у книг по одному автору; книга с NULL-автором пары не имеет — NULL не «равен» ничему). LEFT — 6: пять пар плюс NULL-строка для Крылова («у результата всегда есть строка для каждой строки T1» — определения INNER/LEFT из 7.2.1.1, /docs/17/queries-table-expressions.html).

Вопрос 2. Чем для LEFT JOIN отличается условие правой таблицы в ON от того же условия в WHERE?

Ответ. ON-условие участвует в подборе пар (обрабатывается до соединения): строки левой таблицы без пары всё равно останутся, с NULL-дополнением. WHERE-условие фильтрует готовый результат (после соединения) и отбрасывает NULL-строки — LEFT фактически ведёт себя как INNER. Формулировка «ограничение в ON обрабатывается до соединения, а в WHERE — после» — 7.2.1.1, там же пример с LEFT JOIN t2.

Вопрос 3. Почему NATURAL JOIN считают рискованным и что использовать вместо него?

Ответ. NATURAL неявно строит список соединяемых столбцов из всех одноимённых столбцов двух таблиц: добавление нового одноимённого столбца в любую из таблиц молча меняет условие соединения (примечание в 7.2.1.1). Безопасная замена — явный ON или USING с перечисленными столбцами.
