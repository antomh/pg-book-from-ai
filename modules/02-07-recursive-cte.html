Глава 2.7. Рекурсивные CTE

Уровень: J+ · узел карты тем: T10 · PostgreSQL 17.11

«Выведи всё поддерево категории» — на какую глубину?

В каталоге книги лежат в категориях, категории вложены друг в друга: «Классика» — ребёнок «Художественной литературы», «Русская классика» — ребёнок «Классики». Задача: показать всё дерево категорий с уровнями вложенности. Обычный SELECT справляется на фиксированную глубину: один JOIN — один уровень, два JOIN — два. Если глубина заранее неизвестна (а в реальном каталоге она и не известна), конечного запроса из JOIN не построить. Стандартное решение — хранить связь «родитель—потомок» (список смежности, adjacency list) и обходить его рекурсивным CTE. Это глава уровня J+: приём обязателен к пониманию для работы с деревьями, но откладывается некоторыми курсами «на потом».

Данные для главы — таблица категорий, где parent_id ссылается на category_id той же таблицы (самоссылка):

CREATE TABLE categories (
    category_id integer PRIMARY KEY,
    name        text    NOT NULL,
    parent_id   integer REFERENCES categories (category_id)
);

INSERT INTO categories VALUES
    (1, 'Художественная литература', NULL),
    (2, 'Классика',                  1),
    (3, 'Современная проза',         1),
    (4, 'Русская классика',          2),
    (5, 'Зарубежная классика',       2),
    (6, 'Детектив',                  3);

Общая форма рекурсивного CTE

Документация (раздел 7.8.2 Recursive Queries, /docs/17/queries-with.html): «необязательный модификатор RECURSIVE превращает WITH из простого синтаксического удобства в средство, делающее возможным то, что иначе недостижимо в стандартном SQL. Используя RECURSIVE, WITH-запрос может ссылаться на собственный вывод». Общая форма — всегда нерекурсивный терм, затем UNION (или UNION ALL), затем рекурсивный терм, и «только рекурсивный терм может содержать ссылку на вывод самого запроса» (там же). Простейший пример из документации — сумма целых от 1 до 100:

WITH RECURSIVE t(n) AS (
    VALUES (1)
    UNION ALL
    SELECT n+1 FROM t WHERE n < 100
)
SELECT sum(n) FROM t;

Что выведено и почему: 5050. Якорь VALUES (1) даёт первую строку; рекурсивный терм берёт её, прибавляет 1 и получает следующую; и так до строки со значением 100, где WHERE n < 100 отрежет продолжение. Ниже разберём формальный алгоритм, по которому сервер вычисляет такую конструкцию.

Алгоритм вычисления: рабочая таблица

Документация описывает вычисление дословно (раздел 7.8.2): «Такой запрос выполняется так: (1) вычислить нерекурсивный терм; для UNION (но не UNION ALL) отбросить дубликаты; включить оставшиеся строки в результат рекурсивного запроса, а также поместить их во временную рабочую таблицу. (2) Пока рабочая таблица не пуста, повторять: вычислить рекурсивный терм, подставив текущее содержимое рабочей таблицы вместо рекурсивной самоссылки; для UNION (но не UNION ALL) отбросить дубликаты и строки, дублирующие предыдущие результаты; включить оставшиеся строки в результат и во временную промежуточную таблицу; заменить содержимое рабочей таблицы содержимым промежуточной, затем опустошить промежуточную». И важное примечание там же: «хотя RECURSIVE позволяет задавать запросы рекурсивно, внутренне такие запросы вычисляются итеративно» — то есть это цикл с рабочей таблицей, а не бесконечная глубина вызовов.

Применяем к дереву категорий (обход всего дерева с глубиной):

WITH RECURSIVE tree AS (
    -- нерекурсивный терм (якорь): корни
    SELECT category_id, name, parent_id, 0 AS depth
    FROM categories
    WHERE parent_id IS NULL
    UNION ALL
    -- рекурсивный терм: дети строк из tree
    SELECT c.category_id, c.name, c.parent_id, tree.depth + 1
    FROM categories c
    JOIN tree ON c.parent_id = tree.category_id
)
SELECT * FROM tree ORDER BY category_id;
 category_id |         name         | parent_id | depth
-------------+----------------------+-----------+-------
           1 | Художественная литература |           |     0
           2 | Классика            |         1 |     1
           3 | Современная проза    |         1 |     1
           4 | Русская классика     |         2 |     2
           5 | Зарубежная классика  |         2 |     2
           6 | Детектив             |         3 |     2
(6 rows)

Что выведено и почему, по шагам алгоритма:

  • Шаг 1 (якорь): WHERE parent_id IS NULL даёт корень — категорию 1; строка попадает в результат и в рабочую таблицу ({1}).
  • Итерация 1: рекурсивный терм ищет детей строк рабочей таблицы: parent_id = 1 — это категории 2 и 3 с depth 1; результат пополнился, рабочая таблица теперь {2, 3}.
  • Итерация 2: дети категорий 2 и 3 — это 4, 5 (от «Классики») и 6 (от «Современной прозы»), depth 2; рабочая таблица {4, 5, 6}.
  • Итерация 3: детей у 4, 5, 6 нет — промежуточная таблица пуста, рабочая таблица становится пустой, цикл останавливается («пока рабочая таблица не пуста»).

Ключ к чтению рекурсивного терма: ссылка tree внутри него — это не весь результат, а текущее содержимое рабочей таблицы, то есть строки, полученные на предыдущей итерации. Именно поэтому depth корректно нарастает: +1 за каждую итерацию от строк, порождённых ровно шагом раньше.

Раз глубина уже вычислена, агрегировать по уровням может обычный GROUP BY из главы 2.4 — «сколько категорий на каждой глубине»:

SELECT depth, count(*) AS categories_cnt
FROM tree
GROUP BY depth
ORDER BY depth;
 depth | categories_cnt
-------+----------------
     0 |              1
     1 |              2
     2 |              3
(3 rows)

Что выведено и почему: один корень (depth 0), две категории первого уровня и три второго — обычная свёртка набора строк, который подготовило рекурсивное CTE. (Сравните с альтернативой «materialized path» — хранением пути до корня строкой вроде '1/2/4': обход превращается в LIKE '1/2/%', но путь нужно поддерживать при каждом перемещении узла; это тот же компромисс «денормализация ради скорости», что в главе 4.3.)

Циклы в данных и способы защиты

Если в parent_id закрадётся цикл (2 ссылается на 4, а 4 — на 2), рекурсивный терм будет порождать строки бесконечно. Документация формулирует условие корректности: «работая с рекурсивными запросами, важно быть уверенным, что рекурсивная часть запроса в конце концов не вернёт строк, — иначе запрос будет циклиться бесконечно. Иногда использование UNION вместо UNION ALL решает задачу, отбрасывая строки, дублирующие предыдущие результаты. Однако часто цикл не порождает полностью одинаковых строк результата: может понадобиться проверка одного или нескольких полей, чтобы понять, что эта точка уже была пройдена. Стандартный метод — вычислять массив уже посещённых значений» (раздел 7.8.2, Cycle Detection). Там же документация приводит автоматизацию этого метода — предложение CYCLE: «CYCLE задаёт сначала список столбцов для отслеживания циклов, затем имя столбца, показывающего, обнаружен ли цикл, и, наконец, имя ещё одного столбца, отслеживающего путь»:

WITH RECURSIVE tree AS (
    SELECT category_id, name, parent_id FROM categories WHERE parent_id IS NULL
    UNION ALL
    SELECT c.category_id, c.name, c.parent_id
    FROM categories c JOIN tree ON c.parent_id = tree.category_id
) CYCLE category_id SET is_cycle USING path
SELECT * FROM tree;

Что выведено и почему: тот же набор строк, что и раньше, плюс два служебных столбца: path — массив пройденных category_id, у всех строк is_cycle = false; если бы данные зациклились, рекурсия остановилась бы при повторном достижении той же точки. Для упорядочивания обхода есть парное предложение SEARCH: «SEARCH DEPTH FIRST BY id SET ordercol» / «SEARCH BREADTH FIRST BY id SET ordercol» (раздел 7.8.2, Search order; описание синтаксиса — там же).

Проверь себя

Вопрос 1. Какие две обязательные части есть у любого рекурсивного CTE и почему без якоря обойтись нельзя?

Ответ. Нерекурсивный терм (якорь) и рекурсивный терм, соединённые UNION/UNION ALL; самоссылка допустима только в рекурсивном терме (7.8.2). Якорь порождает строки первой рабочей таблицы; без него рабочая таблица пуста с самого начала, и «пока рабочая таблица не пуста» не выполнится ни разу — результат пуст.

Вопрос 2. Что именно подставляется вместо самоссылки tree на каждой итерации — весь накопленный результат или что-то другое?

Ответ. Текущее содержимое рабочей таблицы — строки предыдущей итерации, а не весь накопленный результат. Обоснование — алгоритм из 7.8.2: «вычислить рекурсивный терм, подставив текущее содержимое рабочей таблицы вместо рекурсивной самоссылки... заменить содержимое рабочей таблицы содержимым промежуточной».

Вопрос 3. Чем опасен UNION ALL в рекурсивном терме при данных с циклом и какие два способа защиты описывает документация?

Ответ. UNION ALL не отбрасывает дубликаты, и цикл в данных (a→b→a) заставит рекурсивный терм порождать строки бесконечно. Способы из раздела Cycle Detection (7.8.2): UNION вместо UNION ALL (помогает, только если цикл порождает полностью одинаковые строки результата) и массив посещённых значений — вручную или предложением CYCLE ... SET ... USING ... .
