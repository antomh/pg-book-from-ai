Глава 7.3. TOAST: хранение больших значений

Уровень: J+ · узел карты тем: T36 · PostgreSQL 17.11

Текст в 54 килобайта вставился в таблицу со страницами по 8 КБ

Глава 7.2 закончилась жёстким правилом: «PostgreSQL использует фиксированный размер страницы (обычно 8 КБ) и не позволяет кортежам пересекать несколько страниц» (/docs/17/storage-toast.html, 65.2, перевод дословный). Но text-поле принимает отзыв на десятки килобайт — без ошибок и без расширения страницы. Куда деваются байты? Ответ — механизм с честным самоназванием: «поэтому невозможно хранить очень большие значения полей напрямую. Чтобы преодолеть это ограничение, большие значения полей сжимаются и/или разбиваются на несколько физических строк. Это происходит прозрачно для пользователя... Техника ласково известна как TOAST (или "лучшая вещь после нарезанного хлеба")» (65.2, дословно; TOAST — The Oversized-Attribute Storage Technique). Разберём, когда срабатывает триггер, куда пишутся данные и как управлять стратегией хранения.

Кто умеет «тостироваться», и где хранится вынесенное

Не каждый тип участвует: «только некоторые типы данных поддерживают TOAST — нет необходимости накладывать накладные расходы на типы, которые не могут давать больших значений полей. Чтобы поддерживать TOAST, тип данных должен иметь переменно-длинное (varlena) представление» (65.2). К TOAST-able типам относятся text, varchar, bytea, jsonb — любые, у которых длина не фиксирована; int или date в этом не нуждаются. Хранилище вынесенных значений — отдельная служебная таблица: «если какие-либо столбцы таблицы TOAST-able, таблица будет иметь связанную TOAST-таблицу, чей OID хранится в записи pg_class.reltoastrelid таблицы» (65.2.1). Значение нарезается: «вынесенные из строки значения делятся (после сжатия, если оно применялось) на куски (chunks) размером не более TOAST_MAX_CHUNK_SIZE байт (по умолчанию это значение выбирается так, чтобы четыре строки-куска поместились на страницу, что даёт около 2000 байт). Каждый кусок хранится как отдельная строка в TOAST-таблице, принадлежащей таблице-владельцу. Каждая TOAST-таблица имеет столбцы chunk_id (OID, идентифицирующий конкретное тостированное значение), chunk_seq (порядковый номер куска внутри значения) и chunk_data (собственно данные куска). Уникальный индекс по chunk_id и chunk_seq обеспечивает быстрое извлечение значений» (65.2.1, дословно). А в самой строке-владельце остаётся только указатель: «указатель... должен хранить OID TOAST-таблицы... и OID конкретного значения (его chunk_id)... общий размер указателя на диске — 18 байт независимо от фактического размера представляемого значения» (65.2.1).

Порог срабатывания

«Код управления TOAST запускается только тогда, когда значение строки для сохранения в таблицу шире, чем TOAST_TUPLE_THRESHOLD байт (обычно 2 КБ). Код TOAST будет сжимать и/или выносить значения полей из строки, пока значение строки не станет короче, чем TOAST_TUPLE_TARGET байт (тоже обычно 2 КБ, с возможностью настройки), или пока больше выгоды получить нельзя» (65.2.1, дословно). Числа не магические: в коде порог привязан к странице — src/include/access/heaptoast.h на коммите 083ac033419f690758508e08c1736089384bbee8: TOAST_TUPLES_PER_PAGE = 4 (строка 45) и TOAST_TUPLE_THRESHOLD = «наибольший размер кортежа, для которого на heap-страницу помещаются 4 кортежа» (строка 48; комментарий выше: «выбираем оба значения так, чтобы соответствовать наибольшему размеру кортежа, при котором TOAST_TUPLES_PER_PAGE кортежей помещаются на heap-страницу»).

Четыре стратегии хранения

Как именно поступать с конкретным столбцом, задаёт стратегия. «Код управления TOAST распознаёт четыре разные стратегии хранения TOAST-able столбцов на диске» (65.2, дословно):

СтратегияПоведение (65.2, дословно)
PLAIN«Предотвращает и сжатие, и вынос из строки. Это единственно возможная стратегия для столбцов не-TOAST-able типов данных»
EXTENDED«Разрешает и сжатие, и вынос из строки. Это значение по умолчанию для большинства TOAST-able типов данных. Сжатие будет предпринято первым, затем вынос из строки, если строка всё ещё слишком велика»
EXTERNAL«Разрешает вынос из строки, но не сжатие. Использование EXTERNAL сделает операции подстроки на широких столбцах text и bytea более быстрыми (ценой увеличенного пространства хранения), потому что эти операции оптимизированы для извлечения только необходимых частей вынесенного значения, когда оно не сжато»
MAIN«Разрешает сжатие, но не вынос из строки. (В действительности вынос из строки всё же будет выполнен для таких столбцов, но только как последнее средство, когда нет другого способа сделать строку достаточно маленькой для размещения на странице)»

Стратегия по умолчанию задана типом, но «стратегия для конкретного столбца таблицы может быть изменена командой ALTER TABLE ... SET STORAGE» (65.2). Справочник уточняет эффект: «Эта форма устанавливает режим хранения для столбца. Она контролирует, хранится ли столбец в строке или во вторичной TOAST-таблице, и должны ли данные сжиматься... Обратите внимание, что ALTER TABLE ... SET STORAGE сама по себе ничего не меняет в таблице; она только задаёт стратегию, которая будет применяться при будущих обновлениях таблицы» (/docs/17/sql-altertable.html). Текущее состояние видно в каталоге: столбец attstorage — «обычно копия pg_type.typstorage типа этого столбца. Для TOAST-able типов данных может быть изменён после создания столбца для управления политикой хранения» (pg_attribute, 51.7), а значения букв описаны в pg_type (51.64): «p (plain): значения всегда должны храниться просто...; e (external): значения могут храниться во вторичном TOAST-отношении...; m (main): значения могут сжиматься и храниться в строке; x (extended): значения могут сжиматься и/или перемещаться во вторичное отношение. x — обычный выбор для toast-able типов».

Демонстрация: строка уезжает в TOAST-таблицу

Расширим читательский дневник полноценными обзорами (ограничение varchar(500) из главы 4.2 мало для эссе — text не ограничивает длину, глава 3.1):

CREATE TABLE reviews_full (
    review_id int PRIMARY KEY,
    reader_id int REFERENCES readers,
    book_id int REFERENCES books ON DELETE CASCADE,
    body text
);

INSERT INTO reviews_full
VALUES (101, 2, 1, repeat('замечательно ', 2000));

SELECT attname, attstorage
FROM pg_attribute
WHERE attrelid = 'reviews_full'::regclass AND attnum > 0;

SELECT reltoastrelid, reltoastrelid::regclass AS toast_table
FROM pg_class
WHERE relname = 'reviews_full';
CREATE TABLE
INSERT 0 1
 attname  | attstorage 
----------+------------
 review_id | p
 reader_id | p
 book_id  | p
 body     | x
(4 rows)

 reltoastrelid | toast_table
---------------+--------------
         16387 | pg_toast.pg_toast_16384
(1 row)

Что выведено и почему: три целочисленных столбца имеют стратегию p (PLAIN) — «единственно возможная стратегия для столбцов не-TOAST-able типов данных»; у body типа text — x (EXTENDED) — «обычный выбор для toast-able типов» (pg_type, 51.64). У таблицы появилась TOAST-таблица (OID в reltoastrelid), а её имя видно через приведение ::regclass: pg_toast_16384. Имя не выдумка — код генерирует его по шаблону pg_toast_%u (подстановка OID таблицы-владельца) в src/backend/catalog/toasting.c (строка 199), и там же комментарий: «TOAST-таблицы для обычных отношений помещаются в pg_toast; для временных — в пер-backendное пространство имён temp-toast-таблиц» (строки 234–235). Числа у вас будут другими — это OID объектов вашей базы; заметьте, что число в имени TOAST-таблицы — OID самой reviews_full (16384), а reltoastrelid (16387) — OID её TOAST-таблицы. Вставленный текст — 52 КБ (52 000 байт: «замечательно » — 13 символов по 2 байта в UTF-8, умноженные на 2000; в двоичных единицах — около 51 КиБ) при стратегии EXTENDED сначала был сжат: хорошо повторяющиеся данные жмутся сильно, и строка могла остаться в главной таблице. Проверим честно, без сжатия:

ALTER TABLE reviews_full ALTER COLUMN body SET STORAGE EXTERNAL;

INSERT INTO reviews_full
VALUES (102, 3, 4, repeat('бессмертно ', 4000));

SELECT attstorage FROM pg_attribute
WHERE attrelid = 'reviews_full'::regclass AND attname = 'body';

SELECT pg_size_pretty(pg_relation_size('reviews_full')) AS main_table,
       pg_size_pretty(pg_relation_size('pg_toast.pg_toast_16384')) AS toast_table;
ALTER TABLE
INSERT 0 1
 attstorage
------------
 e
(1 row)

 main_table | toast_table 
------------+------------
 8 kB       | 88 kB
(1 row)

Что выведено и почему: после SET STORAGE столбец получил стратегию e (EXTERNAL) — «может храниться во вторичном TOAST-отношении» (51.64); сами данные первой строки при этом не тронуты — «SET STORAGE сама по себе ничего не меняет в таблице» (sql-altertable). Новая строка с текстом около 86 КиБ («бессмертно » — 22 байта: 11 символов по 2 в UTF-8, умноженные на 4000) не сжималась и была вынесена: в главной таблице — по-прежнему одна страница, в TOAST-таблице — десятки килобайт чанков. Прикинем: 88 000 байт делятся на чанки по ~2000 — примерно 44–45 кусков, «четыре куска на страницу» (65.2.1) — 11–12 страниц, то есть 88–96 КБ (в нашем запуске — 88 kB); ваше число может отличаться на страницу-другую из-за накладных расходов. С каждым новым большим значением toast_table растёт, а main_table — нет. При чтении SELECT body всё работает прозрачно: «это происходит прозрачно для пользователя» (65.2) — сервер сам собирает значение из чанков по индексу (chunk_id, chunk_seq).

Механизм в коде

При каждой вставке/обновлении heap-строки вызывается heap_toast_insert_or_update — файл src/backend/access/heap/heaptoast.c на базовом коммите (строка 96; шапка файла: «Try to make a given tuple fit into one page by compressing or moving off attributes» — «попытаться уместить данный кортеж в одну страницу, сжимая или вынося атрибуты»). Порядок раундов зафиксирован в комментарии на строках 162–167: «1: Сжимать в строке атрибуты с attstorage EXTENDED и немедленно выносить очень большие атрибуты с attstorage EXTENDED или EXTERNAL; 2: Выносить атрибуты с attstorage EXTENDED или EXTERNAL; 3: Сжимать в строке атрибуты с attstorage MAIN; 4: Выносить атрибуты с attstorage MAIN». Ключевой критерий цикла — суммарный размер данных строки против maxDataLen = RelationGetToastTupleTarget(rel, TOAST_TUPLE_TARGET) - hoff (строка 177). Само вынесение делает toast_tuple_externalize, а запись чанков — toast_save_datum в src/backend/access/common/toast_internals.c (строка 119): цикл «Разбить элемент на куски» (строка 304) нарезает данные порциями Min(TOAST_MAX_CHUNK_SIZE, data_todo) (строка 313) и каждую вставляет в TOAST-таблицу через heap_insert (строка 323) с записью в уникальный индекс. Удаление строки освобождает чанки: heap_toast_delete (heaptoast.c, строка 43) → toast_delete_datum (toast_internals.c, строка 385).

Приятное следствие для конкурентных обновлений (глава 6.4): «во время операции UPDATE значения неизменённых полей обычно сохраняются как есть; поэтому UPDATE строки с вынесенными значениями не несёт затрат TOAST, если ни одно из вынесенных значений не меняется» (65.2) — новые чанки не пишутся, а новая версия строки разделяет старые.

Связь с теорией

Вынос больших значений в отдельное переполненное хранилище — классическая тема организации хранения: курс CMU 15-445 (Spring 2025) разбирает модели хранения и сжатие в лекции #06 Storage Models & Compression, включая overflow-страницы для больших значений; Silberschatz (7-е изд., § 13.1) описывает разбивку записей, не помещающихся в блок, на «сборки из блоков» (наподобие словарей блоков). PostgreSQL добавляет два штриха к учебниковой схеме: сжатие перед выносом (по стратегии столбца) и полная прозрачность для SQL — «large field values are compressed and/or broken up... transparently to the user» (65.2). Книга «PostgreSQL изнутри» (Ч. I) описывает TOAST в том же ключе; детали этой главы сверены с документацией 65.2 и кодом на базовом коммите.

Проверь себя

Вопрос 1. Почему INSERT строки с полем body размером 52 КБ (52 000 байт) не падает с ошибкой, хотя «кортежи не могут пересекать несколько страниц»?

Ответ. Перед записью heap_toast_insert_or_update (heaptoast.c, строка 96) приводит строку к размеру: «большие значения полей сжимаются и/или разбиваются на несколько физических строк» (65.2). При EXTERNAL значение выносится чанками в TOAST-таблицу (toast_save_datum, toast_internals.c, строка 119), а в самой строке остаётся «указатель... 18 байт независимо от фактического размера представляемого значения» (65.2.1) — строка помещается на страницу.

Вопрос 2. В таблице body text со стратегией по умолчанию. Что произойдёт при INSERT значения на 3 КБ и почему — сжатие, вынос, оба или ничего?

Ответ. Стратегия text по умолчанию — EXTENDED («это значение по умолчанию для большинства TOAST-able типов», 65.2). Код TOAST «запускается только тогда, когда значение строки... шире, чем TOAST_TUPLE_THRESHOLD байт (обычно 2 КБ)» (65.2.1), а 3 КБ больше порога, значит обрабатываться будет вся строка; для EXTENDED «сжатие будет предпринято первым, затем вынос из строки, если строка всё ещё слишком велика». Если после сжатия строка станет меньше ~2 КБ, она останется в главной таблице сжатой; иначе большой атрибут поедет в TOAST-таблицу.

Вопрос 3. Выполнили ALTER TABLE reviews_full ALTER COLUMN body SET STORAGE EXTERNAL. Изменились ли уже вставленные строки, и что изменится для новых INSERT?

Ответ. Старые строки не тронуты: «ALTER TABLE... SET STORAGE сама по себе ничего не меняет в таблице; она только задаёт стратегию, которая будет применяться при будущих обновлениях таблицы» (sql-altertable). Новые значения перестанут сжиматься («EXTERNAL разрешает вынос из строки, но не сжатие», 65.2) и будут вынесены чанками в TOAST-таблицу; выгода — «операции подстроки... более быстрые» на широких text (65.2), цена — увеличенное пространство хранения.
