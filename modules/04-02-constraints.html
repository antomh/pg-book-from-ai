Глава 4.2. Ограничения: NOT NULL, UNIQUE, PK, FK, CHECK

Уровень: J · узел карты тем: T19 · PostgreSQL 17.11

Отчёт упал на строке-сироте

Через месяц после запуска дневника чтения отчёт «книги и их авторы» падает на нескольких строках: у книг, добавленных «быстрым импортом», author_id равен числу, которого нет в таблице авторов, — это «сироты». В другом месте два пользователя зарегистрированы на один email, потому что проверка уникальности жила в коде одного из двух приложений, а не в базе. Мораль: если данные обязаны удовлетворять правилу, правило должно жить в базе — тогда его не обойдёт ни один клиент, включая ручной INSERT администратора. Инструмент — ограничения. Раздел 5.5 документации (/docs/17/ddl-constraints.html) начинается с той же мысли: «типы данных — способ ограничить вид данных... но для многих приложений даваемых ими ограничений слишком мало», а завершается обещанием: «если пользователь попытается сохранить данные, нарушающие ограничение, будет выдана ошибка».

CHECK: правило над значениями строки

«Check-ограничение — самый общий тип ограничения. Оно позволяет указать, что значение в определённом столбце должно удовлетворять булеву (истинностному) выражению» (5.5.1). Пример из документации — цены: price numeric CHECK (price > 0). Правило можно именовать: «CONSTRAINT positive_price CHECK (price > 0)» — это «уточняет сообщения об ошибках и позволяет ссылаться на ограничение при его изменении»; без имени «система выберет имя за вас». Ограничение может охватывать и несколько столбцов (table constraint): в документации это пример CHECK (price > discounted_price).

Тонкость, которую легко упустить: из справочника CREATE TABLE — «выражения, вычисляющиеся в TRUE или UNKNOWN, проходят». UNKNOWN — это NULL трёхзначной логики из главы 2.1. Поэтому CHECK (rating > 0) не отклонит строку с rating NULL: NULL > 0 — UNKNOWN, а не FALSE. Если NULL должен быть запрещён — нужен отдельный NOT NULL.

NOT NULL и UNIQUE

NOT NULL: «ограничение not-null просто указывает, что столбец не должен принимать значение null» (5.5.2); оно «функционально эквивалентно созданию check-ограничения CHECK (имя_столбца IS NOT NULL), но в PostgreSQL явное not-null-ограничение создаётся эффективнее».

UNIQUE (5.5.3): «гарантирует, что данные, содержащиеся в столбце или группе столбцов, уникальны среди всех строк таблицы». Два механизма, о которых нужно знать заранее. Первый: «добавление unique-ограничения автоматически создаст уникальный B-tree-индекс по столбцу или группе столбцов, перечисленных в ограничении» — то же верно для первичного ключа. Второй — NULL: «по умолчанию два null-значения не считаются равными при этом сравнении. Это значит, что даже при наличии unique-ограничения возможно хранение дублирующихся строк, содержащих null хотя бы в одном из ограниченных столбцов». Изменяется поведение опцией NULLS NOT DISTINCT (описана там же в 5.5.3 и в справочнике CREATE TABLE).

PRIMARY KEY: один на таблицу

«Ограничение первичного ключа указывает, что столбец или группа столбцов могут использоваться как уникальный идентификатор строк таблицы. Это требует, чтобы значения были одновременно уникальны и не null» (5.5.4). Документация демонстрирует эквивалентность product_no integer UNIQUE NOT NULL и product_no integer PRIMARY KEY, а также составной вариант PRIMARY KEY (a, c). Отсюда три следствия: «добавление первичного ключа автоматически создаст уникальный B-tree-индекс по столбцу... и пометит столбец(ы) как NOT NULL»; «таблица может иметь не более одного первичного ключа»; уникальных и not-null ограничений может быть сколько угодно, «но лишь одно может быть обозначено как первичный ключ».

FOREIGN KEY: ссылочная целостность

«Ограничение внешнего ключа указывает, что значения в столбце (или группе столбцов) должны совпадать со значениями, присутствующими в некоторой строке другой таблицы. Мы говорим, что это поддерживает ссылочную целостность между двумя связанными таблицами» (5.5.5). В нашей предметной области — отзывы, ссылающиеся на книги и читателей. В главе 2.8 мы пользовались упрощённой учебной таблицей (review_id, book_id, rating) — без читателя и текста; ниже — полный DDL дневника. Это целевая схема: как привести таблицу из главы 2.8 к этому виду, покажет мост из команд ALTER TABLE в главе 4.4:

CREATE TABLE reviews (
    review_id  bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    book_id    integer NOT NULL REFERENCES books ON DELETE CASCADE,
    reader_id  integer NOT NULL REFERENCES readers,
    rating     smallint NOT NULL CHECK (rating BETWEEN 1 AND 5),
    comment    text,
    created_at timestamptz NOT NULL DEFAULT now()
);

Сокращённая форма: «в отсутствие списка столбцов первичный ключ ссылочной таблицы используется как ссылаемый столбец» — поэтому REFERENCES books не указывает book_id явно. Внешний ключ может ссылаться и на собственную таблицу («self-referential foreign key») — именно так устроено дерево категорий из главы 2.7: parent_id REFERENCES categories. И ещё одно наблюдение из 5.5.5: «у таблицы может быть более одного ограничения внешнего ключа. Это используется для реализации связей многие-к-многим» — наш reviews с двумя FK и есть такая таблица.

Что произойдёт при нарушении — документированный пример из туториала (3.3, /docs/17/tutorial-fk.html), где таблица weather ссылается на cities:

ERROR:  insert or update on table "weather" violates foreign key constraint "weather_city_fkey"
DETAIL:  Key (city)=(Berkeley) is not present in table "cities".

Это дословный вывод из документации: попытка вставить погоду для несуществующего города отклонена. Имя ограничения (weather_city_fkey) сгенерировано системой — так выглядит автогенерация имён в сообщениях об ошибках; задав явное имя через CONSTRAINT имя ..., вы контролируете, что увидит разработчик в логе. То же сообщение встретит наш INSERT с несуществующим book_id.

ON DELETE: что делать со ссылками при удалении

Внешний ключ запрещает удалять строку, на которую ссылаются? Не обязательно — поведение выбирается при описании. Документация перечисляет варианты дословно: «RESTRICT предотвращает удаление ссылаемой строки. NO ACTION означает, что если при проверке ограничения ещё существуют ссылающиеся строки, выдаётся ошибка; это поведение по умолчанию, если ничего не указано. (Существенная разница между этими двумя вариантами в том, что NO ACTION позволяет отложить проверку до конца транзакции, тогда как RESTRICT — нет.) CASCADE указывает, что при удалении ссылаемой строки ссылающиеся строки должны быть удалены автоматически. Есть ещё два варианта: SET NULL и SET DEFAULT — они приводят к тому, что ссылаемые столбцы в ссылающихся строках устанавливаются в null или значения по умолчанию».

Как выбирать — критерий из документации: «когда ссылающаяся таблица представляет нечто, являющееся компонентом того, что представлено ссылаемой таблицей, и не может существовать независимо, уместен CASCADE. Если две таблицы представляют независимые объекты, более уместны RESTRICT или NO ACTION». Отзыв не существует без книги — поэтому в нашем DDL ON DELETE CASCADE; читатель и отзыв — независимые объекты, поэтому для reader_id оставлен default (NO ACTION): удаление читателя с отзывами потребует явного решения в коде.

FK не создаёт индекс сам

Пункт, который чаще всего вспоминают слишком поздно. Дословно из 5.5.5: «поскольку DELETE строки из ссылаемой таблицы или UPDATE ссылаемого столбца потребуют сканирования ссылающейся таблицы в поисках строк, соответствующих старому значению, часто полезно индексировать и ссылающиеся столбцы. Поскольку это нужно не всегда и существует много вариантов, как индексировать, объявление ограничения внешнего ключа не создаёт автоматически индекс по ссылающимся столбцам». То есть наш reviews.book_id для быстрых DELETE/UPDATE по books.book_id стоит проиндексировать вручную (CREATE INDEX — глава 8.1).

Теория: целостность по Silberschatz

Ограничения, которые мы перечислили, — конкретные имена механизмов охраны целостности. Silberschatz (§ 4.4 «Integrity Constraints», гл. 4, 7-е изд.) разделяет их на доменные ограничения (значения атрибута берутся из допустимого множества — в PostgreSQL эту роль несут типы данных из модуля 3 и CHECK) и ссылочную целостность (referential integrity: ссылающееся значение обязано существовать — в точности семантика FOREIGN KEY из 5.5.5, включая те же пять действий при удалении ссылаемой строки). Теория формулирует это через предикаты целостности, которые СУБД обязана проверять при каждом изменении; в PostgreSQL место этой проверки — конвейер выполнения команды сразу после модификации строки (при NOT DEFERRABLE-ограничениях, то есть по умолчанию, — немедленно; DEFERRABLE-вариант упоминаем справочно, справочник CREATE TABLE).

Проверь себя

Вопрос 1. Почему CHECK (rating BETWEEN 1 AND 5) пропускает строку с rating = NULL, и как заставить базу отклонить её?

Ответ. CHECK принимает выражения, вычисляющиеся «в TRUE или UNKNOWN» (CREATE TABLE, Parameters). Для NULL предикат BETWEEN даёт UNKNOWN — строка проходит. Запретить NULL может только NOT NULL; связка rating smallint NOT NULL CHECK (...) закрывает обе дыры.

Вопрос 2. Что произойдёт при DELETE FROM books WHERE book_id = 1 для таблицы reviews, созданной в этой главе, и почему это правильный выбор для отзывов?

Ответ. Отзывы книги 1 будут удалены автоматически: book_id ... REFERENCES books ON DELETE CASCADE, а «CASCADE указывает, что при удалении ссылаемой строки ссылающиеся строки должны быть удалены автоматически» (5.5.5). Для читателя оставлен default NO ACTION: он получит ошибку при наличии отзывов. Выбор обоснован критерием документации: «компонент, не существующий независимо» — CASCADE; «независимые объекты» — RESTRICT или NO ACTION.

Вопрос 3. Какие индексы появляются автоматически при объявлении PRIMARY KEY и UNIQUE, и какой индекс НЕ появится при объявлении FOREIGN KEY?

Ответ. PRIMARY KEY: «автоматически создаст уникальный B-tree-индекс по столбцу или группе столбцов» и пометит столбцы NOT NULL (5.5.4). UNIQUE: аналогично «автоматически создаст уникальный B-tree-индекс» (5.5.3). FOREIGN KEY: индекса не будет вовсе — «объявление ограничения внешнего ключа не создаёт автоматически индекс по ссылающимся столбцам» (5.5.5); его создают вручную, если нужны быстрые DELETE/UPDATE ссылаемых строк.
