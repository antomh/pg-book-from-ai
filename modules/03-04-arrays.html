Глава 3.4. Массивы

Уровень: J+ · узел карты тем: T15 · PostgreSQL 17.11

У книги несколько тегов: куда их положить

Теги книги — типичный многозначный атрибут: «классика», «поэзия», «роман». Реляционный ответ — отдельная таблица тегов и таблица связи «книга–тег» (модуль 4). Но для маленьких и «плоских» списков PostgreSQL предлагает более короткий путь: хранить список прямо в столбце как массив. Глава отвечает на вопросы: как объявлять, записывать, читать и фильтровать массивы — и где граница разумности этого приёма. Это глава уровня J+.

Объявление и запись

«PostgreSQL позволяет определять столбцы таблицы как переменной длины многомерные массивы. Массивы любого встроенного или пользовательского базового типа, enum-типа, составного типа, типа диапазона или домена могут быть созданы» — раздел 8.15 (/docs/17/arrays.html). Тип массива записывается добавлением [] к типу элемента; сами массивы как тип столбца — расширение PostgreSQL: в стандарте SQL массивных типов нет (стандарт описывает лишь запись значений конструктором ARRAY для одномерных массивов, о чём ниже). Добавим теги книгам:

ALTER TABLE books ADD COLUMN tags text[];

UPDATE books SET tags = ARRAY['классика', 'поэзия'] WHERE book_id = 1;
UPDATE books SET tags = ARRAY['классика']             WHERE book_id = 2;
UPDATE books SET tags = ARRAY['классика', 'роман']    WHERE book_id = 4;

Два способа записи значения — конструктор ARRAY[...] и строковый литерал в фигурных скобках (документация показывает оба на таблице sal_emp из 8.15.1):

UPDATE books SET tags = '{"детектив", NULL}' WHERE book_id = 6;

SELECT title, tags FROM books WHERE book_id IN (1, 6);
       title       |         tags
-------------------+----------------------
 Евгений Онегин    | {классика,поэзия}
 Детектив XXI века | {детектив,NULL}
(2 rows)

Что выведено и почему: вывод массива — в фигурных скобках через запятую; массив может содержать NULL-элемент — это не то же самое, что NULL-массив или пустой массив. Важная деталь про объявления из 8.15.1: «текущая реализация не принуждает к фиксированной длине массива... объявление размера или числа измерений массива в CREATE TABLE — просто документация; оно не влияет на поведение во время выполнения» — то есть text[3] не ограничит длину.

Чтение: индексы, срезы, размеры

«По умолчанию PostgreSQL использует нумерацию массивов с единицы: массив из n элементов начинается с array[1] и кончается array[n]» (8.15.3). Извлечение элемента, среза и длин:

SELECT tags[1]          AS first_tag,
       tags[1:2]       AS slice,
       cardinality(tags) AS total_tags,
       array_length(tags, 1) AS dim1_len
FROM books WHERE book_id = 1;
 first_tag |      slice      | total_tags | dim1_len
-----------+-----------------+------------+----------
 классика  | {классика,поэзия} |          2 |        2
(1 row)

Что выведено и почему: tags[1] — первый элемент (нумерация с 1); tags[1:2] — срез, сам массив; cardinality — «общее число элементов массива по всем измерениям; фактически — число строк, которое вернул бы unnest» (9.19); array_length(tags, 1) — длина первого измерения (и NULL для отсутствующих измерений — «NULL вместо 0 для пустых или отсутствующих измерений массива», 9.19). Поведение при выходе за границы задокументировано точно: «выражение индекса массива вернёт null, если сам массив или любое из выражений индексов равны null. Также null возвращается, если индекс вне границ массива (этот случай не вызывает ошибку)... ссылка на массив с неверным числом индексов даёт null, а не ошибку» (8.15.3, перевод дословный).

Поиск по массиву

Первый способ — из 8.15.5 дословно: «альтернативный метод» поиска по массиву — оператор ANY: SELECT * FROM sal_emp WHERE 10000 = ANY (pay_by_quarter) (в документации это замена громоздкого WHERE pay_by_quarter[1] = 10000 OR ...). На тегах:

SELECT title FROM books WHERE 'поэзия' = ANY (tags);
      title
-----------------
 Евгений Онегин
(1 row)

Второй способ — специальные операторы из таблицы 9.19 (/docs/17/functions-array.html): @> — «содержит ли первый массив второй» (ARRAY[1,4,3] @> ARRAY[3,1] → t), && — «перекрываются ли массивы, то есть есть ли общие элементы», <@ — обратное вложению, || — конкатенация:

SELECT title FROM books WHERE tags @> ARRAY['классика'];
SELECT title FROM books WHERE tags && ARRAY['поэзия', 'фантастика'];
SELECT tags || ARRAY['новинка'] AS extended FROM books WHERE book_id = 2;

Что будет выведено и почему: первый запрос вернёт три книги — «Онегина», «Руслана» и «Войну и мир» (их массивы содержат 'классика'); второй — только «Онегина» (пересечение массивов непусто лишь там, где есть 'поэзия'); третий — массив {классика,новинка} — конкатенация || добавила элемент.

Массив и строки: unnest и array_agg

unnest(anyarray) — «разворачивает массив в множество строк. Элементы массива читаются в порядке хранения» (9.19). Вместе с агрегатом array_agg («собирает все входные значения, включая null, в массив», 9.21) получается обратимое преобразование:

SELECT book_id, unnest(tags) AS tag
FROM books
WHERE book_id IN (1, 2)
ORDER BY book_id, tag;
 book_id |   tag
---------+----------
       1 | классика
       1 | поэзия
       2 | классика
(3 rows)
SELECT book_id, array_agg(tag ORDER BY tag) AS tags
FROM (SELECT book_id, unnest(tags) AS tag
      FROM books WHERE book_id IN (1, 2)) AS flat
GROUP BY book_id;
 book_id |         tags
---------+----------------------
       1 | {классика,поэзия}
       2 | {классика}
(2 rows)

Что выведено и почему: unnest превратил два массива в три строки (по числу элементов), array_agg собрал строки каждой группы обратно в массив — по сути, это «группировка по книге» из главы 2.4, только с массивом на выходе.

Когда массив — правильный выбор

Массив уместен, когда список — атомарный атрибут одной строки (теги записи, телефонные номера контакта) и вы готовы жить без ссылочной целостности на элементы: внешний ключ не может ссылаться на элементы массива — FK ссылается на ключи таблицы (глава 1.1), а элементы массива таблицей не являются. Как только по элементам нужны отдельные атрибуты, уникальность или связи — это уже таблица тегов и таблица связи (модуль 4); массивы при этом остаются удобным форматом вывода: «собрать теги книги в одну строку отчёта» — типовая работа array_agg.

Проверь себя

Вопрос 1. Что вернёт tags[1] для книги 6 с массивом '{"детектив", NULL}' и почему обращение к tags[5] — не ошибка?

Ответ. tags[1] = 'детектив' (нумерация с единицы, 8.15.3). tags[5] вернёт NULL: обращение к отсутствующему элементу не проверяется как ошибка — как и array_length, работающий «NULL вместо 0» с отсутствующими измерениями (9.19). NULL-элемент внутри массива при этом остаётся NULL-значением элемента, не «концом» массива.

Вопрос 2. Чем tags @> ARRAY['классика','поэзия'] отличается от tags && ARRAY['классика','поэзия']?

Ответ. @> требует, чтобы массив содержал все перечисленные элементы («содержит ли первый массив второй»), && — чтобы был хотя бы один общий элемент («есть ли элементы в общем»). Определения — таблица операторов массивов в 9.19: ARRAY[1,4,3] @> ARRAY[3,1] → t; ARRAY[1,4,3] && ARRAY[2,1] → t.

Вопрос 3. Почему объявление tags text[3] не защитит от массива из пяти элементов, и что выбрать, если защита нужна?

Ответ. «Объявление размера или числа измерений массива в CREATE TABLE — просто документация; оно не влияет на поведение во время выполнения» (8.15.1). Если нужен инвариант — использовать ограничение целостности на столбце, например CHECK (cardinality(tags) <= 3) (ограничения CHECK — тема главы 4.2).
