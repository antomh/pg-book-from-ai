Глава 9.1. Путь запроса: от текста до результата

Уровень: J · узел карты тем: T41 · PostgreSQL 17.11

Куда исчезает SELECT из представления

В главе 4.4 вы создали представление book_reviews — «виртуальную таблицу» над reviews, books и authors. Запрос SELECT * FROM book_reviews возвращает строки трёх таблиц, хотя самого объекта book_reviews в базе нет — там только сохранённый SELECT. Значит, между вашим текстом и чтением таблиц кто-то подставил тело представления вместо его имени. Кто, в какой момент и что ещё происходит с запросом по дороге? В главе 7.1 мы прошли путь запроса обзорно; теперь разберём каждую станцию: разбор, семантический анализ, переписывание, планирование, исполнение.

Четыре станции

Внутренний обзор (50.1 /docs/17/query-path.html, перевод дословный): «стадия парсера проверяет запрос, переданный приложением, на корректность синтаксиса и создаёт дерево запроса. Система перезаписи берёт дерево запроса, созданное парсером, и ищет правила (сохранённые в системных каталогах) для применения к дереву запроса. Она выполняет преобразования, заданные в телах правил. Одно из применений системы перезаписи — реализация представлений. Всякий раз, когда выполняется запрос к представлению (то есть к виртуальной таблице), система перезаписи преобразует запрос пользователя к запросу, который обращается к базовым таблицам, заданным в определении представления, вместо него. Планировщик/оптимизатор берёт (переписанное) дерево запроса и создаёт план запроса, который будет входом для исполнителя. Он делает это, сначала создавая все возможные пути, ведущие к тому же результату. Например, если по индексу на сканируемое отношение есть два пути сканирования: простое последовательное сканирование и сканирование с использованием индекса. Затем оценивается стоимость выполнения каждого пути и выбирается самый дешёвый. Самый дешёвый путь разворачивается в полный план, который может использовать исполнитель. Исполнитель рекурсивно проходит по дереву плана и извлекает строки способом, представленным планом». Ответ на вопрос главы: подстановку делает станция переписывания — вторая по счёту.

Станции на ощупь: три ошибки в трёх разных местах

Каждую станцию можно «постучать» неправильным запросом. Ошибка на станции видна по тексту сообщения:

SELCT * FROM book_reviews;

SELECT * FROM book_reviewz;

SELECT nonexistent_col FROM book_reviews;
ERROR:  syntax error at or near "SELCT"
LINE 1: SELCT * FROM book_reviews;
        ^

ERROR:  relation "book_reviewz" does not exist
LINE 1: SELECT * FROM book_reviewz;
                  ^

ERROR:  column "nonexistent_col" of relation "book_reviews" does not exist
LINE 1: SELECT nonexistent_col FROM book_reviews;

Что выведено и почему: первая ошибка — грамматика: сообщение «syntax error» формирует парсер (вызовы parser_yyerror("syntax error") в грамматике src/backend/parser/gram.y — строки 18742 и 18759 на базовом коммите 083ac033419f690758508e08c1736089384bbee8). Вторая и третья — семантический анализ: слова распознаны, но объекта (или столбца) с таким именем нет; сообщения «relation ... does not exist» и «column ... does not exist» выдаёт анализ имён в src/backend/parser/parse_relation.c (строки 1443/1451 и 737 соответственно). Важно: обе ошибки пойманы до планирования и исполнения — планировщик никогда не увидел бы несуществующую таблицу. Третья ошибка — та же станция анализа имён, но проверяется столбец: слова запроса корректны, таблица существует, а вот столбца в ней нет. Все три сообщения приходят из разных мест конвейера — по тексту ошибки можно понять, как далеко запрос успел пройти.

Оркестратор и исполнители станций в коде

Обработку простого запроса ведёт exec_simple_query в src/backend/tcop/postgres.c (строка 1018). Она вызывает по очереди: pg_parse_query (строка 616) — синтаксический разбор в дерево, затем анализ и pg_rewrite_query (строка 809) — перезапись, затем pg_plan_query (строка 891) — планирование. Семантический анализ превращает «сырое» дерево в дерево запроса: «рекурсивно преобразует дерево разбора в дерево запроса» — комментарий к transformStmt в src/backend/parser/analyze.c (строки 307–309, сигнатура на 311). Перезапись начинается в уже знакомом по главе 4.4 месте: «Primary entry point to the query rewriter» — QueryRewrite в src/backend/rewrite/rewriteHandler.c (строка 4556). Планирование: subquery_planner (src/backend/optimizer/plan/planner.c, строка 629) — обход подзапросов и подготовка, standard_planner (там же, строка 288) — сборка окончательного плана. Как планировщик перебирает варианты, описывает README каталога optimizer: «во время планирования/оптимизации мы строим деревья "путей" (Path), представляющие разные способы выполнения запроса. Мы выбираем самый дешёвый путь... и превращаем его в план для передачи исполнителю... Оптимизатор строит структуру RelOptInfo для каждого базового отношения, используемого в запросе... Для каждого RelOptInfo строится список путей, представляющих правдоподобные способы сканирования или соединения этого отношения. Рассмотрев все правдоподобные пути, выбираем самый дешёвый по оценкам стоимости планировщика» (src/backend/optimizer/README, перевод дословный).

Связь с уже изученным

Теперь узлы вашей карты смыкаются: исполнитель «рекурсивно проходит по дереву плана» — это Volcano-модель «один кортеж за раз» из теории обработки запросов; станции работают внутри backend-процесса из главы 7.1; выбор «самого дешёвого пути» — это то, что вы увидите числами в EXPLAIN (глава 9.3), а «сначала создаём все возможные пути... последовательное сканирование или индекс» — обещание индексов из главы 8.1. Порядок станций фиксирован для каждого оператора, но продумывается он на всю транзакцию: «все запросы, сгенерированные строкой запроса, будут в одном и том же командном блоке, если только не встретится BEGIN/COMMIT» — комментарий в exec_simple_query (postgres.c, строки 1045–1050).

Связь с теорией

Станции — это классический конвейер обработки запросов из учебников: Silberschatz (7-е изд., гл. 15 Query Processing: § 15.1 Overview — разбор и трансляция, выбор плана, исполнение) описывает те же шаги: «перед выполнением запроса система должна транслировать его в форму, пригодную для обработки». PostgreSQL добавляет нетипичную для учебников станцию перезаписи правил (rule system) — именно она делает представления «виртуальными таблицами» без копирования данных. Курс CMU 15-445 разбирает конвейер обработки запроса в лекциях #13–15 (Query Processing I–III). План как дерево операторов с интерфейсом next() — модель Volcano (обзор в лекциях курса); в коде это итераторы-узлы из каталога executor.

Проверь себя

Вопрос 1. Расставьте по порядку: планирование, разбор, перезапись, семантический анализ, исполнение. На какой станции SELECT из представления становится SELECT из таблиц?

Ответ. Разбор (синтаксис, gram.y) → семантический анализ (transformStmt — имена таблиц/столбцов, типы) → перезапись (QueryRewrite) → планирование (subquery_planner, standard_planner) → исполнение. Представление подставляется на станции перезаписи: «система перезаписи преобразует запрос пользователя к запросу, который обращается к базовым таблицам, заданным в определении представления» (50.1).

Вопрос 2. Чем ошибка «syntax error at or near "SELCT"» отличается по моменту возникновения от «relation "book_reviewz" does not exist», если оба запроса вводятся в psql?

Ответ. Оба сообщения появляются до исполнения — но на разных станциях: первая — грамматический разбор (грамматика не смогла сопоставить токен SELCT, gram.y, parser_yyerror), вторая — семантический анализ: «дерево разбора рекурсивно преобразуется в дерево запроса» (transformStmt, analyze.c), и анализ имён не нашёл объект (parse_relation.c). До планировщика и исполнителя запрос не доходит ни в одном случае.

Вопрос 3. Планировщик строит «все возможные пути» и выбирает «самый дешёвый». Откуда он знает, какой путь дешёвый, если ничего ещё не выполнял?

Ответ. Стоимость оценивается по модели стоимости и статистике, а не по замеру: планировщик перебирает пути («последовательное сканирование или сканирование с использованием индекса» — 50.1) и оценивает каждый по числу страниц, строк и операций — «затем оценивается стоимость выполнения каждого пути, и выбирается самый дешёвый» (50.1). Числа для оценки берутся из статистики таблиц — тема главы 9.2; сами единицы стоимости — глава 9.5.
