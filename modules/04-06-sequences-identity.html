Глава 4.6. Последовательности: SERIAL и GENERATED AS IDENTITY

Уровень: J · узел карты тем: T23 · PostgreSQL 17.11

id: 1, 2, 5. Кто съел 3 и 4?

В логе приложения записи сессий чтения получают номера 1, 2, 5, 6... Никто не удалял строки. Разработчик подозревает баг и тратит день на поиски «потерянных» id. На самом деле поведение документировано: номера раздаёт генератор, который не умеет брать обратно. Глава разбирает этот механизм — последовательности, — а заодно главный выбор проектировщика суррогатного ключа: serial (расширение PostgreSQL) против GENERATED AS IDENTITY (стандарт SQL).

Что такое последовательность

«CREATE SEQUENCE создаёт новый генератор порядковых номеров. Это включает создание и инициализацию новой специальной однорядной таблицы с заданным именем» — (/docs/17/sql-createsequence.html, перевод дословный). То есть последовательность — самостоятельный объект базы, «специальная однорядная таблица»; в системном каталоге она видна как отношение (глава 1.3). Работа с ней — функции из 9.17 (/docs/17/functions-sequence.html):

  • nextval(regclass) → bigint — «продвигает объект последовательности к следующему значению и возвращает его. Это делается атомарно: даже если несколько сеансов выполняют nextval конкурентно, каждый безопасно получит отличное значение последовательности»;
  • currval(regclass) — «значение, полученное последним вызовом nextval для этой последовательности в текущем сеансе» (и «ошибка выдаётся, если nextval никогда не вызывался для этой последовательности в текущем сеансе»);
  • setval(regclass, bigint) — ручная установка счётчика, «устанавливает текущее значение последовательности».

Диапазон — как у bigint: «последовательности основаны на арифметике bigint, поэтому диапазон не может превышать диапазон восьмибайтового целого» (Notes, CREATE SEQUENCE).

serial: «не настоящий тип»

Раздел 8.1.4 Serial Types (/docs/17/datatype-numeric.html) начинается с важной пометки: «этот раздел описывает специфичный для PostgreSQL способ создания автоинкрементного столбца. Другой способ — использовать стандартную для SQL возможность identity-столбцов». Само определение: «типы данных smallserial, serial и bigserial — не настоящие типы, а лишь нотационное удобство для создания столбцов уникальных идентификаторов». Удобство разворачивается в три команды дословно:

-- CREATE TABLE t (id serial); эквивалентно:
CREATE SEQUENCE t_id_seq AS integer;
CREATE TABLE t (
    id integer NOT NULL DEFAULT nextval('t_id_seq')
);
ALTER SEQUENCE t_id_seq OWNED BY t.id;

Отсюда видны три следствия. Первое: serial — это обычный integer NOT NULL DEFAULT nextval(...), и «в большинстве случаев вы захотели бы также прикрепить ограничение UNIQUE или PRIMARY KEY, чтобы предотвратить случайную вставку дубликатов, но это не делается автоматически». Второе: последовательность помечается «принадлежащей» столбцу («owned by»), «поэтому она будет удалена при удалении столбца или таблицы». Третье: DEFAULT — это выражение, значит конкретно у serial значения id при вставке берутся из nextval (глава 4.1 про DEFAULT).

Откуда дыры

Формулировка из 8.1.4 дословно: «поскольку smallserial, serial и bigserial реализованы с использованием последовательностей, в последовательности значений, появляющихся в столбце, могут быть "дыры" или пропуски, даже если строки никогда не удалялись. Значение, выделенное из последовательности, всё равно "расходуется", даже если строка с этим значением никогда не будет успешно вставлена в столбец таблицы. Это может произойти, например, если вставляющая транзакция откатывается». Причина глубже — в Notes к CREATE SEQUENCE: «поскольку вызовы nextval и setval никогда не откатываются, объекты последовательности нельзя использовать, если требуется "бесшовное" (gapless) назначение номеров». Демонстрация на identity-столбце (см. ниже) — с явным BEGIN/ROLLBACK:

CREATE TABLE reading_sessions (
    session_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    reader_id  integer NOT NULL REFERENCES readers,
    book_id    integer NOT NULL REFERENCES books,
    started_at timestamptz NOT NULL DEFAULT now()
);

INSERT INTO reading_sessions (reader_id, book_id) VALUES (1, 1);

BEGIN;
INSERT INTO reading_sessions (reader_id, book_id) VALUES (2, 4);
ROLLBACK;

INSERT INTO reading_sessions (reader_id, book_id) VALUES (1, 1);

SELECT session_id, reader_id, book_id FROM reading_sessions;
 session_id | reader_id | book_id
------------+-----------+---------
          1 |         1 |       1
          3 |         1 |       1
(2 rows)

Что выведено и почему: первая вставка получила session_id 1 (вызов nextval при INSERT); вставка внутри транзакции получила session_id 2 и откатилась вместе с транзакцией — но «вызовы nextval и setval никогда не откатываются» (Notes, CREATE SEQUENCE), поэтому номер 2 израсходован; последняя вставка получила следующий свободный номер — 3. Строк в таблице две, а счётчик последовательности показывает 3 — следующий INSERT получит 4. Практическое следствие: уникальность id гарантирует PRIMARY KEY, а непрерывность не гарантирует никто — и для прикладных ключей она не нужна.

GENERATED AS IDENTITY: стандартный способ

Identity-столбец описан в разделе 5.3 (/docs/17/ddl-identity-columns.html): «identity-столбец — это специальный столбец, генерируемый автоматически из неявной последовательности. Он может использоваться для генерации значений ключа». Отличия от serial — в дисциплине. Вариант ALWAYS (как в примере выше): «в команде INSERT, если выбран ALWAYS, значение, указанное пользователем, принимается, только если оператор INSERT указывает OVERRIDING SYSTEM VALUE». Вариант BY DEFAULT: «тогда значение, указанное пользователем, имеет приоритет» — поведение ближе к обычному DEFAULT из главы 4.1. Общее для обоих: «identity-столбец автоматически помечается как NOT NULL. Однако identity-столбец не гарантирует уникальность... Уникальность нужно обеспечивать ограничением PRIMARY KEY или UNIQUE».

Что выбрать в 2026 году: GENERATED ... AS IDENTITY. Аргументы: это «стандартная для SQL возможность» (8.1.4), семантика владения встроена в таблицу (неявная последовательность — часть определения столбца, а не отдельный объект с OWNED BY), а запрет ручной вставки при ALWAYS защищает от случайной порчи нумерации. serial встречается в существующих схемах повсеместно и потому должен читаться уверенно — но в новых миграциях стандартный вариант предпочтителен.

Проверь себя

Вопрос 1. Почему после ROLLBACK транзакции со INSERT следующий INSERT получает id через пропуск, и где это документировано?

Ответ. Значение уже выделено nextval, а «вызовы nextval и setval никогда не откатываются» (Notes, CREATE SEQUENCE); поэтому «значение, выделенное из последовательности, всё равно "расходуется", даже если строка с этим значением никогда не будет успешно вставлена... Это может произойти, например, если вставляющая транзакция откатывается» (8.1.4).

Вопрос 2. Что реально создаёт id serial в CREATE TABLE, и какие два ограничения при этом НЕ появятся автоматически?

Ответ. «Нотационное удобство»: CREATE SEQUENCE, столбец integer NOT NULL DEFAULT nextval(...) и OWNED BY (8.1.4). НЕ появятся: уникальность и первичный ключ — «в большинстве случаев вы захотели бы также прикрепить ограничение UNIQUE или PRIMARY KEY... но это не делается автоматически» (там же).

Вопрос 3. Чем GENERATED ALWAYS AS IDENTITY отличается от GENERATED BY DEFAULT AS IDENTITY на INSERT с явным значением id?

Ответ. При ALWAYS «значение, указанное пользователем, принимается, только если оператор INSERT указывает OVERRIDING SYSTEM VALUE»; при BY DEFAULT «значение, указанное пользователем, имеет приоритет» (5.3). Оба варианта «автоматически помечают столбец как NOT NULL» и оба не гарантируют уникальность без PRIMARY KEY/UNIQUE.
