Глава 4.4. ALTER TABLE и представления

Уровень: J · узел карты тем: T21 · PostgreSQL 17.11

Схема живёт дольше первого релиза

Через месяц после запуска продукт просит: хранить источник каждого отзыва (веб или приложение), переименовать колонку, добавить проверку. База не пустая и под нагрузкой — «удалить и пересоздать таблицу» не вариант. С другой стороны, коллеги копируют в код один и тот же JOIN из трёх таблиц, и при переименовании колонки правки разъезжаются по пятнадцати местам. На два этих класса задач PostgreSQL отвечает двумя инструментами: ALTER TABLE для изменения таблиц и представлениями для именованных запросов.

ALTER TABLE: что дёшево, что дорого

Справочник (/docs/17/sql-altertable.html) — самая объёмная команда DDL; для junior-уровня достаточно пяти форм. Первые две — дешёвые операции с метаданными:

ALTER TABLE reviews ADD COLUMN source text NOT NULL DEFAULT 'web';
ALTER TABLE books RENAME COLUMN rating TO base_rating;

Про ADD COLUMN справочник говорит дословно: «эта форма добавляет новый столбец в таблицу, используя тот же синтаксис, что CREATE TABLE». Почему миллионы строк не переписываются — отвечает примечание Notes: «когда столбец добавляется с ADD COLUMN и указан неволатильный (non-volatile) DEFAULT, значение по умолчанию вычисляется в момент выполнения оператора и результат сохраняется в метаданных таблицы. Это значение будет использоваться для столбца во всех существующих строках. Если DEFAULT не указан, используется NULL. В обоих случаях переписывание таблицы не требуется». Механизм: значение лежит в каталоге один раз, а не в каждой строке; при чтении старых строк PostgreSQL подставляет его. Дальше — граница дешевизны, дословно: «добавление столбца с волатильным DEFAULT или изменение типа существующего столбца потребует переписать всю таблицу и её индексы». Поэтому DEFAULT now() при ALTER — дорогая операция на большой таблице, а DEFAULT 'web' — мгновенная (про волатильность выражений — глава 10.1).

DROP COLUMN: «эта форма удаляет столбец из таблицы. Индексы и табличные ограничения, включающие этот столбец, будут удалены автоматически» (там же). RENAME меняет имя без изменения данных. Четвёртая форма — добавление ограничения на живые данные: «обычно эта форма вызывает сканирование таблицы для проверки, что все существующие строки удовлетворяют новому ограничению. Но если указана опция NOT VALID, этот потенциально долгий скан пропускается» — ограничение начнёт действовать на новые записи, а старые проверят позже (VALIDATE CONSTRAINT). Пятая — смена типа столбца (ALTER COLUMN ... TYPE ...), требующая перезаписи таблицы и индексов по цитате Notes выше.

Мост: от учебной таблицы из 2.8 к полной схеме

Настало время выполнить обещанное в главе 4.2: привести таблицу reviews из главы 2.8 (review_id, book_id, rating) к целевому DDL. Миграция собирается из уже разобранных форм ALTER TABLE — каждая группа команд ниже закрывает одно расхождение со целевой схемой:

-- 1) оценка: integer → smallint плюс проверка диапазона (CHECK из 4.2)
ALTER TABLE reviews ALTER COLUMN rating TYPE smallint;
ALTER TABLE reviews ADD CONSTRAINT reviews_rating_check
    CHECK (rating BETWEEN 1 AND 5);

-- 2) у отзыва появляются читатель, текст и время создания
ALTER TABLE reviews
    ADD COLUMN reader_id integer REFERENCES readers,
    ADD COLUMN comment text,
    ADD COLUMN created_at timestamptz NOT NULL DEFAULT now();
INSERT INTO readers (reader_id, email, display_name) VALUES
    (2, 'ivan@example.com', 'Иван'),
    (3, 'olga@example.com', 'Ольга');
UPDATE reviews SET reader_id = CASE review_id
    WHEN 1 THEN 2   -- Иван
    WHEN 2 THEN 3   -- Ольга
    WHEN 4 THEN 3
    WHEN 5 THEN 3
    WHEN 7 THEN 2
    WHEN 8 THEN 3
    ELSE 1          -- отзывы 3 и 6 — за Анной
END;
ALTER TABLE reviews ALTER COLUMN reader_id SET NOT NULL;

-- 3) ключ: integer → bigint, с identity-последовательностью
ALTER TABLE reviews ALTER COLUMN review_id TYPE bigint;
ALTER TABLE reviews ALTER COLUMN review_id
    ADD GENERATED BY DEFAULT AS IDENTITY;

Пояснения по группам. (1) Смена типа на живых данных потребует перезаписи таблицы (Notes выше), а новый CHECK пройдёт: восемь оценок из главы 2.8 — от 3 до 5. (2) reader_id добавлен без NOT NULL: сначала заполняем существующие строки и только потом запрещаем NULL. Почему не «все отзывы — Анне»: в главе 8.1 появится бизнес-правило «один читатель оценивает книгу один раз», поэтому восемь отзывов заранее раздаём трём читателям так, чтобы ни одна пара (reader_id, book_id) не повторилась (у книги 1 и 6 по два-три отзыва — их получают разные читатели); идентификаторы читателей заданы явно — первичный ключ readers без identity (глава 4.1), и мы держим нумерацию под контролем. created_at с волатильным DEFAULT now() проставил существующим строкам момент ALTER. (3) Формы ADD GENERATED ... AS IDENTITY для существующего столбца и RESTART WITH мы выполним после вставок ниже — когда станет виден следующий свободный номер. Заметьте: в целевом DDL у внешнего ключа на книги есть ON DELETE CASCADE; наш столбец book_id ссылается на книги из главы 2.8 без него. Добавить поведение в один шаг нельзя, зато можно пересоздать ограничение:

-- 4) FK на книги: добавить ON DELETE CASCADE (глава 4.2)
ALTER TABLE reviews
    DROP CONSTRAINT reviews_book_id_fkey,
    ADD CONSTRAINT reviews_book_id_fkey
        FOREIGN KEY (book_id) REFERENCES books ON DELETE CASCADE;

Теперь схема совпадает с целевым DDL главы 4.2 (кроме identity-настройки, до неё одна строка ниже).

VIEW: именованный запрос

Проблему «JOIN на три таблицы в каждом отчёте» решает представление: оно «даёт имя запросу, на который можно ссылаться как на обычную таблицу» (туториал 3.2, /docs/17/tutorial-views.html). Справочник CREATE VIEW фиксирует ключевое свойство дословно: «представление не материализуется физически. Вместо этого запрос выполняется каждый раз, когда представление используется в запросе».

CREATE VIEW book_reviews AS
SELECT r.review_id,
       b.title,
       a.name  AS author,
       r.rating,
       r.comment
FROM reviews r
JOIN books   b ON b.book_id = r.book_id
JOIN authors a ON a.author_id = b.author_id;

INSERT INTO reviews (review_id, book_id, reader_id, rating, comment)
VALUES (9, 1, 1, 5, 'Перечитываю каждый год'),
       (10, 4, 2, 4, 'Эпично');

SELECT review_id, title, author, rating, comment
FROM book_reviews
WHERE review_id >= 9
ORDER BY review_id;
 review_id |      title       | author  | rating |       comment
-----------+------------------+---------+--------+---------------------
         9 | Евгений Онегин   | Пушкин  |      5 | Перечитываю каждый год
        10 | Война и мир      | Толстой |      4 | Эпично
(2 rows)

Что выведено и почему: представление собрало данные трёх таблиц по правилам JOIN из главы 2.3; строки 9–10 — новые отзывы читателей 1 (Анна) и 2 (Иван) — идентификаторы продолжают нумерацию восьми отзывов из главы 2.8; book_id 1 — «Евгений Онегин» Пушкина, book_id 4 — «Война и мир» Толстого (идентификаторы соответствуют данным из главы 2.1). Никакая отдельная таблица не хранилась: SELECT из book_reviews развернулся в JOIN по базовым таблицам. Осталась последняя строка моста — настроить identity-последовательность из пункта 3 на следующий свободный номер:

ALTER TABLE reviews ALTER COLUMN review_id RESTART WITH 11;
ALTER TABLE

Явные вставки 9–10 последовательность не двигали — так работает GENERATED BY DEFAULT (глава 4.6): номер выдается только когда столбец не указан явно. Теперь столбец готов выдавать номера автоматически — это пригодится в главе 10.2.

Как это работает внутри: переписывание запроса

Механизм — не «магический executor», а переписывание дерева запроса. В конвейере сервера между разбором SQL и планированием есть стадия перезаписи; её точка входа — функция QueryRewrite в файле src/backend/rewrite/rewriteHandler.c#L4556 на базовом коммите: «Primary entry point to the query rewriter. Rewrite one query via query rewrite system, possibly returning 0 or many queries» (комментарий в исходнике). Ссылку на представление система находит в каталоге (по строке в pg_class, где представление — объект с собственным OID, гл. 51.11), подставляет вместо неё сохранённый при CREATE VIEW запрос и уже потом передаёт результат планировщику. Поэтому представление «вычисляется в момент обращения»: каждая выборка из него — свежий JOIN. Подробный разбор пути запроса — глава 9.1.

MATERIALIZED VIEW: сохранённый результат

Если JOIN тяжёлый, а свежесть данных не критична, результат можно сохранить: «CREATE MATERIALIZED VIEW определяет материализованное представление запроса. Запрос выполняется и используется для наполнения представления в момент выпуска команды (если не используется WITH NO DATA) и может быть обновлён позже командой REFRESH MATERIALIZED VIEW» (/docs/17/sql-creatematerializedview.html). Статистика по книгам — типичный кандидат:

CREATE MATERIALIZED VIEW book_stats AS
SELECT b.title,
       count(*)      AS review_cnt,
       avg(r.rating) AS avg_rating
FROM books b
JOIN reviews r ON r.book_id = b.book_id
GROUP BY b.title;

REFRESH MATERIALIZED VIEW book_stats;

Что произойдёт и почему: при CREATE данные агрегируются один раз и хранятся в собственном отношении (у MV «многие те же свойства, что у таблицы», там же); между CREATE и REFRESH содержимое не меняется само — «запрос... может быть обновлён позже». Цена такого кэша — устаревание: отзыв, добавленный после REFRESH, в book_stats попадёт только после следующего REFRESH. Выбор между VIEW и MATERIALIZED VIEW — это выбор между свежестью и скоростью чтения.

Про имена: у представлений те же правила идентификаторов, что у таблиц (глава 4.1); представление занимает имя в схеме наравне с таблицами — «имя представления должно отличаться от имён всех прочих отношений (таблиц, последовательностей, индексов, представлений, материализованных представлений или сторонних таблиц) в той же схеме» (CREATE VIEW).

Проверь себя

Вопрос 1. Почему ALTER TABLE reviews ADD COLUMN source text NOT NULL DEFAULT 'web' выполняется мгновенно на таблице в миллиард строк, а то же самое с DEFAULT now() — долго?

Ответ. Неволатильный DEFAULT вычисляется один раз «в момент выполнения оператора», а результат «сохраняется в метаданных таблицы» — «переписывание таблицы не требуется» (Notes, ALTER TABLE). Волатильный DEFAULT (например now()) требует своего значения для каждой строки: «добавление столбца с волатильным DEFAULT... потребует переписать всю таблицу и её индексы».

Вопрос 2. Чем работа представления отличается от материализованного представления, и где в конвейере сервера «появляется» представление при SELECT из него?

Ответ. VIEW: «не материализуется физически... запрос выполняется каждый раз, когда представление используется» (CREATE VIEW); MATERIALIZED VIEW: «запрос выполняется и используется для наполнения представления в момент выпуска команды... и может быть обновлён позже» (CREATE MATERIALIZED VIEW). Ссылку на представление переписывает query rewriter — точка входа QueryRewrite в src/backend/rewrite/rewriteHandler.c#L4556 на базовом коммите; это происходит до планирования.

Вопрос 3. Что произойдёт с индексами и ограничениями при ALTER TABLE books DROP COLUMN base_rating, и как добавить CHECK-ограничение, не блокируя таблицу надолго?

Ответ. «Индексы и табличные ограничения, включающие этот столбец, будут удалены автоматически» (ALTER TABLE, DROP COLUMN). Для CHECK — форма ADD CONSTRAINT ... NOT VALID: «обычно эта форма вызывает сканирование таблицы... но если указана опция NOT VALID, этот потенциально долгий скан пропускается»; проверка старых строк откладывается до VALIDATE CONSTRAINT.
