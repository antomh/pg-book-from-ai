Глава 3.6. Приведение и разрешение типов

Уровень: J · узел карты тем: T17 · PostgreSQL 17.11

Почему одно сравнение молчит, а другое падает

Два запроса, которые пишут новички:

SELECT '123' = 123;
SELECT 'abc'::varchar = 42;

Первый вернёт t, второй — ошибку «operator does not exist: character varying = integer». Снаружи выглядит непоследовательно: строку с числом сравнить можно, varchar с числом — нельзя. На самом деле оба результата следуют из одного алгоритма — правил разрешения типов, которые PostgreSQL применяет к каждому выражению. Эта глава разбирает алгоритм: как читаются CAST и ::, что такое «неизвестный» тип литерала, как сервер выбирает перегруженный оператор и почему он отказывается угадывать там, где результат был бы неожиданным.

Явное приведение: CAST и ::

Раздел 4.2.9 Type Casts (/docs/17/sql-expressions.html): «приведение типа задаёт преобразование из одного типа данных в другой. PostgreSQL принимает два эквивалентных синтаксиса:

CAST ( expression AS type )
expression::type

Синтаксис CAST соответствует SQL; синтаксис с :: — историческое употребление PostgreSQL». Уточнение оттуда же: «когда приведение применяется к выражению значения известного типа, оно обозначает преобразование во время выполнения. Приведение успешно, только если определена подходящая операция преобразования. Обратите внимание: это тонко отличается от использования приведений с константами — приведение, применённое к простому строковому литералу, задаёт начальное присвоение типа литеральной константе и успешно для любого типа (если содержимое литерала — допустимый синтаксис ввода для этого типа)». То есть '123'::integer — не «конвертация строки в число», а чтение литерала сразу как числа; а вот price::integer, где price — колонка numeric, — настоящее преобразование значения.

Модель: строгая типизация и литералы «unknown»

«SQL — строго типизированный язык: каждый элемент данных имеет связанный тип, определяющий его поведение и допустимое использование» — так начинается глава 10 Type Conversion (/docs/17/typeconv-overview.html, 10.1). Дальше — ключевой механизм: «сканер/парсер PostgreSQL делит лексические элементы на пять фундаментальных категорий: целые, нецелые числа, строки, идентификаторы и ключевые слова. Константы большинства нечисловых типов сначала классифицируются как строки. Если тип для строкового литерала не указан, сначала назначается тип-заполнитель unknown, который разрешается на следующих стадиях».

Отсюда разница из начала главы. В '123' = 123 правый операнд — тип unknown, и правило разрешения операторов гласит дословно: «если один аргумент вызова бинарного оператора имеет тип unknown, для этой проверки предполагается, что он того же типа, что и другой аргумент» (10.2, /docs/17/typeconv-oper.html). Находится оператор integer = integer — сравнение чисел, результат t.

А в 'abc'::varchar = 42 левый операнд уже типизирован (character varying), правый — integer: оператора varchar = integer в системе нет, и неявного приведения между строковой и числовой категориями тоже нет — сервер отказывается угадывать. Сообщение об ошибке рождается в src/backend/parser/parse_oper.c, строки 637–642 на базовом коммите: errmsg("operator does not exist: %s") и подсказка «No operator matches the given name and argument types. You might need to add explicit type casts.»:

ERROR:  operator does not exist: character varying = integer
HINT:  No operator matches the given name and argument types. You might need to add explicit type casts.

Лечение — явное приведение любой стороны: book_id::varchar = '42' (сравнение строк) или '42'::integer = book_id (сравнение чисел).

Как выбирается оператор: шаги алгоритма

Документация (10.2) описывает процедуру для выражения с оператором — сокращённо, без деталей поиска по схеме:

  1. Из каталога pg_operator отбираются операторы с совпадающими именем и числом аргументов, видимыми в текущем search path.
  2. Ищется оператор, принимающий точно типы аргументов; если один аргумент unknown — для этой проверки он считается типом второго аргумента.
  3. Отбрасываются кандидаты, к типам которых аргументы нельзя неявно преобразовать.
  4. Оставляются кандидаты с наибольшим числом точных совпадений типов; затем — те, что принимают предпочтительные (preferred) типы категории аргументов.
  5. Для аргументов типа unknown выбирается категория (со смещением к строковой — «неизвестный литерал выглядит как строка»); если останется несколько кандидатов — ошибка неоднозначности.

Про категории: «типы данных делятся на несколько базовых категорий, включая boolean, numeric, string, bitstring, datetime, timespan, geometric, network и пользовательские. В каждой категории может быть один или несколько предпочтительных типов (preferred types), которые предпочитаются при выборе из возможных типов» (10.1). Информация о существующих приведениях хранится в системных каталогах, а новые задаются командой CREATE CAST (там же; для встроенных типов набор приведений «тщательно подобран и его лучше не менять»).

Три примера из документации

Пример 1 (точное совпадение после unknown): SELECT 'abc' || 'def'; — «в этом случае нет первоначальной подсказки, какой тип использовать... парсер ищет всех кандидатов и находит, что есть кандидаты, принимающие вход категорий string и bit-string. Поскольку категория string предпочтительна, когда доступна, выбирается она, а затем предпочтительный тип строк text используется как конкретный тип для разрешения литералов unknown» — результат abcdef (пример 10.2 из 10.2 документации).

Пример 2 (preferred тип категории): SELECT |/ 40; — «в стандартном каталоге есть только один оператор квадратного корня (префиксный |/), и он принимает аргумент типа double precision. Сканер назначает аргументу начальный тип integer. Поэтому парсер выполняет преобразование типа операнда, и запрос эквивалентен |/ CAST(40 AS double precision)» — вывод 6.324555320336759 (пример 10.1).

Пример 2.5 (известные типы, но не строковые): SELECT 2 || 3; — оба аргумента теперь типизированы (integer), литералов unknown нет, и шаг 2 алгоритма ищет оператор || для integer, integer: такого в pg_operator нет. Неявного приведения из числовой категории в строковую тоже нет (в pg_cast такое приведение отсутствует, и шаг 3 никого не оставляет), поэтому результат:

ERROR:  operator does not exist: integer || integer
LINE 1: SELECT 2 || 3;
               ^
HINT:  No operator matches the given name and argument types. You might need to add explicit type casts.

Почему сервер не «помог» превратить двойку в строку: правила неявных преобразований «тщательно подобраны» и превращение числа в текст молча — именно «удивительный результат», которого 10.1 избегает; выражение исправляется явным приведением 2::text || 3::text → 23. Это зеркальный случай к '123' = 123 из вводки: там unknown-литерал подстроился под число, а здесь известные числа не подстраиваются под строки.

Пример 3 (preferred тип проявляется в ошибке): SELECT @ '-4.5e500'; — оператор модуля @ для unknown-литерала выбирает предпочтительный тип числовой категории float8, а литерал не помещается в него: ERROR: "-4.5e500" is out of range for type double precision (пример 10.3). Так проявляется принцип из 10.1: «неявные преобразования не должны иметь удивительных или непредсказуемых результатов» — сервер скорее честно упадёт, чем молча сделает не то.

Приведение при записи в столбец

Отдельный контекст — присваивание: «операторы INSERT и UPDATE помещают результаты выражений в таблицу. Выражения должны быть согласованы с типами целевых столбцов и, возможно, преобразованы к ним» (10.1, четвёртая «фундаментальная конструкция» — value storage; правила — раздел 10.4 Value Storage). Поэтому вставка литерала в типизированный столбец работает без явных :::

INSERT INTO editions (edition_id, book_id, format, price)
VALUES (7, 2, 'pdf', 350);

Что произойдёт и почему: литерал 350 имеет начальный тип unknown и приведётся к типу столбца numeric(6,2) в контексте присваивания; в таблице окажется 350.00. То же правило разрешает и VALUES (7, 2, 'pdf', '350') — строковый литерал разобран как numeric. Но VALUES (7, 2, 'pdf', 'abc') — ошибка ввода: содержимое литерала не является допустимым синтаксисом numeric (правило «успешно для любого типа (если содержимое литерала — допустимый синтаксис ввода)», 4.2.9).

Проверь себя

Вопрос 1. Почему SELECT '123' = 123; работает, а SELECT '123'::varchar = 123; — нет?

Ответ. В первом случае '123' — литерал типа unknown: «если один аргумент вызова бинарного оператора имеет тип unknown, для этой проверки предполагается, что он того же типа, что и другой аргумент» (10.2) — находится integer = integer. Во втором тип уже известен (varchar), оператора varchar = integer нет, неявного приведения между строковой и числовой категориями нет — ошибка «operator does not exist» (текст — parse_oper.c#L637–642 на базовом коммите). Исправление — явный CAST: '123'::integer = 123.

Вопрос 2. Что вернёт SELECT 'abc' || 'def'; и по каким шагам сервер пришёл к этому типу?

Ответ. abcdef типа text. Оба литерала — unknown; точного совпадения нет; среди кандидатов есть принимающие категорию string и bit-string; «поскольку категория string предпочтительна, когда доступна, выбирается она, и затем предпочтительный тип строк text используется как конкретный тип для разрешения литералов unknown» (пример 10.2 из 10.2 документации).

Вопрос 3. Чем '350'::numeric как приведение литерала отличается от price::integer для колонки price типа numeric? Почему первое «срабатывает всегда», а второе — нет?

Ответ. «Приведение, применённое к простому строковому литералу, задаёт начальное присвоение типа литеральной константе и успешно для любого типа (если содержимое литерала — допустимый синтаксис ввода для этого типа)». А приведение значения известного типа — «преобразование во время выполнения... успешно, только если определена подходящая операция преобразования» (4.2.9). numeric → integer операция определена (с округлением), а вот, например, record → integer — нет.
