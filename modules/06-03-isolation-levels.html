Глава 6.3. Уровни изоляции и аномалии

Уровень: J · узел карты тем: T29 · PostgreSQL 17.11

Одна транзакция, два SELECT — разные рейтинги

Приложение в одной транзакции дважды читает рейтинг отзыва: сначала для расчёта, потом для отчёта. Между чтениями модератор успел исправить оценку — и отчёт не сходится с расчётом. Это не баг кода: это разрешённое на уровне Read Committed поведение, «неповторяемое чтение». Теория БД каталогизирует такие эффекты как аномалии конкурентности и предлагает уровни изоляции — компромисс «строже изоляция ↔ меньше параллельности». В Silberschatz им посвящены § 17.5 (Transaction Isolation) и § 17.8 (Transaction Isolation Levels); PostgreSQL реализует стандартные уровни поверх версионности строк (глава 6.4).

Четыре феномена

«Стандарт SQL определяет четыре уровня изоляции транзакций», а младшие три описаны через феномены («phenomena») — эффекты взаимодействия конкурентных транзакций, которые на данном уровне не должны происходить. Определения дословно из (/docs/17/transaction-iso.html, 13.2):

  • грязное чтение (dirty read) — «транзакция читает данные, записанные конкурентной незафиксированной транзакцией»;
  • неповторяемое чтение (nonrepeatable read) — «транзакция перечитывает данные, которые читала ранее, и обнаруживает, что они были изменены другой транзакцией (зафиксированной после первого чтения)»;
  • фантомное чтение (phantom read) — «транзакция повторно выполняет запрос, возвращающий набор строк, удовлетворяющих условию поиска, и обнаруживает, что набор строк изменился из-за недавно зафиксированной другой транзакции»;
  • аномалия сериализации (serialization anomaly) — «результат успешной фиксации группы транзакций несовместим ни с одним из возможных порядков последовательного выполнения этих транзакций по одной».

Ключевые факты оттуда же: «в PostgreSQL можно запросить любой из четырёх стандартных уровней изоляции, но внутренне реализованы только три различных уровня, то есть режим Read Uncommitted ведёт себя как Read Committed. Это единственный разумный способ отобразить стандартные уровни на архитектуру многоверсионного управления конкурентностью PostgreSQL». И специфика реализации: «реализация Repeatable Read в PostgreSQL не допускает фантомного чтения. Это допустимо по стандарту SQL, поскольку стандарт указывает, какие аномалии не должны возникать на определённых уровнях; более сильные гарантии допустимы». Заметьте и кнопку сброса стереотипов «уровень по умолчанию — не часть стандарта»: «Read Committed — уровень изоляции по умолчанию в PostgreSQL» — это соглашение реализации, задаваемое параметром default_transaction_isolation (см. справочник SET TRANSACTION).

Read Committed: снимок на каждый оператор

Постановка опыта — одна строка для чистоты эксперимента (вставим свежий отзыв читателя 1 на «Войну и мир»):

INSERT INTO reviews (review_id, reader_id, book_id, rating, comment)
VALUES (15, 1, 4, 3, 'тяжело, но красиво');

Сессия A (читатель отчёта) идёт на уровне по умолчанию:

-- сессия A
BEGIN;
SELECT rating FROM reviews WHERE review_id = 15;
 rating
--------
      3
(1 row)

Пока A держит транзакцию открытой, модератор в сессии B исправляет оценку и фиксирует:

-- сессия B
UPDATE reviews SET rating = 5 WHERE review_id = 15;
UPDATE 1

Сессия A перечитывает ту же строку в той же транзакции:

-- сессия A, та же транзакция
SELECT rating FROM reviews WHERE review_id = 15;
COMMIT;
 rating
--------
      5
(1 row)

COMMIT

Что выведено и почему: это неповторяемое чтение в чистом виде. Правило Read Committed: «когда транзакция использует этот уровень изоляции, запрос SELECT... видит только данные, зафиксированные до начала запроса; он никогда не видит ни незафиксированных данных, ни изменений, зафиксированных конкурентными транзакциями во время выполнения запроса. По сути, запрос SELECT видит снимок базы данных на момент начала выполнения запроса» (13.2.1). И сразу разграничение, объясняющее опыт: «однако SELECT видит эффекты предыдущих обновлений, выполненных внутри его собственной транзакции... обратите внимание, что два последовательных SELECT могут видеть разные данные, даже находясь в одной транзакции, если другие транзакции фиксируют изменения после начала первого SELECT и до начала второго» (13.2.1, перевод дословный).

Потерянное обновление: чтение ради записи

Самая прикладная аномалия конкурентности — потерянное обновление (lost update): две транзакции читают одно значение, обе вычисляют новое на его основе и записывают — и изменение, зафиксированное первой, молча затирается второй. Стандарт SQL не включает её в список феноменов выше (13.2 перечисляет четыре), но именно она ломает счётчики, балансы и остатки. Два сценария — обе сессии на уровне по умолчанию (Read Committed), строка — отзыв 15 с рейтингом 3.

Безопасный сценарий — вычислять новое значение внутри самого UPDATE. Сессии A и B почти одновременно выполняют:

UPDATE reviews SET rating = rating + 1 WHERE review_id = 15;

Вторая транзакция ждёт первую: «ожидающий обновления оператор будет ждать, пока первая транзакция-обновитель не зафиксируется или не откатится» (13.2.1), а затем применяет своё присваивание уже поверх свежего значения — оба приращения сохраняются. Опасный сценарий — «прочитал, посчитал в приложении, записал константу»:

-- сессия A (и точно так же сессия B, почти одновременно)
SELECT rating FROM reviews WHERE review_id = 15;    -- обе прочитали 3
UPDATE reviews SET rating = 4 WHERE review_id = 15; -- обе записали 4

Что произойдёт и почему: обе сессии прочитали 3, обе записали 4 — один из двух инкрементов потерян, и ни одна транзакция не получила ошибку: обычный SELECT ничего не блокирует (глава 6.4). Защита — любая из уже знакомых идей: считать внутри UPDATE (первый сценарий); на Repeatable Read PostgreSQL поймает перезапись ошибкой сериализации — «при попытке обновить ту же строку... транзакция будет отменена с ERROR: could not serialize access due to concurrent update» (13.2.2, тот же текст верен для Serializable — глава 6.5); наконец, «прочитать — изменить» можно защитить явной блокировкой SELECT ... FOR UPDATE из главы 6.6: вторая сессия подождёт фиксации первой и прочитает уже новое значение. Правило для прикладного кода: новое значение вычисляется внутри UPDATE, а не «снаружи» между двумя операторами.

Repeatable Read: снимок на транзакцию

Тот же опыт с повышенным уровнем — «уровень изоляции Repeatable Read видит только данные, зафиксированные до начала транзакции; он никогда не видит ни незафиксированных данных, ни изменений, зафиксированных конкурентными транзакциями во время выполнения транзакции» (13.2.2). Отличие от Read Committed в границе снимка: «запрос в транзакции repeatable read видит снимок на момент начала первого оператора, не являющегося управлением транзакцией, а не на момент начала текущего оператора. Таким образом, последовательные SELECT внутри одной транзакции видят одни и те же данные» (13.2.2). Уровень задаётся командой начала блока: «BEGIN инициирует блок транзакции... Если указан уровень изоляции..., новая транзакция имеет эти характеристики, как если бы была выполнена SET TRANSACTION» (sql-begin):

-- сессия A
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT rating FROM reviews WHERE review_id = 15;   -- 3
-- ... сессия B: UPDATE reviews SET rating = 4 WHERE review_id = 15; COMMIT;
SELECT rating FROM reviews WHERE review_id = 15;   -- снова 3
COMMIT;

Что произойдёт и почему: оба SELECT вернут 3 — второе чтение игнорирует зафиксированное сессией B изменение, потому что снимок A сделан при первом операторе. Обратная сторона усиленной гарантии — конфликты записи: «приложения, использующие этот уровень, должны быть готовы повторять транзакции из-за ошибок сериализации» (13.2.2). Если бы A попыталась UPDATE reviews SET rating = 2 WHERE review_id = 15 после фиксации B, «repeatable read транзакция будет откачена с сообщением ERROR: could not serialize access due to concurrent update, поскольку транзакция repeatable read не может изменять или блокировать строки, изменённые другими транзакциями после её начала» (13.2.2, дословно) — и её придётся выполнить заново.

Что не отменяет никакой уровень

Важное исключение в 13.2 (Important): «изменения последовательности (а значит, и счётчика столбца, объявленного с serial) немедленно видны всем другим транзакциям и не откатываются при аварийном завершении транзакции, которая их сделала» — это в точности «дыры» из главы 4.6, теперь с формальным обоснованием. Ещё одна граница: изоляция защищает данные, но не схему и не последовательности; SELECT соседней сессии, начатый до COMMIT, не увидит новых строк вашего снимка, но любой оператор, начатый после фиксации, — увидит.

Проверь себя

Вопрос 1. Сессия A дважды читает рейтинг в одной транзакции (Read Committed), между чтениями B фиксирует UPDATE. Что увидит A и почему это «законно»?

Ответ. Второй SELECT увидит новое значение: в Read Committed «запрос SELECT видит снимок базы данных на момент начала выполнения запроса», поэтому «два последовательных SELECT могут видеть разные данные, даже находясь в одной транзакции» (13.2.1). Это неповторяемое чтение — на данном уровне оно допустимо (таблица 13.1).

Вопрос 2. Чем снимок Repeatable Read отличается от снимка Read Committed, и какую цену платит приложение за это отличие?

Ответ. RC: снимок «на момент начала выполнения запроса»; RR: снимок «на момент начала первого оператора, не являющегося управлением транзакцией» (13.2.2) — все SELECT одной транзакции видят одни данные. Цена: «приложения, использующие этот уровень, должны быть готовы повторять транзакции из-за ошибок сериализации», при конкурентном UPDATE — ERROR: could not serialize access due to concurrent update (13.2.2).

Вопрос 3. Почему в PostgreSQL нет ни грязного чтения, ни фантомов на Repeatable Read, хотя стандарт их разрешает?

Ответ. Грязное чтение невозможно на всех уровнях, поскольку архитектура MVCC не показывает незафиксированные версии другим транзакциям (глава 6.4). «Реализация Repeatable Read в PostgreSQL не допускает фантомного чтения. Это допустимо по стандарту SQL... стандарт указывает, какие аномалии не должны возникать на определённых уровнях; более сильные гарантии допустимы» (13.2); Read Uncommitted в PG «ведёт себя как Read Committed» по той же причине.
