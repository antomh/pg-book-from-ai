Глава 8.1. B-tree: устройство и применение

Уровень: J · узел карты тем: T37 · PostgreSQL 17.11

Таблица выросла — и каждый поиск читает её целиком

Дневник чтения набирает читателей, и страница «отзывы о книге № 13» открывается всё дольше. Причина знакома по главе 7.2: без указаний серверу остаётся «прочитать таблицу страницу за страницей» — последовательное сканирование, Seq Scan. Документация сравнивает это с книгой без предметного указателя: «термины и понятия, которые часто ищут читатели, собираются в алфавитный указатель в конце книги. Заинтересованный читатель может быстро просмотреть указатель и перейти к нужным страницам, вместо того чтобы читать всю книгу» — и продолжает: «как автор задачи должен предугадать, что читатели будут искать, так и задача программиста баз данных — предвидеть, какие индексы будут полезны» (11.1, /docs/17/indexes-intro.html, перевод дословный). Что такое индекс: «индекс позволяет серверу базы данных находить и извлекать конкретные строки гораздо быстрее, чем без индекса. Но индексы также добавляют накладные расходы к системе базы данных в целом, поэтому их следует использовать разумно» (гл. 11, введение). Проверим оба обещания — и скорость, и цену.

Создание и использование

CREATE INDEX reviews_book_id_idx ON reviews (book_id);

EXPLAIN SELECT * FROM reviews WHERE book_id = 13;
CREATE INDEX
                        QUERY PLAN
----------------------------------------------------------
 Seq Scan on reviews  (cost=0.00..1.13 rows=2 width=84)
   Filter: (book_id = 13)
(2 rows)

Что выведено и почему: индекс создан, но план не изменился. EXPLAIN «отображает план выполнения, который планировщик PostgreSQL генерирует для переданного оператора. План показывает, как таблицы будут сканироваться — обычным последовательным сканированием, индексным сканированием и т.д.» (/docs/17/sql-explain.html, перевод дословный; числа cost у вас будут другими — они зависят от статистики таблицы). Причина Seq Scan не в ошибке: «система... будет использовать индекс в запросах, когда считает, что это будет эффективнее, чем последовательное сканирование таблицы» (11.1). У нас 11 строк (девять отзывов плюс два из опытов изоляции — главы 6.3 и 6.4) — «вероятно, одна страница диска», а «не существует плана, который мог бы победить последовательное чтение одной страницы диска» (11.12 /docs/17/indexes-examine.html). На боевой таблице в миллионы строк тот же запрос даёт:

                              QUERY PLAN
----------------------------------------------------------------------
 Index Scan using reviews_book_id_idx on reviews
   (cost=0.42..8.44 rows=3 width=84)
   Index Cond: (book_id = 13)
(2 rows)

«Index Scan using ...» — планировщик выбрал наш индекс, а строка «Index Cond: (book_id = 13)» показывает условие, по которому индекс ищет записи. Важное обещание из 11.1: «когда индекс создан, никакого дальнейшего вмешательства не требуется: система будет обновлять индекс при изменении таблицы» — индекс не нужно перестраивать после INSERT, UPDATE или DELETE. Плата: «после создания индекса система должна поддерживать его синхронным с таблицей. Это добавляет накладные расходы к операциям изменения данных. Поэтому индексы, которые редко или никогда не используются в запросах, следует удалять» (11.1, дословно). Каждая вставка отзыва теперь пишет и в таблицу, и в каждый индекс по ней.

Какие запросы ускоряет B-tree

По умолчанию CREATE INDEX создаёт B-tree: «команда CREATE INDEX создаёт B-tree индексы, которые подходят для большинства типичных ситуаций» (11.2 /docs/17/indexes-types.html). Применимость: «B-деревья могут обрабатывать запросы равенства и диапазона для данных, которые можно отсортировать в некотором порядке. В частности, планировщик запросов PostgreSQL рассмотрит использование B-tree индекса всякий раз, когда индексированный столбец участвует в сравнении с одним из операторов: < <= = >= >. Конструкции, эквивалентные комбинациям этих операторов, такие как BETWEEN и IN, также могут быть реализованы поиском по B-tree индексу. Также условие IS NULL или IS NOT NULL на индексированном столбце может использоваться с B-tree индексом» (11.2.1, дословно). Ещё: «оптимизатор может использовать B-tree индекс для запросов с операторами сопоставления с образцом LIKE и ~ , если образец — константа и привязан к началу строки — например, col LIKE 'foo%' или col ~ '^foo' , но не col LIKE '%bar'» (11.2.1). Подводный камень для кириллицы: «если ваша база данных не использует локаль C, вам потребуется создать индекс со специальным классом операторов для поддержки индексации запросов сопоставления с образцом» (11.2.1) — это классы text_pattern_ops/varchar_pattern_ops, «значения сравниваются строго символ за символом, а не по правилам сортировки локали» (11.10 /docs/17/indexes-opclass.html). И последнее из 11.2.1: «B-tree индексы также могут использоваться для получения данных в отсортированном порядке» — индекс по created_at избавляет сортировку ORDER BY (подробнее — глава 8.2).

Уникальные индексы

Индексы работают и как ограничение: «индексы могут также использоваться для принудительного обеспечения уникальности значения столбца или уникальности комбинации значений нескольких столбцов... Когда индекс объявлен уникальным, несколько строк таблицы с равными индексированными значениями не допускаются» (11.6 /docs/17/indexes-unique.html, дословно). Бизнес-правило дневника: один читатель оценивает книгу один раз:

CREATE UNIQUE INDEX reviews_one_review_idx
    ON reviews (reader_id, book_id);

INSERT INTO reviews (review_id, reader_id, book_id, rating, comment)
VALUES (17, 1, 3, 5, 'Гоголь — гений');
CREATE INDEX
INSERT 0 1

Первая вставка прошла: пара (1, 3) — читатель 1 ещё не оценивал «Мёртвые души». Повторим оценку — номер другой, но пара та же:

INSERT INTO reviews (review_id, reader_id, book_id, rating, comment)
VALUES (18, 1, 3, 4, 'дубль');
ERROR:  duplicate key value violates unique constraint "reviews_one_review_idx"
DETAIL:  Key (reader_id, book_id)=(1, 3) already exists.

Что выведено и почему: пара (1, 3) уже есть — отзыв review_id 17, вставленный двумя командами выше. Формулировку ошибки вы уже разбирали в главе 6.2: её выдаёт проверка уникальности B-tree при вставке — _bt_check_unique в src/backend/access/nbtree/nbtinsert.c на коммите 083ac033419f690758508e08c1736089384bbee8 (функция со строки 408; errmsg — строка 668, errdetail("Key %s already exists.") — строка 670). Кстати, обойти ошибку можно знакомым по 5.1 ON CONFLICT — он работает именно с уникальными индексами. Связь с ограничениями из 4.2: «PostgreSQL автоматически создаёт уникальный индекс, когда для таблицы определяется ограничение уникальности или первичный ключ. Индекс покрывает столбцы, составляющие первичный ключ или ограничение уникальности, и является механизмом, обеспечивающим соблюдение ограничения» (11.6). Поэтому «нет необходимости вручную создавать индексы на уникальных столбцах; это лишь продублировало бы автоматически созданный индекс» (11.6). Внешние ключи, в отличие от PK, индекс автоматически не получают — индекс для reviews (book_id) из примера выше ускоряет и JOIN по нему: «индекс, определённый на столбце, который является частью условия соединения, также может значительно ускорить запросы с соединениями» (11.1).

Как устроено дерево

B-tree — не бинарное дерево из учебника алгоритмов, а «многоуровневая древовидная структура, где каждый уровень дерева может использоваться как двусвязный список страниц» (64.1.4.1 /docs/17/btree.html, перевод дословный). Страницы — те же 8-килобайтные страницы из главы 7.2: «как внутренние, так и листовые страницы используют стандартный формат страницы» (64.1.4.1). Устройство уровней (64.1.4.1, дословно): «единственная метастраница хранится в фиксированной позиции в начале первого сегментного файла индекса. Все остальные страницы являются либо листовыми, либо внутренними. Листовые страницы — это страницы на самом нижнем уровне дерева... Каждая листовая страница содержит кортежи, указывающие на строки таблицы. Каждая внутренняя страница содержит кортежи, указывающие на следующий уровень вниз по дереву. Обычно более 99% всех страниц — листовые». Кортежи листа — это структура IndexTupleData: первое поле t_tid — «ссылка TID на heap-кортеж» (src/include/access/itup.h, строки 35–37 на базовом коммите), то есть тот самый ctid «(страница, элемент)» из главы 7.2. Рядом с t_tid лежит ключ — значение book_id, отсортированное по порядку сравнения столбца. Поиск по дереву — функция _bt_search в src/backend/access/nbtree/nbtsearch.c (строка 96): цикл «выполняется один раз на каждый уровень спуска по дереву» (комментарий на строке 113); на каждом уровне бинарный поиск _bt_binsrch (строка 337) выбирает кортеж- разделитель, чей «downlink указывает на дочернюю страницу, на которую мы вот-вот спустимся» (комментарий на строках 146–147). Итог: глубина дерева логарифмична по числу записей — миллионы строк при сотнях записей на страницу дают высоту 3–4.

Рост дерева: «новые листовые страницы добавляются в B-tree индекс, когда существующая листовая страница не может вместить входящий кортеж. Операция разбиения страницы освобождает место для элементов... перемещая часть элементов на новую страницу. Разбиения страниц "каскадируются вверх" рекурсивно. Когда корневая страница наконец не может вместить новый downlink, происходит разбиение корневой страницы... добавляя новый уровень к структуре дерева» (64.1.4.1, дословно). Поэтому B-tree — «сбалансированное» дерево: все листы на одной глубине. Для конкурентного доступа реализация следует алгоритму Лемана–Яо: README модуля nbtree объясняет, что по сравнению с классическим B-деревом L&Y «добавляет указатель right-link к каждой странице — на правого соседа. Также добавляет "high key" к каждой странице — верхнюю границу ключей, которым разрешено находиться на этой странице. Эти два дополнения делают возможным обнаружить конкурентное разбиение страницы, что позволяет искать в дереве, не удерживая read-блокировки» (src/backend/access/nbtree/README на базовом коммите, перевод дословный). Ограничение на размер одной записи: «элемент индекса не может превышать примерно одну треть страницы (после TOAST-сжатия, если применимо)» (64.1.1) — очень длинные ключи B-tree не любит.

Связь с теорией

B+-дерево — классика учебников: Silberschatz (7-е изд., гл. 14 Indexing) разбирает упорядоченные индексы и B+-дерево (§ 14.1–14.3): внутренние узлы хранят только ключи- указатели, данные — в листьях, связанных в список; именно эту схему вы узнали выше в описании уровней PostgreSQL. Курс CMU 15-445 посвящает B+-деревьям лекции #08–09 (Tree Indexes). Отличие PostgreSQL от «учебникового» B+-дерева — высококонкурентный вариант Лемана–Яо с right-link и high key (см. README модуля nbtree) и хранение в листовых кортежах не самих строк, а TID-ссылок на версии строк heap (глава 6.4): MVCC порождает несколько индексных записей на логическую строку.

Проверь себя

Вопрос 1. Вы создали индекс, но EXPLAIN по-прежнему показывает Seq Scan. Индекс сломан?

Ответ. Нет: «система будет использовать индекс в запросах, когда считает, что это будет эффективнее, чем последовательное сканирование таблицы» (11.1). На маленькой таблице «не существует плана, который мог бы победить последовательное чтение одной страницы диска» (11.12) — Seq Scan и есть оптимальный план. Плюс проверьте, что по таблице запускался ANALYZE: без статистики планировщик «предполагает некоторые значения по умолчанию, которые почти наверняка неточны» (11.12).

Вопрос 2. Какие из этих условий могут использовать B-tree-индекс по столбцу title: title = 'Мёртвые души', title LIKE '%душ%', title LIKE 'Мёрт%', rating <> 5?

Ответ. Равенство — да: B-tree «обрабатывает запросы равенства и диапазона» по операторам =, <, <=, >=, > (11.2.1). LIKE 'Мёрт%' — да, «образец... привязан к началу строки» (11.2.1; для не-C локалей нужен text_pattern_ops, 11.10). LIKE '%душ%' — нет: образец не привязан к началу. <> — нет: почти никогда не полезен для поиска по индексу (64.1.2: «было бы почти никогда не полезно использовать <> в поиске по индексу»).

Вопрос 3. Почему CREATE UNIQUE INDEX ON reviews (reader_id, book_id) гарантирует «один отзыв на книгу от читателя», и что происходит при попытке вставить вторую пару (2, 1)?

Ответ. «Когда индекс объявлен уникальным, несколько строк таблицы с равными индексированными значениями не допускаются» (11.6) — при вставке B-tree находит место для нового ключа, обнаруживает равный и отвергает вставку (_bt_check_unique, nbtinsert.c, строки 408/668/670). Команда завершается ошибкой duplicate key value violates unique constraint с DETAIL про уже существующий ключ (глава 6.2). Альтернатива — ON CONFLICT из главы 5.1.
