Глава 10.3. Триггеры: реакция на изменения

Уровень: J+ · узел карты тем: T48 · PostgreSQL 17.11

Кто понизил рейтинг?

Рейтинг книги в читательском дневнике изменился с 5 на 1. Подозреваемый — приложение, но приложение обновлялось трижды за неделю, а заходили в базу ещё и через psql, и через скрипт миграции. Лог изменений в приложении не спасает: он пишет только то, что видит само приложение. Нужна запись в самой базе данных — автоматическая, при любом UPDATE. Для этого в SQL есть триггеры.

Что такое триггер

Определение из 37.1 Overview of Trigger Behavior (/docs/17/trigger-definition.html, перевод дословный): «триггер — это спецификация, что база данных должна автоматически выполнять определённую функцию всякий раз, когда выполняется определённый тип операции. Триггеры могут быть прикреплены к таблицам..., представлениям и сторонним таблицам. На таблицах триггеры могут быть определены для выполнения до или после любой операции INSERT, UPDATE или DELETE, либо один раз на каждую изменённую строку, либо один раз на SQL-оператор». Классификация оттуда же: триггеры «классифицируются в зависимости от того, срабатывают ли они до, после или вместо операции» — BEFORE, AFTER и INSTEAD OF (последние — только для представлений, глава 4.4); «строчные BEFORE-триггеры срабатывают непосредственно перед обработкой конкретной строки, тогда как строчные AFTER-триггеры срабатывают в конце оператора (но до строчных... то есть до statement-level AFTER-триггеров)». Важная деталь про пустые операторы: «оператор, затрагивающий ноль строк, всё равно приведёт к выполнению применимых триггеров уровня оператора». И правило порядка: «если для одного события на одном отношении определено более одного триггера, триггеры будут срабатывать в алфавитном порядке по имени».

Пометка: триггеры есть и в стандарте SQL (Silberschatz, § 5.3), но конкретный синтаксис CREATE TRIGGER — диалект PostgreSQL.

Аудит изменения рейтинга

Сначала таблица журнала (GENERATED IDENTITY — глава 4.6, timestamptz — глава 3.2):

CREATE TABLE review_rating_log (
    log_id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    review_id   int NOT NULL REFERENCES reviews(review_id),
    old_rating  smallint,
    new_rating  smallint,
    changed_at  timestamptz NOT NULL DEFAULT now()
);

Дальше — особенность PostgreSQL, отличающая его от учебников: «триггерная функция должна быть определена до того, как сам триггер может быть создан. Триггерная функция должна быть объявлена как функция без аргументов, возвращающая тип trigger» (37.1). То есть нужны два объекта: функция (что делать) и триггер (когда и на какой таблице). Функция пишется на PL/pgSQL из главы 10.2 и получает строки NEW и OLD:

CREATE FUNCTION log_rating_change()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO review_rating_log (review_id, old_rating, new_rating)
    VALUES (NEW.review_id, OLD.rating, NEW.rating);
    RETURN NEW;
END;
$$;

CREATE TRIGGER reviews_rating_audit
AFTER UPDATE ON reviews
FOR EACH ROW
WHEN (OLD.rating IS DISTINCT FROM NEW.rating)
EXECUTE FUNCTION log_rating_change();

Разбор. AFTER UPDATE ... FOR EACH ROW — функция сработает после каждой изменённой строки UPDATE. WHEN (OLD.rating IS DISTINCT FROM NEW.rating) — фильтр срабатывания: «определение триггера может также задать булево условие WHEN, которое будет проверяться, чтобы определить, должен ли триггер сработать. В строчных триггерах условие WHEN может исследовать старые и/или новые значения колонок строки» (37.1); предикат IS DISTINCT FROM взят из главы 2.1 — он честно сравнивает и NULL. RETURN NEW; для AFTER-триггера формальность: «возвращаемое значение игнорируется для строчных триггеров, срабатывающих после операции, так что они могут возвращать NULL» (37.1) — но вернуть строку безопасно и в BEFORE. Проверяем:

UPDATE reviews SET rating = 1 WHERE review_id = 3;
SELECT log_id, review_id, old_rating, new_rating, changed_at
FROM review_rating_log;

UPDATE reviews SET rating = 1 WHERE review_id = 3;
SELECT count(*) FROM review_rating_log;
UPDATE 1
 log_id | review_id | old_rating | new_rating |          changed_at
--------+-----------+------------+------------+------------------------------
      1 |         3 |          4 |          1 | 2025-12-30 12:04:11.30973+03
(1 row)

UPDATE 1
 count
-------
     1
(1 row)

Что выведено и почему (время будет вашим): первый UPDATE изменил рейтинг отзыва 3 с 4 на 1 (4 — оценка этой книги из главы 2.8, отзыв нигде не менялся) — сработало условие WHEN, в журнал попала строка со старым и новым значением. Второй UPDATE записал то же самое значение 1 — строка в reviews «обновилась» (UPDATE 1), но условие OLD.rating IS DISTINCT FROM NEW.rating ложно, триггер не сработал, счётчик журнала не вырос. Значение NULL в old_rating/new_rating появилось бы при изменении с/на NULL — обычное сравнение <> здесь бы ошиблось, IS DISTINCT FROM — нет (глава 2.1).

BEFORE: право менять и отменять

BEFORE-триггеры сильнее: они видят строку до записи и могут её изменить или отменить операцию. «В случае BEFORE- и INSTEAD OF-триггеров возможно-изменённая строка, возвращённая каждым триггером, становится входом для следующего триггера. Если любой BEFORE- или INSTEAD OF- триггер возвращает NULL, операция отменяется для этой строки, и последующие триггеры не срабатывают (для этой строки)» (37.1). Практические следствия: нормализация данных в NEW (например, NEW.rating := LEAST(NEW.rating, 5)), тихий пропуск отдельных строк через RETURN NULL. Мы уже встречали триггеры без объявления: каскадные действия ограничения внешнего ключа из главы 4.2 внутри устроены как триггеры — файл src/backend/utils/adt/ri_triggers.c так и назван: «общие триггерные процедуры для проверок ограничений ссылочной целостности» (шапка, строки 3–5); в каталоге pg_trigger системные триггеры помечены полем tgisinternal («trigger is system-generated», pg_trigger.h, строка 47).

Как это исполняется

Создание: CREATE TRIGGER обрабатывает CreateTrigger в src/backend/commands/trigger.c (строка 159 на коммите 083ac033419f690758508e08c1736089384bbee8; расширенный вариант с условием срабатывания — CreateTriggerFiringOn, строка 176) и пишет строку в системный каталог pg_trigger: tgrelid — «таблица, к которой прикреплён триггер» (строка 37), tgname (41), tgfoid — «OID функции, которая будет вызвана» (42), tgtype — «BEFORE/AFTER/INSTEAD, UPDATE/DELETE/INSERT, ROW/STATEMENT» (43), а условие WHEN — в tgqual («выражение WHEN, или NULL, если его нет», строка 69); каталог CATALOG(pg_trigger, 2620, ...) объявлен в src/include/catalog/pg_trigger.h (строка 34). Исполнение: при каждом UPDATE исполнитель вызывает строчные BEFORE-триггеры через ExecBRUpdateTriggers (trigger.c, строка 3152) до записи строки. AFTER-триггеры устроены иначе: «строчные AFTER-триггеры срабатывают в конце оператора» (37.1), и в коде это очередь событий — события накапливаются при обработке строк и запускаются функцией afterTriggerInvokeEvents (строка 4703) из AfterTriggerEndQuery (строка 5141), когда оператор завершает работу. Отсюда важное следствие для логов: если AFTER-триггер упадёт с ошибкой, весь оператор откатится, потому что «триггер выполняется как часть той же транзакции, что и оператор, который его вызвал, так что если либо оператор, либо триггер вызовет ошибку, эффекты обоих будут откачены» (37.1) — глава 6.1 в действии. Плата за автоматизм: триггер срабатывает на каждый UPDATE, включая массовые, — при миллионах строк журнал растёт так же массово.

Связь с теорией

Триггеры — концепция стандарта SQL: Silberschatz (7-е изд., гл. 5 Advanced SQL, § 5.3 Triggers, с. 206) определяет их как операторы, автоматически выполняемые как побочный эффект модификации базы данных, и разбирает классические применения: аудит, поддержка производных значений, целостность. Раздел 37.1 — спецификация PostgreSQL тех же идей; отличие в том, что триггерная функция у PostgreSQL — отдельный переиспользуемый объект, а не встроенный блок CREATE TRIGGER. Связь с остальной книгой: условие WHEN — обычное булево выражение (глава 2.1), тело — PL/pgSQL (глава 10.2), журнал — таблица с IDENTITY (глава 4.6), атомарность вместе с оператором — транзакции (глава 6.1).

Проверь себя

Вопрос 1. Чем AFTER ... FOR EACH ROW отличается от BEFORE ... FOR EACH ROW по моменту срабатывания и возможностям?

Ответ. «Строчные BEFORE-триггеры срабатывают непосредственно перед обработкой конкретной строки, тогда как строчные AFTER-триггеры срабатывают в конце оператора (но до statement-level AFTER-триггеров)» (37.1). BEFORE может менять строку («возможно-изменённая строка, возвращённая каждым триггером, становится входом для следующего») и отменять операцию («если любой BEFORE- или INSTEAD OF-триггер возвращает NULL, операция отменяется для этой строки», 37.1). AFTER подходит для журналирования: строка уже точно изменена.

Вопрос 2. Почему в условии WHEN используется IS DISTINCT FROM, а не <>? Что будет, если заменить?

Ответ. IS DISTINCT FROM (глава 2.1) даёт корректное сравнение при NULL: если старое или новое значение — NULL, OLD.rating <> NEW.rating вернёт NULL (трёхзначная логика SQL, глава 2.1), условие не сработает, и изменение с NULL или на NULL не попадёт в журнал. IS DISTINCT FROM в таких случаях возвращает true — изменение фиксируется.

Вопрос 3. Триггерная функция упала с ошибкой во время UPDATE 500 строк. Что произойдёт с журналом, с таблицей и почему?

Ответ. Откатится всё: «триггер выполняется как часть той же транзакции, что и оператор, который его вызвал, так что если либо оператор, либо триггер вызовет ошибку, эффекты обоих будут откачены» (37.1). Ни изменения строк, ни вставки в журнал не останутся — атомарность транзакции из главы 6.1 распространяется и на триггерные эффекты.
