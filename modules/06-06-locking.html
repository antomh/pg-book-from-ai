Глава 6.6. Блокировки и тупики

Уровень: J · узел карты тем: T32 · PostgreSQL 17.11

UPDATE «завис», и никто не понимает почему

Модератор открыл транзакцию, обновил один отзыв и ушёл на обед. Все операции с этой строкой в других сессиях висят без ошибки и без результата. Техподдержка спрашивает: «что за блокировка, кто её держит и когда отпустит?» MVCC из главы 6.4 снял конфликты «чтение против записи», но записи между собой по-прежнему сериализуются — блокировками строк; добавляются и блокировки уровня таблицы. Эта глава — карта: какие блокировки бывают, кто их берёт, как читать ожидание и что делать с тупиками.

Два уровня: таблица и строка

«PostgreSQL предоставляет различные режимы блокировок для управления конкурентным доступом к данным в таблицах. Эти режимы могут использоваться для управляемого приложением блокирования в ситуациях, когда MVCC не даёт желаемого поведения. Кроме того, большинство команд PostgreSQL автоматически приобретают блокировки подходящих режимов, чтобы гарантировать, что упоминаемые таблицы не будут удалены или изменены несовместимым образом» — (/docs/17/explicit-locking.html, 13.3, перевод дословный). Табличные режимы — восемь штук, и вот главное о них: «единственное реальное различие между режимами — набор режимов, с которыми каждый конфликтует (таблица 13.2)». Кто что берёт автоматически (13.3.1, дословно):

РежимТипичный владелец
ACCESS SHARE«Команда SELECT приобретает блокировку этого режима на упоминаемых таблицах»
ROW SHARE«Команда SELECT... с опциями FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE или FOR KEY SHARE»
ROW EXCLUSIVE«Команды UPDATE, DELETE, INSERT и MERGE приобретают этот режим на целевой таблице»
SHARE UPDATE EXCLUSIVE«Этот режим защищает таблицу от конкурентных изменений схемы и запусков VACUUM. Приобретается VACUUM (без FULL), ANALYZE, CREATE INDEX CONCURRENTLY...»
SHARE«Этот режим защищает таблицу от конкурентных изменений данных. Приобретается CREATE INDEX (без CONCURRENTLY)»
SHARE ROW EXCLUSIVE«Приобретается CREATE TRIGGER и некоторыми формами ALTER TABLE»
EXCLUSIVE«Позволяет только конкурентные блокировки ACCESS SHARE, то есть только чтение из таблицы может продолжаться параллельно»
ACCESS EXCLUSIVE«Приобретается DROP TABLE, TRUNCATE, REINDEX, CLUSTER, VACUUM FULL...»; «это режим по умолчанию для операторов LOCK TABLE без явного указания режима»

Полезные следствия из 13.3.1: «только блокировка ACCESS EXCLUSIVE блокирует оператор SELECT (без FOR UPDATE/SHARE)» — обычное чтение никогда не ждёт из-за табличных блокировок, кроме самых жёстких; и «однажды полученная, блокировка обычно удерживается до конца транзакции. Но если блокировка получена после установки savepoint, она освобождается немедленно при откате к этому savepoint». Явно запросить табличную блокировку можно командой LOCK: «LOCK TABLE запрашивает табличную блокировку, ожидая при необходимости освобождения конфликтующих блокировок. Если указан NOWAIT, LOCK TABLE не ждёт... Однажды полученная, блокировка удерживается до конца текущей транзакции. (Команды UNLOCK TABLE не существует; блокировки всегда освобождаются в конце транзакции.)» (/docs/17/sql-lock.html).

Блокировки строк: FOR UPDATE и его семья

Строчные блокировки — то, что «подвесило» UPDATE из проблемы: «блокировки уровня строки не влияют на запросы к данным; они блокируют только писателей и блокирующих ту же строку» (13.3.2). Блокирует пишущий оператор автоматически: «режим блокировки FOR UPDATE также приобретается любым DELETE строки и любым UPDATE, изменяющим значения определённых столбцов» (13.3.2). Читателю доступно то же оружие явно: «FOR UPDATE заставляет строки, полученные оператором SELECT, быть заблокированными как для обновления. Это предотвращает их блокировку, изменение или удаление другими транзакциями до конца текущей транзакции» (13.3.2). Паттерн «прочитать — изменить — зафиксировать» без гонок:

BEGIN;

SELECT review_id, rating FROM reviews
WHERE reader_id = 1 AND book_id = 4
FOR UPDATE;

UPDATE reviews SET comment = 'обновлено после проверки'
WHERE reader_id = 1 AND book_id = 4;

COMMIT;

Что произойдёт и почему: SELECT пометил строки читателя 1 по книге 4 как занятые до конца транзакции; конкурентный UPDATE тех же строк будет ждать (модератор из входной проблемы именно в этом состоянии), а другой SELECT ... FOR UPDATE — тоже. Обычный SELECT без FOR UPDATE не заметит ничего — «блокировки уровня строки не влияют на запросы к данным» (13.3.2), он увидит и старые, и новые версии по правилам снимков из главы 6.4. Родственные режимы из той же таблицы 13.3.3: FOR NO KEY UPDATE («ведёт себя похоже на FOR UPDATE, кроме того, что полученная блокировка слабее»), FOR SHARE, FOR KEY SHARE; ожидание можно отключить опцией NOWAIT у SELECT — тогда вместо ожидания будет немедленная ошибка.

Что происходит при ожидании

Механизм ожидания в исходном коде двухступенчатый. Постановка в очередь и захват тяжёлой (heavyweight) блокировки — LockAcquire в src/backend/storage/lmgr/lock.c (строка 756 на коммите 083ac033419f690758508e08c1736089384bbee8); её комментарий честен про цену: «NOTE: если мы ждём блокировку, нет способа прервать ожидание иначе как откатом транзакции» — Ctrl+C в psql оборвёт не ожидание, а транзакцию. Ожидание завершения транзакции-владельца строки — XactLockTableWait в src/backend/storage/lmgr/lmgr.c (строка 657): именно она заставляет второй UPDATE висеть, пока первый не зафиксируется или откатится. Отсюда практическое правило производительности: «это плохая идея — держать транзакции открытыми долгое время (например, ожидая пользовательский ввод)» (13.3.4, Tip).

Взаимоблокировки

Определение: «использование явных блокировок может увеличить вероятность взаимоблокировок (deadlocks), при которых две (или более) транзакции держат блокировки, которые хочет каждая из других. Например, если транзакция 1 приобретает исключительную блокировку таблицы A и затем пытается приобрести исключительную блокировку таблицы B, в то время как транзакция 2 уже исключительно заблокировала B и хочет исключительную блокировку A, ни одна не может продолжить» (13.3.4). Развязка: «PostgreSQL автоматически обнаруживает ситуации взаимоблокировки и разрешает их откатом одной из участвующих транзакций, позволяя другим завершиться. (Какую именно транзакцию откатить — трудно предсказать, и на это не следует полагаться.)» Важно: «взаимоблокировки могут также возникать как результат блокировок уровня строки (и, таким образом, они могут возникать даже без явных блокировок)». Документированный сценарий на двух строках счёта (UPDATE accounts ... WHERE acctnum = 11111 в одной транзакции и ... = 22222, затем перекрёстно — 13.3.4) переносится на нашу схему один в один:

-- сессия 1
BEGIN;
UPDATE reviews SET rating = rating WHERE review_id = 1;  -- блокирует строку 1

-- сессия 2 (параллельно)
BEGIN;
UPDATE reviews SET rating = rating WHERE review_id = 2;  -- блокирует строку 2

-- сессия 1
UPDATE reviews SET rating = rating WHERE review_id = 2;  -- ждёт сессию 2

-- сессия 2
UPDATE reviews SET rating = rating WHERE review_id = 1;  -- цикл: тупик

Что произойдёт и почему: каждая сессия держит по строке и хочет строку соседа — «транзакция 1 заблокирована на транзакции 2, а транзакция 2 заблокирована на транзакции 1: условие взаимоблокировки. PostgreSQL обнаружит эту ситуацию и откатит одну из транзакций» (13.3.4, по мотивам примера с accounts). Обратите внимание на rating = rating: UPDATE блокирует строку, даже если значение не меняется — счётчик команды включает «строки, совпавшие по условию, но чьи значения не изменились» (Outputs, sql-update). Оставшаяся сессия продолжит работу и зафиксируется; aborted-сессии придётся повторить транзакцию (глава 6.2). Лучшая защита — дисциплина порядка: «лучшая защита от взаимоблокировок — в целом избегать их, гарантируя, что все приложения, использующие базу данных, приобретают блокировки на несколько объектов в согласованном порядке» (13.3.4) — в примере выше оба UPDATE в порядке возрастания review_id не создали бы цикла. И запасной план: «взаимоблокировки можно обрабатывать на лету, повторяя транзакции, которые прерваны из-за взаимоблокировок» (13.3.4).

Связь с теорией

Взаимоблокировки — классика управления конкурентностью: Silberschatz разбирает их в § 18.2 (Deadlock Handling): граф ожидания, цикл в котором и есть тупик; стратегии — предотвращение (согласованный порядок захвата — то, что рекомендует документация) и обнаружение с жертвой (то, что делает PostgreSQL автоматически). Блокировочные протоколы двухфазные (§ 18.1) в терминах таблицы 13.1 реализуются командой LOCK, но PostgreSQL целенаправленно уводит разработчика от них к MVCC (глава 6.4).

Проверь себя

Вопрос 1. Почему обычный SELECT не «виснет» на заблокированной UPDATE строке, а второй UPDATE — виснет?

Ответ. «Блокировки уровня строки не влияют на запросы к данным; они блокируют только писателей и блокирующих ту же строку» (13.3.2) — SELECT читает по правилам MVCC (глава 6.4). Пишущий оператор приобретает режим FOR UPDATE («также приобретается любым DELETE... и UPDATE, изменяющим значения определённых столбцов») и конфликтует с чужой такой же блокировкой: ожидание идёт через XactLockTableWait (lmgr.c L657) до COMMIT/ROLLBACK владельца.

Вопрос 2. Две транзакции: первая держит блокировку строки A и ждёт строку B, вторая держит B и ждёт A. Что сделает PostgreSQL и можно ли предсказать «жертву»?

Ответ. «PostgreSQL автоматически обнаруживает ситуации взаимоблокировки и разрешает их откатом одной из участвующих транзакций... (Какую именно транзакцию откатить — трудно предсказать, и на это не следует полагаться.)» (13.3.4). Приложение обязано уметь повторить прерванную транзакцию.

Вопрос 3. Какие два приёма из документации снижают риск взаимоблокировок, и почему UPDATE ... SET x = x тоже может участвовать в тупике?

Ответ. Приёмы: «все приложения... приобретают блокировки на несколько объектов в согласованном порядке» и «повторение транзакций, которые прерваны из-за взаимоблокировок» (13.3.4). SET x = x блокирует строку, потому что UPDATE считает «строки, совпавшие по условию, но чьи значения не изменились» (sql-update, Outputs), — для блокировок важен целевой ряд, а не факт изменения значения.
