Глава 1.2. Кластер, база данных, роль; psql

Уровень: J · узел карты тем: T02 · PostgreSQL 17.11

Куда именно вы «входите», когда подключаетесь к PostgreSQL

Сценарий: вы установили PostgreSQL, открыли psql и создали таблицы учебного проекта. Через месяц появляется второй проект — и вопрос: «завести ещё одну базу или ещё одну таблицу в той же?» А рядом вопрос коллеги: «дай мне доступ, только к моим таблицам». Чтобы отвечать на такие вопросы, нужно понимать, из каких уровней состоит работающий PostgreSQL и что из этого видно из одного подключения. Это глава о каркасе, в который попадают все ваши таблицы.

Иерархия: кластер → базы → схемы → таблицы

Документация описывает устройство так (раздел «Schemas», 5.10, /docs/17/ddl-schemas.html, дословно в переводе):

Кластер баз данных PostgreSQL содержит одну или несколько именованных баз данных. Роли и некоторые другие типы объектов общие для всего кластера. Клиентское подключение к серверу может обращаться к данным только одной базы — той, что указана в запросе на соединение.

И далее там же: «база данных содержит одну или несколько именованных схем, которые, в свою очередь, содержат таблицы; схемы также содержат и другие именованные объекты — типы данных, функции, операторы».

В виде схемы уровней:

кластер (набор баз данных, управляемый одним
   работающим экземпляром сервера PostgreSQL)
├── база bookshelf
│   ├── схема public  → таблицы authors, books
│   └── схема archive → таблицы books_2023
├── база postgres (создаётся при инициализации)
└── базы-шаблоны template0, template1
      (используются как образцы для CREATE DATABASE)

роли: postgres, app_user, …   ← общие на весь кластер, базе не принадлежат

Два следствия из этой цитаты, которые часто удивляют новичков:

  • Одно подключение = одна база. Запрос SQL изнутри сессии не может обратиться к таблицам другой базы того же кластера. Чтобы перейти на другую базу, нужно новое соединение с указанием её имени (в psql метакоманда \c «устанавливает новое соединение с сервером PostgreSQL» — дословно по документации; она заменяет текущее подключение, а не расширяет).
  • Роли не принадлежат базам. У каждой роли есть право или запрет на доступ к конкретной базе, но сама учётная запись — одна на весь кластер: не может быть двух разных ролей с именем joe в двух базах одного кластера (там же, 5.10).

Почему база — именно «верхний» уровень: документация главы «Managing Databases» формулирует прямо: «базы данных — это самый верхний иерархический уровень организации SQL-объектов» (/docs/17/managing-databases.html, раздел Overview).

Схемы внутри базы

Схема — это пространство имён внутри базы. В базах, создаваемых по умолчанию, есть схема public: таблицы без явного указания схемы попадают в неё, и обращения вида books без префикса интерпретируются через неё (механизм поиска имён search_path подробно разобран в главе 4.5). Свою схему создать просто:

CREATE SCHEMA archive;

после чего таблицы можно создавать уже в ней: CREATE TABLE archive.books_2023 (...). Синтаксис — /docs/17/sql-createschema.html; описание схем — /docs/17/ddl-schemas.html (5.10).

База и роль как объекты SQL

Создание новой базы — обычная SQL-команда; право на неё даёт привилегия CREATEDB (для ролей — раздел «Creating a Database» (22.2) в Managing Databases, синтаксис — /docs/17/sql-createdatabase.html): 

CREATE DATABASE bookshelf;

Учётные записи в PostgreSQL называются ролями. Документация главы «Database Roles» формулирует: «концепция ролей вбирает в себя концепции пользователей и групп» (/docs/17/user-manag.html, раздел Introduction). Роль с атрибутом LOGIN может подключаться к серверу:

CREATE ROLE app_user LOGIN PASSWORD 'change-me';

(синтаксис и атрибуты ролей — /docs/17/sql-createrole.html; выдача прав на объекты — тема главы 11.1). Подключаясь, вы всегда задаёте пару «роль + база»: об этом — вводная часть Tutorial: Getting Started.

psql: терминальный клиент

psql — это «терминальный фронтенд к PostgreSQL: он позволяет вводить запросы в интерактивном режиме, отправлять их в PostgreSQL и видеть результаты», дословно по документации /docs/17/app-psql.html. Учебник не выполняет SQL за вас, поэтому дальше показываем сессии как статические примеры: команда — и что будет выведено.

Подключение с указанием базы и осмотр окружения:

$ psql bookshelf
psql (17.11)
Type "help" for help.

bookshelf=# \dt
         List of relations
 Schema |  Name   | Type  | Owner
--------+---------+-------+----------
 public | authors | table | postgres
 public | books   | table | postgres
(2 rows)

Что здесь произошло и почему: приглашение bookshelf=# показывает имя текущей базы; \dt — метакоманда psql (команды, начинающиеся с обратной косой черты), которая выводит список таблиц (\dt, \dn — схемы, \l — базы данных; полный список метакоманд — раздел «Meta-Commands» в документации psql). Метакоманды — это не SQL: они обрабатываются самим psql.

Переход на другую базу — отдельным переподключением:

bookshelf=# \c postgres
You are now connected to database "postgres" as user "postgres".
postgres=#

Что здесь произошло и почему: \c устанавливает новое соединение к серверу с новыми параметрами (база, пользователь, хост, порт); прежнее соединение замещается — формулировка и синтаксис приведены в разделе «Meta-Commands» документации psql (/docs/17/app-psql.html).

Проверь себя

Вопрос 1. Приложение подключено к базе bookshelf. Может ли оно одним и тем же соединением выполнить запрос к таблице в базе postgres?

Ответ. Нет. Клиентское подключение работает ровно с одной базой — той, что указана при соединении; это зафиксировано в разделе 5.10 «Schemas»: /docs/17/ddl-schemas.html. Нужна таблица из другой базы — это отдельное соединение (или перенос данных в одну базу, например в разные схемы).

Вопрос 2. Две команды в вашей компании используют один кластер PostgreSQL. Почему не получится завести в каждой командной базе роль с одинаковым именем reader?

Ответ. Роли общие для всего кластера, базе они не принадлежат — там же, 5.10. Имя роли уникально в кластере; доступ роли к конкретным базам настраивается отдельно. Разграничение «чужое-своё» внутри одной базы делают схемы и привилегии (главы 4.5 и 11.1).

Вопрос 3. Чем метакоманда psql \dt отличается от SQL-запроса SELECT? Почему вывод \dt выглядит «по-человечески»?

Ответ. Метакоманды обрабатывает сам клиент psql (они начинаются с обратной черты и не отправляются на сервер в исходном виде), а SELECT — язык запросов сервера. Удобный вывод \dt — тоже работа клиента. И там и там данные об объектах берутся из хранимых сервером метаданных — что это за хранилище, показывает глава 1.3.
