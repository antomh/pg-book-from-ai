Глава 4.5. Схемы и search_path

Уровень: J+ · узел карты тем: T22 · PostgreSQL 17.11

Два приложения, одна база, таблица events — у каждого

В одной базе работают веб-приложение и фоновый загрузчик — оба принесли по таблице events. Уровень «база данных» не поможет: в главе 1.2 мы видели, что соединение работает ровно с одной базой. Промежуточный уровень именования PostgreSQL — схемы: пространство имён внутри базы. Глава отвечает на вопросы: как разложить объекты по схемам, почему books без префикса обычно указывает на public.books, как сервер ищет объект по незакавыченному имени и где тут спрятана проблема безопасности. Уровень J+.

Схема — пространство имён внутри базы

Раздел 5.10 (/docs/17/ddl-schemas.html) задаёт устройство: «база данных содержит одну или несколько именованных схем, которые, в свою очередь, содержат таблицы. Схемы содержат и другие виды именованных объектов, включая типы данных, функции и операторы. Внутри одной схемы два объекта одного типа не могут иметь одинаковое имя» (перевод дословный). Зачем это нужно — документация даёт три причины: «позволить многим пользователям работать с одной базой, не мешая друг другу; организовать объекты базы данных в логические группы; сторонние приложения можно поместить в отдельные схемы, чтобы они не конфликтовали с именами других объектов». И ограничение: «схемы аналогичны каталогам на уровне операционной системы, за исключением того, что схемы не могут быть вложенными».

CREATE SCHEMA reader_app;

CREATE TABLE reader_app.events (
    -- столбцы identity — тема следующей главы (4.6); пока читайте
    -- эту строку как «автонумерация»
    event_id   bigint GENERATED ALWAYS AS IDENTITY,
    kind       text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);

reader_app.events — полное (квалифицированное) имя. Таблица events веб-приложения может жить своей схемой web.events, и конфликтов имён не будет. Обращение к объекту другой схемы — только с префиксом.

Откуда взялась public

Все наши таблицы до сих пор создавались без префикса — и попадали в схему public: «по умолчанию такие таблицы (и другие объекты) автоматически помещаются в схему с именем public. Каждая новая база данных содержит такую схему» (5.10.2). Документация подчёркивает эквивалентность: CREATE TABLE products (...) — то же, что CREATE TABLE public.products (...). В терминах главы 1.3: \d books показывал таблицу в схеме public, потому что она — первая подходящая в пути поиска имён. Как это работает — следующий раздел.

search_path: как разрешается незакавыченное имя

Полные имена писать утомительно, поэтому большинство запросов обходится короткими. Правило из 5.10.3: «система определяет, какую таблицу имеют в виду, следуя пути поиска (search path) — списку схем для поиска. Первая совпавшая таблица в пути поиска считается искомой. Если совпадений в пути поиска нет, сообщается об ошибке, даже если совпадающие имена есть в других схемах базы». Посмотреть текущий путь:

SHOW search_path;
   search_path
-----------------
 "$user", public
(1 row)

Что выведено и почему: это значение по умолчанию из 5.10.3 (вывод совпадает с документированным примером там же). Первый элемент — «схема с тем же именем, что и текущий пользователь; если такой схемы не существует, элемент игнорируется» (у нас такой схемы нет), второй — public. Заодно это правило создания: «первая существующая схема в пути поиска — место по умолчанию для создания новых объектов. Именно поэтому по умолчанию объекты создаются в схеме public».

SET search_path TO reader_app, public;

INSERT INTO events (kind) VALUES ('book_opened');

Что произойдёт и почему: после SET путь начинается с reader_app, поэтому незакавыченный events разрешится в reader_app.events, и строка попадёт в таблицу приложения; а новый CREATE TABLE foo (...) без префикса создал бы reader_app.foo — первая схема пути стала «текущей» и для поиска, и для создания.

pg_catalog ищется всегда

Системный каталог из главы 1.3 живёт в собственной схеме: «помимо public и пользовательских схем, каждая база данных содержит схему pg_catalog, в которой находятся системные таблицы и все встроенные типы данных, функции и операторы» (5.10.5). Важное правило оттуда: «pg_catalog всегда фактически является частью пути поиска. Если она не названа явно в пути, она неявно ищется перед схемами пути. Это гарантирует, что встроенные имена всегда будут находимы». Поэтому pg_class, now(), + находятся без каких-либо префиксов при любом search_path — и поэтому пользователю не стоит называть свои объекты с префикса pg_ («системные таблицы будут продолжать следовать соглашению начинаться с pg_, так что они не будут конфликтовать с незакавыченными пользовательскими именами, пока пользователи избегают префикса pg_», там же).

Проблема безопасности: подмена имени

Путь поиска — не только удобство, но и вектор атаки. Сценарий из 5.10.6: злоумышленник, имеющий право создавать объекты в некоторой схеме, первой в чьём-то search_path, может подложить туда объект с чужим именем — например, функцию с тем же именем и совместимой сигнатурой, и чужой запрос молча вызовет её. Формулировка документации: «безопасная схема использования (secure schema usage pattern) предотвращает изменение поведения чужих запросов недоверенными пользователями». Для junior-уровня следствие одно: в коде приложения надёжнее обращаться к объектам по полным именам (public.books вместо books) или держать search_path под контролем администратора базы; детально механизмы доступа — модуль 11.

Проверь себя

Вопрос 1. Где окажется таблица после CREATE TABLE t(...) при search_path = "$user", public, если схема с именем пользователя не существует? Почему?

Ответ. В public. Несуществующий элемент "$user" игнорируется; «первая существующая схема в пути поиска — место по умолчанию для создания новых объектов» (5.10.3), а public «каждая новая база данных содержит» (5.10.2).

Вопрос 2. При search_path = reader_app, public запрос обращается к events. В какой таблице окажется INSERT, и что произойдёт, если убрать reader_app из пути?

Ответ. INSERT пойдёт в reader_app.events: «первая совпавшая таблица в пути поиска считается искомой» (5.10.3). После удаления схемы из пути тот же запрос будет разрешён в public.events, а если её нет — «сообщается об ошибке, даже если совпадающие имена есть в других схемах базы».

Вопрос 3. Почему pg_class находится при любом search_path, и почему пользователю не стоит называть свои таблицы с префикса pg_?

Ответ. «pg_catalog всегда фактически является частью пути поиска... неявно ищется перед схемами пути. Это гарантирует, что встроенные имена всегда будут находимы» (5.10.5). Префикс pg_ зарезервирован конвенцией системных объектов, чтобы «не конфликтовать с незакавыченными пользовательскими именами» (там же); pg_ -имя пользователя могло бы быть перекрыто системным объектом.
