Глава 4.7. Декларативное партиционирование

Уровень: J+ · узел карты тем: T24 · PostgreSQL 17.11

Таблица на миллиард отзывов, из которой каждый год вычищают старьё

Проект вырос. Таблица отзывов копит миллионы строк в год, и каждый январь по регламенту нужно избавляться от данных трёхлетней давности. DELETE миллионов строк — часы блокировок, а потом сервер неделями чистит мёртвые версии (глава 6.7). При этом почти все запросы читают только последние месяцы. Все три проблемы решает один приём: объявить таблицу набором физических кусков по диапазону дат. Глава показывает декларативное партиционирование PostgreSQL на RANGE, LIST и HASH, главную ловушку с первичными ключами и то, как планировщик находит нужный кусок. Уровень J+.

Что даёт партиционирование

«Партиционирование означает разбиение одной логически большой таблицы на меньшие физические куски» — раздел 5.12 (/docs/17/ddl-partitioning.html). Документация сразу называет и выгоду для нашего сценария: «массовые загрузки и удаления могут выполняться добавлением или удалением партиций... удаление отдельной партиции с помощью DROP TABLE или ALTER TABLE DETACH PARTITION намного быстрее массовой операции. Эти команды также полностью избегают накладных расходов VACUUM, вызванных массовым DELETE» (5.12.1, перевод дословный). Там же — граница целесообразности: «эти выгоды обычно оправданы, только когда таблица иначе была бы очень большой. Точная точка, в которой таблица получит выгоду от партиционирования, зависит от приложения, хотя правило большого пальца — размер таблицы должен превышать физическую память сервера базы данных».

PostgreSQL предлагает три встроенных способа разбиения (дословно из 5.12.1): RANGE — «таблица разбивается на "диапазоны", определённые ключевым столбцом или набором столбцов, без перекрытий»; LIST — «таблица разбивается явным перечислением, какие значения ключа попадают в каждую партицию»; HASH — «таблица разбивается указанием модуля и остатка для каждой партиции. Каждая партиция будет содержать строки, для которых хеш-значение ключа партиции, делённое на указанный модуль, даёт указанный остаток».

Создание партиционированной таблицы

Рецепт из документации: сначала родительская таблица с предложением PARTITION BY, затем партиции. Пересоберём отзывы: таблица reviews из глав 4.2 и 4.4 уже существует, поэтому в реальном проекте её предварительно переименовали бы (ALTER TABLE reviews RENAME TO reviews_old) или удалили (DROP TABLE reviews) и перенесли данные; сами шаги переноса — тема эксплуатации, не учебника. Заметьте и смену типа ключа: review_id bigint — осознанное решение для таблицы, которую проектируют «на вырост» (диапазоны целых типов — глава 3.1; миграция integer → bigint на живой таблице — в главе 4.4):

CREATE TABLE reviews (
    review_id  bigint NOT NULL,
    reader_id  integer NOT NULL REFERENCES readers,
    book_id    integer NOT NULL REFERENCES books,
    rating     smallint NOT NULL CHECK (rating BETWEEN 1 AND 5),
    comment    text,
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (review_id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE reviews_2026_10 PARTITION OF reviews
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

CREATE TABLE reviews_2026_11 PARTITION OF reviews
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

Правила раскладки задают границы партиций: «определение каждой партиции должно указывать границы, соответствующие методу партиционирования и ключу родителя. Обратите внимание, что указание границ, при которых значения новой партиции перекрывались бы с одной или несколькими существующими партициями, вызовет ошибку» (5.12.2). Вставляемая строка направляется в партицию по значению created_at: по справочнику CREATE TABLE — «при создании range-партиции нижняя граница, указанная в FROM, — включающая, тогда как верхняя, указанная в TO, — исключающая. То есть значения из списка FROM допустимы для этой партиции, а значения из списка TO — нет». Важно понимать статус кусков: «партиции, созданные таким образом, — во всех отношениях обычные таблицы PostgreSQL»: их можно индексировать отдельно, копировать, а в конце года — «отстегнуть»: ALTER TABLE reviews DETACH PARTITION reviews_2026_10; — после чего партиция снова становится самостоятельной таблицей, которую можно заархивировать или удалить DROP'ом без VACUUM.

Ловушка: первичный ключ обязан включать ключ партиционирования

Обратите внимание на PRIMARY KEY (review_id, created_at) — именно created_at добавлен к идентификатору. Причина документирована дословно: «чтобы создать ограничение unique или primary key на партиционированной таблице, ключи партиционирования не должны включать выражений или вызовов функций, а столбцы ограничения должны включать все столбцы ключа партиционирования. Это ограничение существует, потому что отдельные индексы, составляющие ограничение, могут напрямую обеспечивать уникальность только внутри своих партиций; поэтому сама структура партиций должна гарантировать, что дубликатов в разных партициях нет» (5.12.2). Простой PRIMARY KEY (review_id) создать не получится: индекс внутри октябрьской партиции не знает о ноябрьской. Это следствие приходится проектировать заранее: глобальная уникальность review_id теперь поддерживается парой (review_id, created_at) — и приложению стоит генерировать review_id последовательностью (глава 4.6), если нужна монополия на уникальность идентификатора без даты.

Как запрос находит нужную партицию

На концептуальном уровне — отсечение партиций (partition pruning): «партиционное отсечение — техника оптимизации запросов, улучшающая производительность для декларативно партиционированных таблиц... при включённом отсечении планировщик исследует определение каждой партиции и доказывает, что партицию не нужно сканировать, потому что она не может содержать строк, удовлетворяющих WHERE-условию запроса. Когда планировщик может это доказать, он исключает (отсекает) партицию из плана запроса» (5.12.4). Для запроса SELECT ... FROM reviews WHERE created_at >= '2026-11-01' планировщик отсекает октябрьскую партицию: диапазон её границ не пересекается с условием, и чтение диска сокращается ровно до «горячих» месяцев. Это не ручной код, а штатная работа планировщика (по умолчанию включена: параметр enable_partition_pruning = on, там же). Детальная кухня планировщика — модуль 9.

Когда партиционировать не надо

Правило большого пальца из 5.12.1 — «таблица должна превышать физическую память сервера» — отсекает большинство учебных и малых проектов. Партиции добавляют стоимость: планирование «в целом хорошо справляется с иерархиями партиций до нескольких тысяч партиций, при условии, что типичные запросы позволяют планировщику отсечь все, кроме малого числа партиций... время планирования растёт, а потребление памяти — выше, когда после отсечения остаётся больше партиций» (5.12.6). Дизайн-совет документации: «выбор схемы партиционирования должен определяться требованиями приложения», а не модой; типовые варианты — RANGE по времени для журналов и событий (наш случай), LIST по регионам, HASH для равномерного распределения нагрузки (5.12.6).

Проверь себя

Вопрос 1. Почему для архивации старых отзывов DETACH PARTITION выгоднее DELETE, и при каких размерах таблицы партиционирование вообще имеет смысл?

Ответ. «Удаление отдельной партиции с помощью DROP TABLE или ALTER TABLE DETACH PARTITION намного быстрее массовой операции. Эти команды также полностью избегают накладных расходов VACUUM, вызванных массовым DELETE» (5.12.1). Порог: «выгоды обычно оправданы, только когда таблица иначе была бы очень большой... правило большого пальца — размер таблицы должен превышать физическую память сервера базы данных» (там же).

Вопрос 2. Почему PRIMARY KEY партиционированной reviews обязан включать created_at, и что гарантирует уникальность review_id между партициями?

Ответ. «Столбцы ограничения должны включать все столбцы ключа партиционирования... отдельные индексы, составляющие ограничение, могут напрямую обеспечивать уникальность только внутри своих партиций; поэтому сама структура партиций должна гарантировать, что дубликатов в разных партициях нет» (5.12.2). Уникальность «голого» review_id между партициями не гарантируется ничем — только парой (review_id, created_at) или дисциплиной генерации (последовательность, глава 4.6).

Вопрос 3. Запрос фильтрует reviews по условию created_at >= '2026-11-01'. Что сделает планировщик с партицией reviews_2026_10 и как называется этот механизм?

Ответ. Исключит её из плана — partition pruning: «планировщик исследует определение каждой партиции и доказывает, что партицию не нужно сканировать, потому что она не может содержать строк, удовлетворяющих WHERE-условию запроса» (5.12.4); параметр enable_partition_pruning по умолчанию включён.
