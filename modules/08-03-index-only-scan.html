Глава 8.3. Index-only scan и карта видимости

Уровень: J+ · узел карты тем: T39 · PostgreSQL 17.11

«Индекс покрывает запрос» — а heap всё равно читается

В главе 8.2 запрос SELECT rating, created_at FROM reviews WHERE book_id = 13 получил план «Index Only Scan» — данные взяты из индекса, таблица не читалась. Разработчик запускает тот же запрос после вечерней активности модуля 6 (вставки, обновления, откаты) — и в плане появляется обращение к таблице. Индекс не изменился, запрос не изменился. Почему «покрывающий» индекс иногда перестаёт покрывать? Ответ спрятан в связке двух механизмов: MVCC (глава 6.4) и карты видимости (глава 6.7).

Два условия и третье, невидимое

Идея метода из 11.9 (/docs/17/indexes-index-only-scans.html, перевод дословный): «базовая идея — возвращать значения прямо из каждого элемента индекса вместо обращения к соответствующему элементу heap. Есть два фундаментальных ограничения на то, когда этот метод может использоваться». Первое: «тип индекса должен поддерживать index-only сканирования. B-tree индексы всегда это делают. GiST и SP-GiST поддерживают index-only сканирования для одних классов операторов, но не для других. Прочие типы индексов поддержки не имеют. Базовое требование: индекс должен физически хранить или уметь восстанавливать исходное значение данных для каждого элемента индекса. Как контрпример, GIN индексы не могут поддерживать index-only сканирования, потому что каждый элемент индекса обычно содержит только часть исходного значения данных». Второе: «запрос должен ссылаться только на столбцы, хранящиеся в индексе» — включая INCLUDE-столбцы из главы 8.2. И третье, самое интересное: «есть дополнительное требование для любого сканирования таблицы в PostgreSQL: оно должно проверять, что каждая извлечённая строка "видима" снимку MVCC запроса... Информация о видимости не хранится в элементах индекса, только в элементах heap. На первый взгляд это сделало бы index-only сканирование бессмысленным, так как проверка видимости требовала бы обращения к heap в любом случае» (11.9). Вот разгадка нашей загадки: иногда — требовала бы.

Карта видимости: выход из тупика

Продолжение 11.9 (дословно): «однако для редко меняющихся данных есть обходной путь. PostgreSQL отслеживает для каждой страницы heap таблицы, все ли строки, хранящиеся на этой странице, достаточно стары, чтобы быть видимыми всем текущим и будущим транзакциям. Эта информация хранится в бите карты видимости таблицы. Index-only сканирование, найдя подходящий элемент индекса, проверяет бит карты видимости соответствующей heap-страницы. Если он установлен, строка известна как видимая, и данные могут быть возвращены без дальнейшей работы. Если он не установлен, должен быть посещён элемент heap, чтобы выяснить, видима ли строка, — так что никакого выигрыша перед обычным индексным сканированием нет». Дешевизна проверки: «поскольку карта видимости в четыре порядка меньше heap, который она описывает, для доступа к ней нужно гораздо меньше физического ввода-вывода. В большинстве ситуаций карта видимости всё время остаётся в кеше». Кто ставит биты — вы знаете из главы 6.7: VACUUM, «поддерживать карту видимости для каждой таблицы, чтобы отслеживать, какие страницы содержат только кортежи, о которых известно, что они видимы всем активным транзакциям» (24.1.4). Поэтому вывод 11.9 (дословно): «index-only сканирование будет выигрышным, только если значительная доля heap-страниц таблицы имеет установленные биты all-visible. Но таблицы, в которых большая часть строк не меняется, достаточно распространены, чтобы сделать этот тип сканирования очень полезным на практике».

В коде бит видимости — это не метафора. Карта видимости — отдельный файл форка рядом с таблицей; на каждую heap-страницу в ней отведено 2 бита: BITS_PER_HEAPBLOCK 2, флаги VISIBILITYMAP_ALL_VISIBLE 0x01 и VISIBILITYMAP_ALL_FROZEN 0x02 (src/include/access/visibilitymapdefs.h на коммите 083ac033419f690758508e08c1736089384bbee8, строки 17–21; второй бит — про заморозку из главы 6.7). Устанавливает биты функция visibilitymap_set (src/backend/access/heap/visibilitymap.c, строка 274); при обычной уборке её вызывает lazy_scan_heap — та самая функция VACUUM из главы 6.7 (src/backend/access/heap/vacuumlazy.c, вызов на строке 1553 внутри цикла по страницам). Проверяет бит сам index-only-узел — ниже.

Демонстрация: Heap Fetches до и после VACUUM

Смотрим отзывы «Войны и мира» (книга 4 — два отзыва, переживших обновление в 6.3; вставка отзыва 17 в 8.1 тоже сделала страницу не полностью видимой). Оговорка о размере: на таблице в одну страницу планировщик выбрал бы Seq Scan, поэтому на время опыта выключаем его — приём из главы 8.2:

SET enable_seqscan = off;

EXPLAIN ANALYZE
SELECT book_id, rating FROM reviews
WHERE book_id = 4;

VACUUM reviews;

EXPLAIN ANALYZE
SELECT book_id, rating FROM reviews
WHERE book_id = 4;
Index Only Scan using reviews_book_rating_idx on reviews
  (cost=0.29..8.31 rows=2 width=8) (actual time=0.020..0.021 rows=2 loops=1)
  Index Cond: (book_id = 4)
  Heap Fetches: 2
Planning Time: 0.116 ms
Execution Time: 0.033 ms
VACUUM
Index Only Scan using reviews_book_rating_idx on reviews
  (cost=0.29..8.31 rows=2 width=8) (actual time=0.018..0.019 rows=2 loops=1)
  Index Cond: (book_id = 4)
  Heap Fetches: 0
Planning Time: 0.110 ms
Execution Time: 0.027 ms

Что выведено и почему: EXPLAIN ANALYZE «заставляет оператор действительно выполниться, а не только спланироваться. Тогда к отображению добавляется фактическая статистика времени выполнения» (/docs/17/sql-explain.html, 43.9.1, перевод дословный). Строка «Heap Fetches: 2» — счётчик обращений к таблице: бит карты видимости на странице с отзывами книги 4 не был установлен (страница пережила обновление из 6.3 и вставку из 8.1, а после VACUUM в 6.7 её снова «испортила» вставка отзыва 17; бит ставит только VACUUM). После VACUUM бит установлен — «данные могут быть возвращены без дальнейшей работы» (11.9), и «Heap Fetches: 0»: таблица не прочитана ни разу. Обратите внимание на время планирования в обоих случаях и на то, что стоимость не изменилась: планировщик не знает заранее, сколько будет heap-обращений, — он видит только данные каталога. Числа actual time у вас будут другими; важны Heap Fetches: N → 0.

Механизм в коде

Узел плана «Index Only Scan» реализован в src/backend/executor/nodeIndexonlyscan.c. Функция выборки — IndexOnlyNext (строка 62). Ключевое решение — в комментарии на строках 127–130: «мы можем пропустить чтение heap, если TID ссылается на heap-страницу, на которой все кортежи известны видимыми всем. В любом случае мы используем индексный кортеж, а не heap-кортеж, как источник данных» (перевод дословный). Проверка бита — макрос VM_ALL_VISIBLE (строки 161–163); если бит не установлен: «чёрт, придётся посетить heap, чтобы проверить видимость» (комментарий на строке 166, далее index_fetch_heap на строке 169). Каждый такой случай увеличивает счётчик ntuples2 через InstrCountTuples2 — и именно он выводится в EXPLAIN как «Heap Fetches» (src/backend/commands/explain.c, строка 1993). Напомним связь с MVCC (глава 6.4): если в параллельной незавершённой транзакции изменилась строка книги 13, то бит сбросится, и ваш запрос честно проверит видимость версии в heap — index-only scan никогда не вернёт строку, невидимую снимку запроса. Данные — из индекса, истина о видимости — из таблицы.

Связь с теорией

«Покрывающий индекс» — классическое понятие теории индексирования: индекс, содержащий все запрошенные атрибуты, избавляет от обращения к данным. В документации PostgreSQL термин covering введён в 11.9; в Silberschatz (7-е изд., гл. 14 Indexing) покрывающим индексам отдельного параграфа в оглавлении главы нет (составным ключам посвящён § 14.6), поэтому за теоретическим разбором отсылаем к курсу CMU. Специфика PostgreSQL, которой нет в классической модели: информация о видимости при многоверсионности живёт только в строках, а не в индексах, поэтому «чистое» чтение из индекса потребовало отдельной структуры — карты видимости — и её поддержки VACUUM. Это хороший пример того, как решение из теории (покрывающий индекс) на практике связано с устройством хранения (глава 7.2) и конкурентностью (глава 6.4). Курс CMU 15-445 обсуждает покрывающие индексы в лекциях #08–09 (Tree Indexes).

Проверь себя

Вопрос 1. Почему для index-only scan недостаточно, чтобы индекс содержал все столбцы запроса? Что ещё проверяет сервер?

Ответ. «Есть дополнительное требование для любого сканирования таблицы в PostgreSQL: оно должно проверять, что каждая извлечённая строка "видима" снимку MVCC запроса... Информация о видимости не хранится в элементах индекса, только в элементах heap» (11.9). Сервер проверяет бит карты видимости страницы: «если он установлен, строка известна как видимая, и данные могут быть возвращены без дальнейшей работы. Если не установлен, должен быть посещён элемент heap» (11.9).

Вопрос 2. В EXPLAIN ANALYZE узла Index Only Scan было «Heap Fetches: 40», после VACUUM стало 0. Что изменилось и почему это ускоряет запрос?

Ответ. VACUUM «поддерживает карту видимости, чтобы отслеживать, какие страницы содержат только кортежи, о которых известно, что они видимы всем активным транзакциям» (24.1.4). До уборки биты не были установлены, и узел для каждого элемента индекса «посещал элемент heap, чтобы выяснить, видима ли строка» (11.9) — 40 раз. После уборки проверки проходят по карте: «карта видимости в четыре порядка меньше heap... В большинстве ситуаций карта видимости всё время остаётся в кеше» (11.9).

Вопрос 3. Таблицу постоянно обновляют и вставляют новые строки. Стоит ли проектировать под неё покрывающий индекс ради index-only scan?

Ответ. Как правило, нет: index-only сканирование «будет выигрышным, только если значительная доля heap-страниц таблицы имеет установленные биты all-visible» (11.9), а при активных изменениях VACUUM не успевает/не может держать биты установленными — почти каждый элемент потребует «посетить элемент heap». Покрывающий индекс приносит пользу таблицам, «в которых большая часть строк не меняется» (11.9): справочникам, архивам, колонкам отчётности.
