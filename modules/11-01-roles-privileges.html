Глава 11.1. Роли, привилегии, владение

Уровень: J · узел карты тем: T50 · PostgreSQL 17.11

Стажёр с паролем

В команде появился стажёр, и ему нужен доступ к базе читательского дневника. Пока все подключались одним суперпользователем — так работало, пока «все» означало одного человека. Теперь вопросы: как завести отдельную учётную запись, как дать ей ровно те права, что нужны для чтения отзывов, и почему нельзя просто раздать всем пароль от postgres. Глава отвечает на них — и вводит модель прав PostgreSQL целиком: роли, привилегии, владение.

Роль: и пользователь, и группа

В PostgreSQL нет отдельных «пользователей» и «групп». Из главы 21 Database Roles (/docs/17/user-manag.html, перевод дословный): «роль может рассматриваться либо как пользователь базы данных, либо как группа пользователей базы данных — в зависимости от настройки роли. Роли могут владеть объектами базы данных (например, таблицами и функциями) и могут назначать привилегии на эти объекты другим ролям, контролируя, кто имеет доступ к каким объектам... Концепция ролей поглощает концепции «пользователей» и «групп». В версиях PostgreSQL до 8.1 пользователи и группы были разными видами сущностей, но теперь есть только роли. Любая роль может действовать как пользователь, как группа или как обе». Где живут роли: «роли базы данных глобальны для всей инсталляции кластера (а не отдельно для каждой базы)» (21.1 /docs/17/database-roles.html). Посмотреть их можно через каталог: «чтобы определить набор существующих ролей, изучите системный каталог pg_roles: SELECT rolname FROM pg_roles; или чтобы увидеть только способных входить в систему: SELECT rolname FROM pg_roles WHERE rolcanlogin» (21.1) — представление pg_roles вы уже встречали в главе 1.3.

Атрибуты роли определяют, чем она может быть. Из 21.2 Role Attributes (/docs/17/role-attributes.html): «только роли с атрибутом LOGIN могут использоваться как начальное имя роли для соединения с базой данных. Роль с атрибутом LOGIN может считаться тем же, что «пользователь базы данных». Чтобы создать роль с правом входа, используйте любое из: CREATE ROLE имя LOGIN; CREATE USER имя; (CREATE USER эквивалентен CREATE ROLE, за исключением того, что CREATE USER по умолчанию включает LOGIN, а CREATE ROLE — нет)». И главное предостережение: «суперпользователь базы данных обходит все проверки прав, кроме права входа. Это опасная привилегия, и её не следует использовать беспечно; лучше выполнять большую часть работы ролью, не являющейся суперпользователем» (21.2). Заводим роль приложения — читателя со стажёрскими задачами:

CREATE ROLE app_reader LOGIN PASSWORD 'learn-sql-11';

Пароль в команде — для учебного примера; в реальности пароли не пишут в скриптах (они попадают в историю shell и в ~/.psql_history) и не хранят в открытом виде — см. методы аутентификации в части IV документации (эксплуатационная тема, вне рамок учебника).

Привилегии: что можно делать с объектом

Теперь роль есть, но прав у неё никаких. Из 5.8 Privileges (/docs/17/ddl-priv.html, далее дословно): «когда объект создаётся, ему назначается владелец. Владелец — обычно роль, выполнившая оператор создания. Для большинства видов объектов начальное состояние таково, что только владелец (или суперпользователь) может делать с объектом что-либо. Чтобы позволить другим ролям использовать его, привилегии должны быть выданы. Существуют разные виды привилегий: SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER, CREATE, CONNECT, TEMPORARY, EXECUTE, USAGE, SET, ALTER SYSTEM и MAINTAIN». Как видно, таблицы из главы 4.1 вы создавали владельцем — и только владелец мог их читать. Особое правило: «право изменять или уничтожать объект присуще владению объектом и не может быть выдано или отозвано само по себе» — то есть GRANT UPDATE не даёт права DROP TABLE. Выдаём права на чтение и добавление отзывов:

GRANT USAGE ON SCHEMA public TO app_reader;
GRANT SELECT, INSERT ON reviews TO app_reader;

SELECT has_table_privilege('app_reader', 'reviews', 'INSERT') AS can_insert,
       has_table_privilege('app_reader', 'reviews', 'UPDATE')  AS can_update;
GRANT
GRANT

 can_insert | can_update
-------------+------------
 t           | f
(1 row)

Что выведено и почему: GRANT выдаёт привилегии, функция has_table_privilege(user, table, privilege) (9.27 /docs/17/functions-info.html) проверяет их без подключения другой сессией: INSERT выдан, UPDATE — нет. USAGE ON SCHEMA нужна, потому что таблица лежит в схеме (глава 4.5): «для схем [USAGE] позволяет доступ к объектам, содержащимся в схеме (при условии, что требования к привилегиям самих объектов также выполнены). По сути это позволяет получателю «находить» объекты внутри схемы» (5.8). Проверка «в бою» — из командной строки, как в главе 1.2:

psql -U app_reader -d bookshelf -c "SELECT count(*) FROM reviews;"
psql (17.11)
Password for user app_reader:
 count
-------
    13
(1 row)
psql -U app_reader -d bookshelf -c "UPDATE reviews SET rating = 5;"
psql (17.11)
Password for user app_reader:
ERROR:  permission denied for table reviews

Что выведено и почему: SELECT прошёл — привилегия SELECT выдана; число 13 — живые отзывы, накопленные к этому моменту (главы 2.8, 4.4, 6.3–6.4, 8.1 и 10.2: мёртвые версии из главы 6.4 SELECT не видит). UPDATE отклонён с ошибкой «permission denied for table reviews» — текст ошибки формирует aclcheck_error в src/backend/catalog/aclchk.c (функция — строка 2705, сообщение «permission denied for table %s» — строка 2804 на коммите 083ac033419f690758508e08c1736089384bbee8). Прежде чем сервер выполнит оператор, он проверяет ACL — список управления доступом; для таблиц он хранится в колонке relacl (aclitem[]) каталога pg_class (src/include/catalog/pg_class.h, строка 134), а проверяет его функция pg_class_aclcheck (aclchk.c, строка 4096), которая читает ACL и возвращает ACLCHECK_OK либо ACLCHECK_NO_PRIV — по последнему и поднимается показанная ошибка.

PUBLIC, WITH GRANT OPTION и отзыв прав

Два уточнения к GRANT. Первое: «специальное имя роли PUBLIC можно использовать, чтобы выдать привилегию каждой роли в системе» (5.8) — удобно для справочных таблиц, опасно для рабочих. Второе: «обычно только владелец объекта (или суперпользователь) может выдавать и отзывать привилегии на объект. Однако можно выдать привилегию «с опцией выдачи» (with grant option), которая даёт получателю право выдавать её в свою очередь другим» (5.8). Отзыв — REVOKE: «чтобы отозвать ранее выданную привилегию, используйте подходяще названную команду REVOKE: REVOKE ALL ON accounts FROM PUBLIC» (5.8); то же в синтаксисе REVOKE для нашей роли — REVOKE INSERT ON reviews FROM app_reader;. Про кадровые изменения: владение переносится командой ALTER TABLE ... OWNER TO ... (5.8), а удалить роль, владеющую объектами, просто так нельзя: «любые объекты, принадлежащие роли, должны быть сначала удалены или переприписаны другим владельцам; и любые права, выданные роли, должны быть отозваны» (21.4 Dropping Roles /docs/17/role-removal.html).

Зачем отдельная роль приложения

Сведём принципы, которые дают эти механизмы. Приложение подключается своей ролью (app_reader), люди — своими; таблицами владеет третья, «хозяйская» роль. Тогда: ротация людей не трогает объекты (DROP ROLE человека не требует переприписи таблиц — 21.); утечка пароля приложения даёт минимум прав (минимальные привилегии — только то, что нужно коду); в pg_stat_activity из главы 7.1 видно, какая роль выполняет запрос, — виновник медленных запросов находится сразу. Где это хранится: роли — в каталоге pg_authid (общем для кластера; поля rolname — «имя роли» — строка 34, rolsuper — «читать это поле только через superuser()» — строка 35, rolcanlogin — «разрешено ли входить как пользователь сессии» — строка 39, rolpassword — «пароль, если есть» — строка 46; src/include/catalog/pg_authid.h, CATALOG(pg_authid) — строка 31), команду CREATE ROLE обрабатывает CreateRole (src/backend/commands/user.c, строка 132).

Связь с теорией

Разграничение доступа — часть теории баз данных: Silberschatz (7-е изд., гл. 4 Intermediate SQL, § 4.7 Authorization, с. 165) вводит именно эту модель — привилегии (authorization) на уровне объектов, роли (вместо пользователей и групп), GRANT/REVOKE и владение как источник прав. PostgreSQL реализует её «ролями, поглощающими пользователей и группы» (глава 21) — та же эволюция, что и в стандарте SQL; уточнения диалекта: ALTER SYSTEM, SET и MAINTAIN в списке привилегий — расширения PostgreSQL. С GRANTED BY тоньше: сама опция есть в стандарте SQL, но там допускает только CURRENT_USER/CURRENT_ROLE, а «остальные варианты являются расширениями PostgreSQL» (Compatibility, sql-grant). Теория доступа на уровне строк (row-level) в Silberschatz не покрывается — это предмет следующей главы (и пометка карты тем: RLS покрывается только документацией).

Проверь себя

Вопрос 1. Чем CREATE ROLE отличается от CREATE USER, и что означает атрибут LOGIN?

Ответ. «CREATE USER эквивалентен CREATE ROLE, за исключением того, что CREATE USER по умолчанию включает LOGIN, а CREATE ROLE — нет» (21.2). LOGIN — «только роли с атрибутом LOGIN могут использоваться как начальное имя роли для соединения с базой данных; роль с атрибутом LOGIN может считаться тем же, что «пользователь базы данных»» (21.2). Роль без LOGIN — кандидат в «группу» (глава 21: «любая роль может действовать как пользователь, как группа или как обе»).

Вопрос 2. Роль имеет GRANT SELECT ON reviews, но получает «permission denied» при чтении. Какие две возможные причины и какая проверка локализует проблему?

Ответ. Причина 1: нет USAGE на схеме — «для схем [USAGE] позволяет доступ к объектам, содержащимся в схеме» (5.8). Причина 2: SELECT выдан не на ту таблицу (другая схема — глава 4.5) или уже отозван. Локализация: SELECT has_table_privilege('роль', 'схема.таблица', 'SELECT') (9.27) — покажет фактическое состояние; текст ошибки «permission denied for table ...» приходит из aclcheck_error (aclchk.c L2705), когда pg_class_aclcheck вернул отказ.

Вопрос 3. Почему нельзя выдать право DROP TABLE через GRANT, и что нужно сделать перед DROP ROLE роли, владеющей таблицей?

Ответ. «Право изменять или уничтожать объект присуще владению объектом и не может быть выдано или отозвано само по себе» (5.8) — уничтожение доступно только владельцу (или суперпользователю, который «обходит все проверки прав» — 21.2). Перед DROP ROLE: «любые объекты, принадлежащие роли, должны быть сначала удалены или переприписаны другим владельцам; и любые права, выданные роли, должны быть отозваны» (21.4); переприись — ALTER TABLE ... OWNER TO (5.8) или REASSIGN OWNED.
