Глава 1.1. Что такое базы данных и реляционная модель

Уровень: J · узел карты тем: T01 · PostgreSQL 17.11

Зачем перекладывать данные из файлов в СУБД

Допустим, вы пишете приложение «читательский дневник»: список книг, авторов, оценки. Первое естественное решение — хранить данные в файлах, например в JSON или CSV. Пока пользователей двое и все записи добавляет ваш код, это работает. Проблемы начинаются, когда данные становятся общими и меняются часто:

  • Противоречия. Ничто не мешает записать две книги с одинаковым идентификатором или сослаться на автора, которого не существует. Каждый клиентский код обязан сам проверять правила — и рано или поздно забывает.
  • Конкурентный доступ. Два одновременно работающих клиента читают и меняют один файл. Кто-то обязательно потеряет чужие изменения.
  • Поиск и структура. Чтобы найти «все книги 2023 года с оценкой выше 4», придётся загрузить и разобрать всё целиком; произвольные запросы — это постоянный ручной код.

Именно эти три класса проблем — целостность, конкурентность, произвольные запросы — и закрывают системы управления базами данных (СУБД): программа берёт на себя хранение данных и правила над ними, а приложения работают с данными через единый интерфейс — язык запросов. Почему такой интерфейс оказался языком таблиц, чем реляционная модель оказалась удобнее файловой кладки — целостность и декларативные запросы вместо процедурного кода, — и какой словарь за ней стоит, — предмет этой главы. Подробное обсуждение мотивации СУБД см. в Silberschatz, Database System Concepts, 7-е изд., глава 1 «Introduction» (раздел «Purpose of Database Systems»); по-русски — Моргунов, PostgreSQL. Основы языка SQL, глава 1.

Модель: данные — это таблицы

PostgreSQL — реляционная СУБД: данные организованы по реляционной модели, предложенной Э. Ф. Коддом (исторический очерк — Silberschatz, Database System Concepts, 7-е изд., глава 1, раздел «History of Database Systems»). Минимальный словарь модели (Silberschatz, 7-е изд., глава 2 «Introduction to the Relational Model»):

В PostgreSQL каждая таблица описана набором столбцов с типами; полный список встроенных типов — в документации «Data Types»: /docs/17/datatype.html. Проектирование «какие таблицы и какие столбцы» — это перевод предметной области на язык отношений; для «читательского дневника» естественны две таблицы:

CREATE TABLE authors (
    author_id  integer  PRIMARY KEY,
    name       text     NOT NULL
);

CREATE TABLE books (
    book_id    integer  PRIMARY KEY,
    title      text     NOT NULL,
    author_id  integer  REFERENCES authors (author_id)
);

Что здесь произошло: мы объявили не только данные, но и правила над ними. Разберём каждое.

Ключи: как модель обеспечивает уникальность и связи

Первичный ключ (PRIMARY KEY) — столбец или набор столбцов, однозначно идентифицирующий строку; именно на него ссылаются внешние ключи других строк и таблиц. Документация формулирует так: «первичный ключ обозначает столбец или группу столбцов, которые могут использоваться как уникальный идентификатор строк таблицы», и для этого значения должны быть уникальны и не равны NULL — раздел «Primary Keys» (5.5.4): /docs/17/ddl-constraints.html. Похожее ограничение UNIQUE (5.5.3 там же) требует уникальности, но допускает NULL; NOT NULL (5.5.2) просто запрещает отсутствующее значение.

Внешний ключ (FOREIGN KEY, 5.5.5 там же) — это ссылка строки одной таблицы на строку другой. Для books.author_id правило звучит так: значение этого столбца обязано существовать среди authors.author_id. Попытка вставить книгу с несуществующим автором будет отклонена сервером — а не вашим кодом. Это и есть главный выигрыш СУБД: правила хранятся вместе с данными и действуют для любого клиента.

Пояснение: что именно проверяет внешний ключ

Внешний ключ проверяет ссылочную целостность: каждой книге — существующий автор. Он не проверяет «осмысленность» ссылки (что автор действительно написал эту книгу) и, в частности, не создаёт индекс на ссылающемся столбце — подробности и последствия для производительности обсуждаются в главе 4.2. Формальное определение ссылочной целостности — Silberschatz, 7-е изд., глава 4 «Intermediate SQL», раздел «Integrity Constraints».

Тонкость: SQL-таблица — не совсем «множество»

В строгой реляционной модели отношение — это множество кортежей: дубликатов нет. SQL (и PostgreSQL) ведёт себя иначе: таблица может содержать одинаковые строки, если никакие ограничения этого не запрещают, и результат запроса без специальных указаний — мультимножество (bag). Это поведение SQL описано в Silberschatz, 7-е изд., глава 3 «Introduction to SQL» (раздел о структуре запросов). Например, если в таблице books три книги одного автора:

SELECT author_id FROM books;

вернёт три строки — по одной на каждую книгу, включая повторы идентификатора. Убрать дубликаты и получить «множество» можно явно, ключевым словом DISTINCT — это документированное поведение списка выборки (раздел 7.3.3 «DISTINCT», /docs/17/queries-select-lists.html):

SELECT DISTINCT author_id FROM books;

Что будет выведено и почему: первый запрос выводит значение author_id для каждой строки таблицы — повторов не избегает никто, раз их в данных три, их и будет три; второй сворачивает одинаковые значения в одну строку, потому что DISTINCT сравнивает строки результата и отбрасывает точные дубликаты. Сравнение здесь — по значению; забегая вперёд: сравнение с NULL (в том числе NULL = NULL) возвращает не TRUE/FALSE, а NULL — это трёхзначная логика SQL, о ней подробно в главе 2.1; описание NULL-семантики в документации — «Comparison Operators»: /docs/17/functions-comparison.html.

Что даёт модель разработчику

Реляционная модель — это контракт: таблица с объявленными типами, ключами и связями описывает инварианты данных, которые сервер охраняет при любом способе записи. Разработчику это значит: проверка «существует ли автор», «уникален ли идентификатор» не размазывается по коду приложений, а исполняется в одном месте. Плата за это — данные надо проектировать: думать о ключах и связях заранее. Этим мы займёмся всерьёз в модуле 4 (нормализация); сейчас достаточно держать в голове таблицу терминов выше.

Проверь себя

Вопрос 1. В таблице без ограничений дважды вставили полностью одинаковую строку. Нарушило ли это реляционную модель? Нарушило ли это PostgreSQL?

Ответ. Реляционную модель — да: отношение — множество кортежей, дубликат в нём невозможен (Silberschatz, 7-е изд., гл. 2). PostgreSQL — нет: SQL-таблица без ключей/уникальности допускает одинаковые строки, результат выборки ведёт себя как мультимножество; чтобы получить «множество», в запросе указывают DISTINCT (/docs/17/queries-select-lists.html, раздел DISTINCT).

Вопрос 2. Что произойдёт при попытке вставить строку в books со значением author_id, которого нет в authors?

Ответ. Сервер отклонит операцию ошибкой: внешний ключ books.author_id REFERENCES authors (author_id) требует, чтобы ссылаемое значение существовало (ссылочная целостность). Это поведение описано в разделе «Foreign Keys» документации: /docs/17/ddl-constraints.html.

Вопрос 3. Чем PRIMARY KEY отличается от просто UNIQUE + NOT NULL на практике и зачем первичный ключ нужен вообще?

Ответ. По ограничениям PK сводится к уникальности + NOT NULL (раздел 5.5.4 /docs/17/ddl-constraints.html). Смысл первичного ключа — объявить канонический способ адресации строки: на него удобно ссылаться внешними ключами из других таблиц, и модель данных фиксирует, что строка идентифицируется именно этим набором столбцов. Формально — это выбранный «потенциальный ключ» (candidate key); теория — Silberschatz, 7-е изд., гл. 2 (раздел о ключах).
