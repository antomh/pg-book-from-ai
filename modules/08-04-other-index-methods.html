Глава 8.4. Другие методы: hash, GIN, GiST, SP-GiST, BRIN

Уровень: J+ · узел карты тем: T40 · PostgreSQL 17.11

Три запроса, с которыми B-tree не справляется

B-tree из главы 8.1 ускоряет сравнения по порядку сортировки. Но дневнику чтения нужны и другие запросы. Первый: «книги с тегом "классика"», где теги — массив (tags @> ARRAY['классика']) — B-tree по массиву целиком сравнивает весь массив, а не наличие элемента. Второй: «десять ближайших к заданной точке» — поиск не по равенству и не по диапазону, а по расстоянию. Третий: гигантская таблица событий, где значение времени растёт вместе с номером страницы — B-tree по такому столбцу огромен, а выигрыш сомнителен. Для таких случаев в PostgreSQL есть другие методы доступа: «PostgreSQL предоставляет несколько типов индексов: B-tree, Hash, GiST, SP-GiST, GIN и BRIN... Каждый тип индекса использует другой алгоритм, лучше всего подходящий к разным типам индексируемых условий. По умолчанию команда CREATE INDEX создаёт B-tree индексы, которые подходят для большинства типичных ситуаций. Другие типы индексов выбираются написанием ключевого слова USING, за которым следует имя типа индекса» (11.2 /docs/17/indexes-types.html, перевод дословный).

Hash: только равенство

Самый простой альтернативный метод: «Hash индексы хранят 32-битный хеш-код, вычисленный из значения индексированного столбца. Следовательно, такие индексы могут обрабатывать только простые сравнения на равенство. Планировщик запросов рассмотрит использование hash индекса, когда индексированный столбец участвует в сравнении с оператором =» (11.2.2, дословно). Устройство — хеш-таблица на страницах: «hash индекс состоит из двух или более "корзин" (buckets), в которые кортежи помещаются всякий раз, когда их хеш-ключ отображается на номер корзины. Отображение ключа в номер корзины выбрано так, чтобы индекс мог наращиваться инкрементально. Когда к индексу добавляется новая корзина, ровно одна существующая корзина должна быть "разделена" (split), и часть её кортежей переносится в новую корзину» (src/backend/access/hash/README на коммите 083ac033419f690758508e08c1736089384bbee8, перевод дословный). Обратите внимание на два практических следствия: по хеш-коду нельзя искать диапазон (порядок теряется), и «в настоящее время уникальным может быть объявлен только B-tree индекс» (11.6 — цитата из главы 8.1). Поэтому равенство B-tree тоже обслуживает, а hash остаётся нишевым методом.

GIN: инвертированный индекс для составных значений

Главный герой для первого запроса: «GIN индексы — это "инвертированные индексы", подходящие для значений данных, которые содержат несколько составляющих значений, таких как массивы. Инвертированный индекс содержит отдельную запись для каждого составляющего значения и может эффективно обрабатывать запросы, проверяющие наличие конкретных составляющих значений» (11.2.5, дословно). Расшифровка имени и механика — из README модуля: «Gin расшифровывается как Generalized Inverted Index... Инвертированный индекс — структура, хранящая множество пар (ключ, список вхождений), где "список вхождений" (posting list) — множество heap-строк, в которых ключ встречается... GIN индекс состоит из B-tree индекса, построенного по значениям ключей, где каждый ключ — элемент некоторого индексируемого объекта (элемент массива, лексема для tsvector)» (src/backend/access/gin/README, перевод дословный). Стандартные классы операторов включают GIN для массивов с операторами <@ @> = && (11.2.5; смысл операторов массивов — 9.19). Демонстрация на тегах книг:

CREATE TABLE book_tags (
    book_id integer REFERENCES books,
    tags     text[] NOT NULL
);

INSERT INTO book_tags VALUES
    (1,  ARRAY['классика', 'стихи']),
    (4,  ARRAY['классика', 'роман']),
    (6,  ARRAY['фантастика']);

CREATE INDEX book_tags_tags_idx ON book_tags USING gin (tags);

-- учебный приём из главы 8.2: на трёх строках планировщик
-- выбрал бы Seq Scan
SET enable_seqscan = off;

EXPLAIN SELECT * FROM book_tags
WHERE tags @> ARRAY['классика'];
CREATE TABLE
INSERT 0 3
CREATE INDEX
                              QUERY PLAN
----------------------------------------------------------------
 Bitmap Heap Scan on book_tags  (cost=12.05..15.61 rows=2 width=64)
   Recheck Cond: (tags @> '{классика}'::text[])
   -> Bitmap Index Scan on book_tags_tags_idx  (cost=0.00..12.04 rows=2 width=0)
         Index Cond: (tags @> '{классика}'::text[])
(5 rows)

Что выведено и почему: план двухуровневый — «Bitmap Index Scan» по GIN-индексу и «Bitmap Heap Scan» по таблице. Это общий механизм комбинирования: «чтобы объединить несколько индексов, система сканирует каждый нужный индекс и готовит в памяти битовую карту, дающую расположения строк таблицы, которые сообщаются как соответствующие условиям этого индекса» (11.5 /docs/17/indexes-bitmap-scans.html, перевод дословный). GIN находит по ключу «классика» список строк (книги 1 и 4), и heap-страницы читаются по битовой карте. Оговорка о размере: три строки — одна страница, поэтому без SET enable_seqscan = off (учебный приём из главы 8.2) планировщик честно выбрал бы Seq Scan; числа cost «ненастоящие» в том смысле, что реальный выбор для такой таблицы — последовательное сканирование. «Recheck Cond» — перепроверка условия по самой строке: некоторые классы операторов GIN возвращают «шумовые» кандидаты и требуют проверки. Числа cost зависят от статистики. GIN-индексы применимы и к jsonb (оператор @> «содержит», глава 3.5), и к полнотекстовому поиску по tsvector — это отдельные большие темы (за пределами учебника).

GiST и SP-GiST: инфраструктуры для геометрии и kNN

Для второго запроса — «десять ближайших» — нужны GiST или SP-GiST. «GiST индексы — это не один вид индекса, а скорее инфраструктура, внутри которой могут быть реализованы различные стратегии индексации. Соответственно, конкретные операторы, с которыми может использоваться GiST индекс, зависят от стратегии индексации (класса операторов). Например, стандартная поставка PostgreSQL включает классы операторов GiST для нескольких двумерных геометрических типов данных» (11.2.3, дословно). Соседство ищется так: «GiST индексы также способны оптимизировать поиски "ближайшего соседа", такие как SELECT * FROM places ORDER BY location <-> point '(101,456)' LIMIT 10; который находит десять мест, ближайших к заданной целевой точке» (11.2.3, дословно). Возможность «зависит от конкретного используемого класса операторов» (11.2.3) — расстояние <-> поддерживают геометрические типы вроде point. Внутри — обобщённое дерево поиска: «GiST расшифровывается как Generalized Search Tree. Это сбалансированный древовидный метод доступа, который служит базовым шаблоном, в котором реализуются произвольные схемы индексирования» (/docs/17/gist.html, 64.2, дословно).

SP-GiST — родственник с другой организацией страниц: «SP-GiST — сокращение от space-partitioned GiST. SP-GiST поддерживает деревья поиска с разделением пространства, которые облегчают разработку широкого диапазона различных несбалансированных структур данных, таких как квадродеревья, k-d деревья и радиксные деревья (tries). Общая черта этих структур — они многократно делят пространство поиска на разделы, которые не обязаны быть равного размера» (64.3.1 /docs/17/spgist.html, дословно). Как и GiST, «SP-GiST поддерживает поиски "ближайшего соседа"» (11.2.4). Отличие от B-tree принципиально: разделение по пространству значений, а не по порядку сортировки — поэтому SP-GiST полезен для точек, префиксов IP-адресов, путей.

BRIN: сводки по диапазонам страниц

Третий запрос — события, растущие вместе со страницами. «BRIN индексы (сокращение от Block Range INdexes) хранят сводки о значениях, хранящихся в последовательных физических диапазонах блоков таблицы. Поэтому они наиболее эффективны для столбцов, чьи значения хорошо коррелируют с физическим порядком строк таблицы. Для типов данных с линейным порядком сортировки индексируемые данные соответствуют минимальному и максимальному значениям столбца для каждого диапазона блоков» (11.2.6, дословно). Идея из README модуля: «существенная идея BRIN индекса — отслеживать обобщающие значения в последовательных группах heap-страниц (диапазонах страниц); например, минимум и максимум... Эти значения могут использоваться, чтобы не сканировать такие страницы при сканировании таблицы, в зависимости от условий запроса» (src/backend/access/brin/README, перевод дословный). Плата за компактность: «цена этого — необходимость обновлять хранимые сводные значения каждого диапазона страниц при вставке кортежей в них» (там же). Для таблицы событий, где время только растёт, диапазонные сводки почти всегда точны и крошечны по сравнению с B-tree:

CREATE TABLE access_log (
    reader_id integer,
    at        timestamptz NOT NULL
);

CREATE INDEX access_log_at_brin_idx ON access_log USING brin (at);
CREATE TABLE
CREATE INDEX

Что произошло: индекс создан; на такой таблице запрос WHERE at >= '2026-11-01' получил бы Seq Scan (таблица только что создана и пуста), а на большой лог-таблице, где строки дописываются в конец, — план Bitmap Heap Scan с BRIN-условием — по сводкам «минимум–максимум на диапазон страниц» планировщик отбрасывает диапазоны, где нужных значений быть не может. Если же значения столбца разбросаны по страницам случайно, «наиболее эффективны для столбцов, чьи значения хорошо коррелируют с физическим порядком» (11.2.6) — BRIN превращается в полный перебор сводок без отбрасывания. Итоговая шпаргалка по выбору метода: равенство или диапазон по сортируемому столбцу — B-tree; «наличие элемента» в массиве/jsonb — GIN; геометрия и kNN — GiST/SP-GiST; гигантская таблица с естественно упорядоченным столбцом — BRIN; чистое равенство без диапазонов — hash (нишевый).

Связь с теорией

Все пять методов — персонажи учебной теории индексирования (Silberschatz, 7-е изд., гл. 14): хеш-индексы — § 14.5 Hash Indices (хеш-корзины и разделение корзин из README соответствуют классической схеме); инвертированные индексы для составных значений и битовые карты — § 14.9 Bitmap Indices и обсуждение индексов для составных ключей; пространственные индексы — § 14.10 Indexing of Spatial and Temporal Data (kNN-поиск и деревья разбиения пространства). Книга «PostgreSQL изнутри» (Ч. V) разбирает эти же методы доступа применительно к реализации PostgreSQL; детали главы сверены с документацией 11.2 и README-файлами модулей на базовом коммите. Замечание о диалекте: USING с методами GIN/GiST/SP-GiST/BRIN и их операторы — расширения PostgreSQL; в других СУБД аналоги называются иначе (частичные индексы из 8.2 — тоже диалектная черта).

Проверь себя

Вопрос 1. Запрос WHERE tags @> ARRAY['детектив'] по столбцу text[]. Почему B-tree по tags не поможет и что выбрать?

Ответ. B-tree сравнивает значения как единое целое по порядку сортировки — «может обрабатывать запросы равенства и диапазона для данных, которые можно отсортировать» (11.2.1), а «наличие элемента» в массиве — не такое сравнение. Нужен GIN: «инвертированный индекс содержит отдельную запись для каждого составляющего значения и может эффективно обрабатывать запросы, проверяющие наличие конкретных составляющих значений» (11.2.5); для массивов — операторы <@ @> = && (11.2.5).

Вопрос 2. Чем BRIN индекс по столбцу at (время события) отличается от B-tree по тому же столбцу, и когда он проигрывает?

Ответ. BRIN «хранит сводки о значениях в последовательных физических диапазонах блоков... минимум и максимум для каждого диапазона блоков» (11.2.6) — крошечный, но неточный: отбрасывает только целые диапазоны страниц. Проигрывает, когда значения «не хорошо коррелируют с физическим порядком строк таблицы» (11.2.6): в каждый диапазон попадают все возможные значения, и сводки не отбрасывают ничего. B-tree указывает на каждую строку точно, но и весит сопоставимо с данными.

Вопрос 3. Что общего у GiST и SP-GiST и почему для ORDER BY location <-> point '(101,456)' LIMIT 10 не годится B-tree?

Ответ. Оба — «инфраструктура... внутри которой могут быть реализованы различные стратегии индексации» (11.2.3, для SP-GiST — 11.2.4: «предлагают инфраструктуру, поддерживающую различные виды поиска»); оба поддерживают kNN. B-tree не годится, потому что запрос упорядочивает не по значению столбца, а по расстоянию: B-tree «выдаёт отсортированный вывод» только по порядку сортировки столбца (11.4), а «ближайшие» требует расстояния до точки — GiST-классы операторов умеют обходить дерево по возрастанию расстояния и остановиться на первых 10 строках (11.2.3: «находит десять мест, ближайших к заданной целевой точке»).
