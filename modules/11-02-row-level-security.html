Глава 11.2. Row-Level Security

Уровень: J+ · узел карты тем: T51 · PostgreSQL 17.11

Фильтр, который забыли написать

В читательском дневнике появилась таблица личных заметок: каждый пишет записи для себя, и все записи лежат в одной таблице. Привилегии из главы 11.1 работают на уровне объекта: GRANT SELECT ON notes TO app_reader открывает всю таблицу. Фильтр «только свои строки» до сих пор писали в приложении: WHERE owner = current_user. В одном из отчётов фильтр забыли — и каждый увидел чужие заметки. Ошибка не в коде одного отчёта, а в архитектуре: правило «каждый видит только свои строки» должно жить в базе, где его нельзя обойти забывчивым SQL. Это и есть Row-Level Security.

Политики безопасности строк

Определение из 5.9 Row Security Policies (/docs/17/ddl-rowsecurity.html, перевод дословный): «в дополнение к стандартной SQL системе привилегий, доступной через GRANT, таблицы могут иметь политики безопасности строк, ограничивающие, в расчёте на пользователя, какие строки могут возвращаться обычными запросами или вставляться, обновляться и удаляться командами модификации данных. Эта возможность также известна как Row-Level Security. По умолчанию у таблиц нет никаких политик, так что если пользователь имеет привилегии доступа к таблице согласно системе привилегий SQL, все строки в ней одинаково доступны для запросов или обновлений. Когда row security включена на таблице (с помощью ALTER TABLE ... ENABLE ROW LEVEL SECURITY), весь обычный доступ к таблице для выбора строк или изменения строк должен быть разрешён политикой безопасности строк. (Однако владелец таблицы обычно не подчиняется политикам безопасности строк.) Если для таблицы не существует политик, используется политика запрета по умолчанию (default-deny), означающая, что ни одна строка не видна и не может быть изменена». И важная граница: «операции, применяемые ко всей таблице, такие как TRUNCATE и REFERENCES, не подчиняются row security» — RLS про строки, а не про таблицу.

Готовим данные. Две роли-читателя и таблица заметок (роли без LOGIN подключаться не могут, но переключиться на них можно: «текущий пользователь сессии должен иметь опцию SET для указанного role_name... (если пользователь сессии — суперпользователь, может быть выбрана любая роль)» — SET ROLE, /docs/17/sql-set-role.html):

CREATE ROLE alice;
CREATE ROLE bob;

CREATE TABLE notes (
    note_id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    owner      text NOT NULL DEFAULT current_user,
    body       text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);

INSERT INTO notes (owner, body) VALUES
    ('alice', 'Перечитать Онегина'),
    ('bob',   'Не соглашаться на седьмую главу');

GRANT SELECT, INSERT, UPDATE ON notes TO alice, bob;

Здесь current_user — функция из 9.27, «возвращает имя пользователя текущего контекста исполнения» (/docs/17/functions-info.html). Последний GRANT обязателен: таблицу создал суперпользователь, и без выдачи привилегий (глава 11.1) роли alice и bob получили бы permission denied for table notes ещё до проверок RLS — политики наслаиваются на привилегии, а не заменяют их. Политика и её включение:

CREATE POLICY notes_isolation ON notes
    USING (owner = current_user)
    WITH CHECK (owner = current_user);

ALTER TABLE notes ENABLE ROW LEVEL SECURITY;

Разбор синтаксиса по CREATE POLICY (/docs/17/sql-createpolicy.html, далее дословно). Про включение: «обратите внимание, что row-level security должна быть включена на таблице (с помощью ALTER TABLE ... ENABLE ROW LEVEL SECURITY), чтобы созданные политики применялись». Про два выражения: «существующие строки таблицы проверяются против выражения USING, тогда как новые строки, которые будут созданы через INSERT или UPDATE, проверяются против выражения WITH CHECK. Когда выражение USING возвращает true для данной строки, эта строка видна пользователю; если же возвращается false или null, строка не видна. Обычно ошибки при невидимой строке не возникает... Когда выражение WITH CHECK возвращает true для строки, строка вставляется или обновляется; если же false или null — возникает ошибка». Если WITH CHECK не задан, «выражение USING используется и для определения того, какие строки видимы (обычный случай USING), и какие новые строки будут разрешены к добавлению (случай WITH CHECK)». По умолчанию политика применяется ко всем командам и ролям: «по умолчанию для вновь созданных политик — они применяются ко всем командам и ролям, если не указано иное».

Проверка изоляции

SET ROLE alice;
SELECT note_id, owner, body FROM notes;

INSERT INTO notes (owner, body) VALUES ('bob', 'Записка от имени Боба');
UPDATE notes SET body = 'перехвачено' WHERE owner = 'bob';
SET
 note_id | owner |        body
---------+-------+---------------------
       1 | alice | Перечитать Онегина
(1 row)

ERROR:  new row violates row-level security policy "notes_isolation" for table "notes"
UPDATE 0

Что выведено и почему: после SET ROLE alice функция current_user возвращает alice (9.27), и SELECT показал только её заметку — строка Боба отфильтрована выражением USING без всякой ошибки. INSERT с owner = 'bob' прошёл проверку WITH CHECK ('bob' = 'alice' — false) и упал с ошибкой «new row violates row-level security policy "notes_isolation" for table "notes"». UPDATE чужой строки молча обновил ноль строк: USING скрыл её ещё до поиска. Точное сообщение ошибки берётся из ExecWithCheckOptions (src/backend/executor/execMain.c, сигнатура — строка 2094; errmsg «new row violates row-level security policy "%s" for table "%s"» — строка 2196 на коммите 083ac033419f690758508e08c1736089384bbee8; тот же формат сообщения показывают тесты регрессии, src/test/regress/expected/rowsecurity.out, строки 358–361).

Вернуть себе полную роль — RESET ROLE;. И крайний случай для проверки понимания: если на таблице с включённой RLS нет ни одной политики, действует default-deny — «ни одна строка не видна и не может быть изменена» (5.9): не «видно всё», как подсказывает интуиция, а наоборот.

Кто обходит политики

Из 5.9 (дословно): «суперпользователи и роли с атрибутом BYPASSRLS всегда обходят систему безопасности строк при доступе к таблице. Владельцы таблиц обычно тоже обходят row security, хотя владелец таблицы может выбрать подчинение политикам row security с помощью ALTER TABLE ... FORCE ROW LEVEL SECURITY. Включение и выключение row security, как и добавление политик к таблице, — всегда привилегия только владельца таблицы». Поэтому в демо мы работали через SET ROLE: таблицей notes владеет создавшая её роль (раздел 5.8 — «владелец — обычно роль, выполнившая оператор создания»), и на него политики не действуют. Политики — диалект PostgreSQL: в стандарте SQL разграничение доступа до строк не определено (в Silberschatz этой темы нет; согласно карте тем модуля тема покрывается документацией PostgreSQL).

Как это исполняется

Политики применяются на станции перезаписи запроса — той самой, что раскрывает представления (глава 9.1). В src/backend/rewrite/rewriteHandler.c внутри функции fireRIRrules (строка 2019) для каждой таблицы запроса вызывается get_row_security_policies (строка 2246). Сначала решается, применима ли RLS вообще: это делает check_enable_rls — «определить, основываясь на отношении, настройке row_security и текущей роли, применима ли RLS к этому запросу» (комментарий в src/backend/utils/misc/rls.c, функция на строке 52; в PostgreSQL 17 она живёт в этом файле). Затем get_row_security_policies (src/backend/rewrite/rowsecurity.c, строка 98) выбирает подходящие политики (get_policies_for_relation, строка 541) и присоединяет их к запросу двумя способами: add_security_quals (строка 700) превращает выражения USING в условия фильтрации строк, а add_with_check_options (строка 796) — выражения WITH CHECK в проверки новых строк. Первые исполняются как обычные условия при выборке; вторые — в момент модификации: ExecWithCheckOptions вызывается из исполнительного цикла UPDATE/INSERT для каждой новой строки (src/backend/executor/nodeModifyTable.c, строки 1018–1019). Отсюда порядок из документации: «для INSERT, UPDATE и MERGE выражения WITH CHECK принудительно применяются после срабатывания BEFORE-триггеров и до любых реальных модификаций данных» (CREATE POLICY) — то, что BEFORE-триггер из главы 10.3 успевает изменить строку до политики. И про видимость: «это выражение вычисляется для каждой строки до любых условий или функций, пришедших из запроса пользователя. (Единственные исключения из этого правила — leakproof-функции, которые гарантированно не протекают информацией; оптимизатор может применить такие функции до проверки row-security)» (5.9) — пометка LEAKPROOF из главы 10.1 защищает и здесь.

Связь с теорией

Мандатное и дискреционное управление доступом — классификация из теории безопасности баз данных: GRANT/REVOKE из главы 11.1 — дискреционная модель (Silberschatz, 7-е изд., § 4.7 Authorization). Row-Level Security — средство тонкой настройки той же модели до уровня строк: правило доступа переносится из приложения внутрь СУБД и проверяется при перезаписи каждого запроса. В стандартных учебниках (Silberschatz) эта техника не разбирается — материал главы целиком опирается на документацию PostgreSQL и исходный код; для практики этого достаточно: политика, включение RLS и понимание, где проверка исполняется, — полный junior+-набор.

Проверь себя

Вопрос 1. Чем USING отличается от WITH CHECK в политике, и что произойдёт, если задать только USING?

Ответ. «Существующие строки таблицы проверяются против выражения USING, тогда как новые строки, которые будут созданы через INSERT или UPDATE, проверяются против выражения WITH CHECK» (CREATE POLICY). Невидимая строка (USING = false/null) просто скрыта, а провал WITH CHECK — ошибка. Если WITH CHECK не задан, «выражение USING используется и для определения того, какие строки видимы, и какие новые строки будут разрешены к добавлению» (CREATE POLICY) — в демо это означало бы запрет вставлять чужие заметки тем же условием owner = current_user.

Вопрос 2. На таблице выполнены ENABLE ROW LEVEL SECURITY и CREATE POLICY ... TO alice. Что увидит роль bob, имеющая GRANT SELECT, и что будет, если политик нет вовсе?

Ответ. Роль bob не входит в перечисленные роли политики — применимых к нему политик нет, и действует default-deny: «если политик для таблицы не существует, используется политика запрета по умолчанию, означающая, что ни одна строка не видна и не может быть изменена» (5.9). То же верно и для таблицы с включённой RLS без единой политики: пустой результат, а не «всё видно». Привилегия SELECT из главы 11.1 остаётся необходимой — «весь обычный доступ... должен быть разрешён политикой» поверх неё (5.9).

Вопрос 3. На каком этапе обработки запроса применяются политики и какие две конструкции они порождают в запросе?

Ответ. На станции перезаписи (глава 9.1): fireRIRrules (rewriteHandler.c L2019) вызывает get_row_security_policies (L2246), применимость решает check_enable_rls (rls.c L52). Политики превращаются в security quals — условия фильтрации строк для USING (add_security_quals, rowsecurity.c L700) — и в with-check options — проверки новых строк для WITH CHECK (add_with_check_options, L796); последние исполняет ExecWithCheckOptions (execMain.c L2094), вызываемый из nodeModifyTable.c (L1018–1019).
