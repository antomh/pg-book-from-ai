Глава 10.4. Процедуры и CALL

Уровень: J+ · узел карты тем: T49 · PostgreSQL 17.11

Удаление, которое нельзя остановить

Раз в месяц из читательского дневника надо удалять отзывы старше года. Отзывов миллионы, и удалять их одним DELETE нельзя: транзакция вырастет до гигабайт WAL (глава 6.1), заблокирует строки на часы и при откате вернёт всё назад. Нужны циклы: удалить порцию — закрепить — удалить следующую. То есть DELETE... COMMIT... DELETE... COMMIT. В функции так нельзя: «(вы не можете использовать команды управления транзакциями, например COMMIT, SAVEPOINT, и некоторые служебные команды, например VACUUM, в SQL-функциях)» (36.5 /docs/17/xfunc-sql.html). Для этого в PostgreSQL есть отдельный объект — процедура (в списке поддерживаемых версий документации CALL самая старая — 11).

Процедура: то же, но с транзакциями

Синтаксис зеркален CREATE FUNCTION, но вызов — отдельная команда CALL: «CALL выполняет процедуру» (CALL, /docs/17/sql-call.html). Процедура чистки порциями:

CREATE PROCEDURE purge_old_reviews(p_days int)
LANGUAGE plpgsql
AS $$
BEGIN
    LOOP
        DELETE FROM reviews
        WHERE review_id IN (
            SELECT review_id
            FROM reviews
            WHERE created_at < now() - p_days * interval '1 day'
            LIMIT 1000
        );
        COMMIT;
        EXIT WHEN NOT FOUND;
    END LOOP;
END;
$$;

CALL purge_old_reviews(365);
CALL

Что выведено и почему: CALL выполнил процедуру, и psql подтвердил выполнение (таблица reviews в наших главах мала — удалится не более чем всё, что старше года, за один проход цикла). Как это работает: LOOP и EXIT WHEN — из 41.6.5 (глава 10.2); подзапрос с LIMIT 1000 отбирает порцию строк для удаления; после DELETE переменная FOUND установлена («UPDATE, INSERT, DELETE и MERGE устанавливают FOUND в true, если затронута хотя бы одна строка», 41.5.5), поэтому EXIT WHEN NOT FOUND завершит цикл, когда порции иссякнут. Главное здесь — COMMIT внутри тела: «в процедурах, вызываемых командой CALL, а также в анонимных блоках кода (команда DO), можно завершать транзакции командами COMMIT и ROLLBACK. Новая транзакция запускается автоматически после завершения транзакции этими командами, так что отдельной команды START TRANSACTION нет» (41.8 Transaction Management /docs/17/plpgsql-transactions.html, перевод дословный). Каждая итерация — короткая транзакция: WAL фиксируется порциями, блокировки не копятся, откат теряет только последнюю порцию.

Чем процедура отличается от функции

Сведём различия, каждое — по первоисточнику:

  • Вызов. Функция вызывается в выражениях — SELECT rate_book(...), в WHERE, в индексных выражениях (глава 8.2). Процедура — только командой CALL: «чтобы вызвать функцию (не процедуру), используйте SELECT» (CALL, Notes). Если написать SELECT purge_old_reviews(365);, сервер отклонит:
SELECT purge_old_reviews(365);
ERROR:  purge_old_reviews(integer) is a procedure
LINE 1: SELECT purge_old_reviews(365);
               ^
HINT:  To call a procedure, use CALL.

Что выведено и почему: разбор выражения в SELECT встретил объект pg_proc с prokind = 'p' и не-вызов CALL; ошибка формируется в src/backend/parser/parse_func.c: errmsg «%s is a procedure» (строка 297) и errhint «To call a procedure, use CALL.» (строка 301) на коммите 083ac033419f690758508e08c1736089384bbee8.

  • Транзакции. Функция всегда исполняется внутри транзакции вызвавшего её оператора (глава 6.1) и «вы не можете использовать команды управления транзакциями... в SQL-функциях» (36.5); PL/pgSQL-функции — то же ограничение: «управление транзакциями возможно только при вызовах CALL или DO с верхнего уровня или во вложенных вызовах CALL или DO без каких-либо промежуточных команд» (41.8). Процедура, вызванная с верхнего уровня, может COMMIT/ROLLBACK (41.8). При этом есть ограничение вызова: «если CALL выполняется в блоке транзакции, то вызванная процедура не может выполнять команды управления транзакциями. Команды управления транзакциями разрешены, только если CALL выполняется в собственной транзакции» (CALL, Notes) — то есть BEGIN; CALL purge_old_reviews(365); ... с COMMIT внутри процедуры не сработает.
  • Результат. Функция возвращает значение в выражении (RETURNS, глава 10.1); у процедуры выходных значений в выражении нет — «если процедура имеет выходные параметры, то будет возвращена строка результата, содержащая значения этих параметров» (CALL), не более того. Для массовых операций это и не нужно: результат purge_old_reviews — изменение данных, а не значение.

Как это устроено внутри

Хранение единообразно: и функции, и процедуры — строки каталога pg_proc (глава 10.1), различает колонка prokind: «f» для функции, «p» для процедуры (PROKIND_FUNCTION 'f'/ PROKIND_PROCEDURE 'p', pg_proc.h, строки 151 и 154). Даже парсер почти не различает их: грамматика CREATE PROCEDURE строит тот же узел CreateFunctionStmt с флагом is_procedure = true (gram.y, строка 8307; у CREATE FUNCTION флаг ложен — строки 8264, 8278, 8293), а обрабатывает обе команды CreateFunction (functioncmds.c, строка 1011). По-настоящему расходятся пути исполнения: SELECT с функцией уходит в план запроса (глава 9.1), а CALL — служебная команда: в src/backend/tcop/utility.c оператор T_CallStmt (строка 850) вызывает ExecuteCallStmt (строка 851), определённую в functioncmds.c (строка 2188). Ключ к транзакциям — параметр «atomic»: «когда ExecuteCallStmt() вызывается с верхнего уровня, мы передаём atomic = false (напомним: это означает транзакции = да). Затем мы создаём узел CallContext с содержимым atomic = false, который передаётся в поле fcinfo->context вызову процедуры. Реализация языка должна затем принять соответствующие меры, чтобы разрешить или запретить команды транзакций, основываясь на этой информации, например вызвать SPI_connect_ext(SPI_OPT_NONATOMIC)» (комментарий в functioncmds.c, строки 2172–2176, перевод дословный). Именно поэтому COMMIT работает в процедуре с верхнего уровня и запрещён внутри функции: PL/pgSQL проверяет атомарность контекста вызова.

Связь с теорией

Разделение «функция вычисляется в выражении, процедура вызывается отдельно» — из стандарта SQL и учебников: Silberschatz (7-е изд., гл. 5, § 5.2 Functions and Procedures, с. 198) проводит ту же границу: функции возвращают значение и вызываются в выражениях SQL, процедуры выполняются отдельной командой и нужны для действий. Управление транзакциями внутри процедур в стандарте описано иначе (SQL/PSM), и реализация PostgreSQL через CALL/DO с неатомарным контекстом — диалектное решение. Практический ориентир этой главы: транзакционные batch-операции — процедуре, вычисления — функции, простые запросы — SQL-функции (глава 10.1).

Проверь себя

Вопрос 1. Почему purge_old_reviews нельзя написать функцией? Что говорит документация о командах управления транзакциями в SQL-функциях?

Ответ. Функции исполняются внутри транзакции вызвавшего оператора, и «вы не можете использовать команды управления транзакциями, например COMMIT, SAVEPOINT... в SQL-функциях» (36.5). Порционная чистка требует завершать транзакцию после каждой порции — это умеют только процедуры (и DO): «в процедурах, вызываемых командой CALL... можно завершать транзакции командами COMMIT и ROLLBACK» (41.8).

Вопрос 2. Что произойдёт при BEGIN; CALL purge_old_reviews(365); — и почему тот же вызов без BEGIN работает?

Ответ. С явным BEGIN вызов CALL попадает «в блок транзакции», и «вызванная процедура не может выполнять команды управления транзакциями» (CALL, Notes) — COMMIT внутри тела завершится ошибкой. Без BEGIN CALL выполняется «в собственной транзакции» (CALL, Notes): ExecuteCallStmt передаёт atomic = false (functioncmds.c L2172–2176), и PL/pgSQL разрешает COMMIT; новая транзакция стартует автоматически после каждого COMMIT (41.8).

Вопрос 3. Как сервер отличает процедуру от функции при хранении и при вызове SELECT?

Ответ. Хранение общее — каталог pg_proc, различает prokind: 'f' — функция, 'p' — процедура (pg_proc.h L151/L154); CREATE PROCEDURE парсится в тот же CreateFunctionStmt с is_procedure = true (gram.y L8307). При SELECT над процедурой разбор выражения отвергает её: errmsg «%s is a procedure» и errhint «To call a procedure, use CALL.» (parse_func.c L297, L301). CALL же идёт служебным путём: T_CallStmt → ExecuteCallStmt (utility.c L850–851, functioncmds.c L2188).
