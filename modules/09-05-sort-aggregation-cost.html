Глава 9.5. Сортировка, агрегация и стоимость

Уровень: J+ · узел карты тем: T45 · PostgreSQL 17.11

Почему два почти одинаковых GROUP BY дают разные планы

Глава 2.4 научила писать GROUP BY; глава 9.3 — читать планы. Но в планах двух похожих запросов с агрегацией появились разные узлы: у одного HashAggregate, у другого GroupAggregate. А над ними иногда возникает Sort с загадочной строкой Sort Method: quicksort Memory: 74kB. И наконец: в планах повсюду cost=0.29..8.44 — что это за единицы, в которых «дешевле» и «дороже»? Эта глава закрывает все три вопроса — и завершает модуль о планировщике.

Sort: сортировка в памяти и вне её

Сортировки запроса исполняет модуль src/backend/utils/sort/tuplesort.c на коммите 083ac033419f690758508e08c1736089384bbee8. Его шапка (перевод дословный): «этот модуль предоставляет обобщённое средство сортировки кортежей... Модуль работает эффективно как для малых, так и для больших объёмов данных. Малые объёмы сортируются в памяти с помощью qsort(). Большие объёмы сортируются с использованием временных файлов и стандартного алгоритма внешней сортировки». Граница «малых и больших» — память, отведённая операции: «объём памяти, разрешённый для одной операции сортировки, задаётся в килобайтах вызывающим кодом (большинство передаёт work_mem)» (там же). work_mem — «задаёт базовый максимум памяти для операции запроса (такой как сортировка или хеш-таблица) до записи во временные дисковые файлы. Значение по умолчанию — четыре мегабайта (4MB)» (19.4.1 /docs/17/runtime-config-resource.html, перевод дословный). В EXPLAIN ANALYZE узел Sort отчитывается о выбранном пути: «узлы Sort и Hash предоставляют дополнительную информацию» (14.1.2 /docs/17/using-explain.html) — строки вида Sort Key: t1.fivethous, Sort Method: quicksort Memory: 74kB из учебного примера 14.1.2. Напомним из главы 8.2: сортировку может совсем убрать индекс — «индекс может выдавать строки в определённом отсортированном порядке. Это позволяет выполнить ORDER BY запроса без отдельного шага сортировки» (11.4).

Агрегация: два узла для GROUP BY

Что делает агрегатная функция с каждой строкой, описывает шапка src/backend/executor/nodeAgg.c (перевод дословный): «ExecAgg обычно вычисляет каждый агрегат следующими шагами: transvalue = initcond; для каждого входного_кортежа: transvalue = transfunc(transvalue, входное_значение); result = finalfunc(transvalue, ...)». То есть avg(rating) из 2.4 — это накопление состояния по строкам, а не «магия одного прохода». Для GROUP BY есть две стратегии исполнения, и их имена в плане берутся из кода вывода: AGG_HASHED → «HashAggregate», AGG_SORTED → «GroupAggregate» (src/backend/commands/explain.c, строки 1548–1566: разбор aggstrategy). Hash-стратегия: «хеширование можно смешивать с сортированной группировкой... можно поддерживать AGG_HASHED с несколькими хеш-таблицами и вовсе без сортировки» (nodeAgg.c, дословно) — группы складываются в хеш-таблицу по ключу GROUP BY. Sorted-стратегия работает по входу, уже упорядоченному по ключу группы: «AGG_SORTED узлы представляют "rollup"... первый отсортированный узел берёт вход из внешнего поддерева, которое планировщик уже упорядочил» (nodeAgg.c). И особый случай из 2.4: «если обычный вызов агрегата указывает DISTINCT или ORDER BY, мы сортируем входные кортежи и устраняем дубликаты (если требуется) перед выполнением описанного процесса» (nodeAgg.c, дословно).

Демонстрация на отзывах; во втором запросе вход упорядочен индексом (book_id, rating) из главы 8.2:

EXPLAIN
SELECT book_id, avg(rating) FROM reviews GROUP BY book_id;

EXPLAIN
SELECT book_id, avg(rating) FROM reviews
GROUP BY book_id
ORDER BY book_id;
                        QUERY PLAN
--------------------------------------------------------------
 HashAggregate  (cost=1.36..1.49 rows=5 width=12)
   Group Key: book_id
   ->  Seq Scan on reviews  (cost=0.00..1.12 rows=12 width=8)
(3 rows)

                            QUERY PLAN
----------------------------------------------------------------
 GroupAggregate  (cost=0.29..1.62 rows=5 width=12)
   Group Key: book_id
   ->  Index Only Scan using reviews_book_rating_idx on reviews
         (cost=0.29..1.41 rows=12 width=8)
(4 rows)

Что выведено и почему (числа условны): без упорядоченного входа планировщик выбрал HashAggregate — построить хеш-таблицу групп по мере чтения; когда строки уже идут по возрастанию book_id (Index Only Scan по индексу из главы 8.2 + глава 8.3), дешевле GroupAggregate: копить состояние, пока ключ группы не сменится. Второй план заодно показывает знакомый по 8.3 Index Only Scan. Какой план выбрать — снова решает оценка стоимости.

Из чего состоит cost

Финальный вопрос модуля: единицы cost. Ответ из 19.7.2 Planner Cost Constants (/docs/17/runtime-config-query.html, перевод дословный): «стоимости измеряются в условных единицах, определяемых параметрами стоимости планировщика. Традиционная практика — измерять стоимости в единицах чтений дисковых страниц; то есть seq_page_cost условно равен 1.0, а остальные параметры стоимости задаются относительно него». Сами параметры (значения по умолчанию): seq_page_cost — «оценка стоимости чтения дисковой страницы, являющегося частью серии последовательных чтений. По умолчанию 1.0»; random_page_cost — «оценка стоимости непоследовательно читаемой дисковой страницы. По умолчанию 4.0... Уменьшение этого значения относительно seq_page_cost приведёт к тому, что система будет предпочитать индексные сканирования; его увеличение сделает индексные сканирования относительно более дорогими»; cpu_tuple_cost — «оценка стоимости обработки каждой строки во время запроса. По умолчанию 0.01»; cpu_index_tuple_cost — «оценка стоимости обработки каждой записи индекса при индексном сканировании. По умолчанию 0.005»; cpu_operator_cost — «оценка стоимости обработки каждого оператора или функции. По умолчанию 0.0025». Так cost=1.36..1.49 для HashAggregate из примера складывается приблизительно так: одна страница Seq Scan (1.0) + 12 строк × cpu_tuple_cost + узлы агрегата (пять групп по book_id — книги 1, 2, 3, 4 и 6 — та же таблица из 12 отзывов, что и в главах 9.2–9.3, поэтому и стоимости Seq Scan совпадают). Для сравнения планов между собой единица не важна — важны отношения. Настройка этих параметров — эксплуатационная тема (middle+): «к сожалению, не существует чётко определённого метода определения идеальных значений переменных стоимости» (19.7.2). Быстрое вмешательство в выбор планов — параметры enable_* из 19.7.1: «эти параметры предоставляют грубый метод влияния на планы запросов, выбираемые оптимизатором запросов... Лучшие способы улучшить качество планов включают подгонку констант стоимости, ручной запуск ANALYZE, увеличение default_statistics_target» (19.7.1, дословно).

Связь с теорией

Внешняя сортировка — классика Silberschatz (7-е изд., гл. 15, § 15.4 Sorting): сортировка runs и их слияние, когда данные не помещаются в память; tuplesort.c — прямая реализация («малые объёмы... qsort(); большие... временные файлы и стандартный алгоритм внешней сортировки»), причём README модуля ссылается на Кнута. Агрегация — § 15.6 Other Operations. Оценка стоимости операторов — § 15.2 Measures of Query Cost: стоимость оператора складывается из I/O (страницы) и CPU (кортежи/операторы) — ровно то, что вы видели в параметрах seq_page_cost и cpu_*. Курс CMU 15-445 разбирает сортировку и агрегацию в лекции #11 (Sorting & Aggregations); русскоязычный разбор — книга «PostgreSQL 18. Оптимизация запросов» (гл. «Сортировка и группировка»).

Проверь себя

Вопрос 1. В EXPLAIN ANALYZE у узла Sort строка «Sort Method: quicksort Memory: 74kB». Что изменится, если данных станет в сто раз больше?

Ответ. Пока сортировка вписывается в work_mem («по умолчанию четыре мегабайта», 19.4.1), работает быстрый вариант: «малые объёмы сортируются в памяти с помощью qsort()» (tuplesort.c). Когда память исчерпана, включается внешний путь: «большие объёмы сортируются с использованием временных файлов и стандартного алгоритма внешней сортировки» (tuplesort.c) — Sort Method сменится на внешний вариант, а во временном каталоге появятся файлы сортировки.

Вопрос 2. Чем GroupAggregate отличается от HashAggregate и почему у второго запроса из примера планировщик выбрал GroupAggregate?

Ответ. HashAggregate строит хеш-таблицу групп («AGG_HASHED... без сортировки вообще», nodeAgg.c) по мере чтения; GroupAggregate требует вход, упорядоченный по ключу группы («первый отсортированный узел берёт вход из внешнего поддерева, которое планировщик уже упорядочил», nodeAgg.c). Во втором запросе строки уже шли по book_id из Index Only Scan по индексу (book_id, rating) (глава 8.2: индекс «позволяет выполнить ORDER BY без отдельного шага сортировки», 11.4) — сортировать не нужно, и сгруппировать по мере следования дешевле хеш-таблицы.

Вопрос 3. Можно ли по значению cost сказать, сколько миллисекунд займёт запрос? Из чего складывается это число?

Ответ. Нет: «стоимости измеряются в условных единицах... в единицах чтений дисковых страниц; seq_page_cost условно равен 1.0» (19.7.2) — это безразмерные величины для сравнения планов. Складываются из страниц I/O (seq_page_cost 1.0, random_page_cost 4.0) и работы процессора: строк (cpu_tuple_cost 0.01), записей индекса (cpu_index_tuple_cost 0.005), операторов и функций (cpu_operator_cost 0.0025) — все значения по умолчанию из 19.7.2.
