Глава 10.2. PL/pgSQL: логика на сервере

Уровень: J+ · узел карты тем: T47 · PostgreSQL 17.11

IF, которого нет в SQL

Функция из главы 10.1 умеет только выполнять запросы. Но правилу «читатель голосует за книгу — если уже голосовал, оценка обновляется, иначе вставляется новый отзыв» нужен if/else: SQL-функция такое тело выразить не может. Можно, конечно, проверить наличие строки в приложении — но тогда между SELECT и INSERT пройдёт время, и два параллельных запроса вставят два отзыва (гонка, о которой глава 6.6). Решение — языки с управляющими конструкциями, работающие внутри сервера. В PostgreSQL это прежде всего PL/pgSQL.

Что это за язык

Из 41.1 Overview (/docs/17/plpgsql-overview.html, перевод дословный): «PL/pgSQL — загружаемый процедурный язык для системы баз данных PostgreSQL. Целями проектирования PL/pgSQL были создание загружаемого процедурного языка, который можно использовать для создания функций, процедур и триггеров, добавляет управляющие конструкции к языку SQL, может выполнять сложные вычисления, наследует все пользовательские типы, функции, процедуры и операторы... В PostgreSQL 9.0 и более поздних PL/pgSQL установлен по умолчанию». Зачем он нужен, там же: «С PL/pgSQL вы можете сгруппировать блок вычислений и серию запросов внутри сервера баз данных, получив мощь процедурного языка и простоту использования SQL, но со значительной экономией накладных расходов на обмены клиент/сервер». Пометка: PL/pgSQL — диалект PostgreSQL; в стандарте SQL процедурный язык называется SQL/PSM, и PostgreSQL его не реализует.

Структура функции — 41.2 Structure of PL/pgSQL (/docs/17/plpgsql-structure.html): тело — блок из секций объявления и операторов; переменные объявляются в DECLARE. Пишем нашу функцию:

CREATE FUNCTION rate_book(p_reader_id int, p_book_id int,
                          p_rating int)
RETURNS int
LANGUAGE plpgsql
AS $$
DECLARE
    v_review_id reviews.review_id%TYPE;
BEGIN
    SELECT review_id INTO v_review_id
    FROM reviews
    WHERE reader_id = p_reader_id
      AND book_id   = p_book_id;

    IF FOUND THEN
        UPDATE reviews
        SET rating = p_rating
        WHERE review_id = v_review_id;
    ELSE
        INSERT INTO reviews (reader_id, book_id, rating)
        VALUES (p_reader_id, p_book_id, p_rating)
        RETURNING review_id INTO v_review_id;
    END IF;

    RETURN v_review_id;
END;
$$;

Разбор по элементам языка. reviews.review_id%TYPE — «%TYPE предоставляет тип данных колонки таблицы или ранее объявленной переменной PL/pgSQL» (41.3.3 Copying Types, /docs/17/plpgsql-declarations.html): тип переменной берётся от колонки, а не дублируется вручную. SELECT ... INTO — 41.5.3 Executing a Command with a Single-Row Result (/docs/17/plpgsql-statements.html): «результат SQL-команды, возвращающей одну строку... может быть присвоен переменной... SELECT select_expressions INTO [STRICT] target FROM ...». IF — 41.6.4: «IF и CASE позволяют выполнять альтернативные команды на основе условий... PL/pgSQL имеет три формы IF» — здесь вторая, с ELSE. RETURNING ... INTO переиспользует тот же механизм 41.5.3. FOUND — специальная переменная состояния из 41.5.5: «оператор SELECT INTO устанавливает FOUND в true, если строка назначена, и в false, если строка не возвращена»; там же про вторую ветку: «UPDATE, INSERT, DELETE и MERGE устанавливают FOUND в true, если затронута хотя бы одна строка».

SELECT rate_book(2, 13, 5);
SELECT rate_book(2, 13, 1);
 rate_book
-----------
        11
(1 row)

 rate_book
-----------
        11
(1 row)

Что выведено и почему: номер 11 не случаен — отзывы 1–10 накопились в главах 2.8 и 4.4, спам 11–12 из 5.2 удалён, и identity-последовательность, перезапущенная в 4.4 на 11, выдаёт первый свободный номер. Первый вызов не нашёл отзыва читателя 2 (Ивана из главы 4.4) о книге 13 «Пиковая дама» — FOUND = false, сработала ветка INSERT без явного review_id (столбец — GENERATED BY DEFAULT AS IDENTITY с главы 4.4), вернулся review_id новой строки. Второй вызов нашёл ту же строку — сработал UPDATE, вернулся тот же идентификатор: голос «обновился», второй строки не появилось. Заметьте: честная альтернатива для этого частного случая — один оператор INSERT ... ON CONFLICT ... DO UPDATE из главы 5.1, без всякого PL/pgSQL. Функция оправдана, когда логика действительно ветвистая: проверки бизнес-правил, разные коды результата, работа с несколькими таблицами. Это принципиальная граница применимости: данные обрабатываются по возможности в SQL, а не в цикле (см. ниже).

Циклы и граница применимости

«С помощью операторов LOOP, EXIT, CONTINUE, WHILE, FOR и FOREACH вы можете организовать в функции повторение серии команд» (41.6.5 Simple Loops /docs/17/plpgsql-control-structures.html). Самый частый — цикл по результату запроса: «Используя другой тип цикла FOR, вы можете итерироваться по результатам запроса... Цель последовательно принимает каждую строку-результат запроса, и тело цикла выполняется для каждой» (41.6.6):

-- вместо этого цикла — один UPDATE ниже!
CREATE FUNCTION set_min_rating(p_book_id int, p_min int)
RETURNS void
LANGUAGE plpgsql
AS $$
BEGIN
    FOR r IN
        SELECT review_id FROM reviews
        WHERE book_id = p_book_id AND rating < p_min
    LOOP
        UPDATE reviews SET rating = p_min WHERE review_id = r.review_id;
    END LOOP;
END;
$$;

Тот же результат без цикла: UPDATE reviews SET rating = p_min WHERE book_id = p_book_id AND rating < p_min; — один вызов UPDATE затрагивает все строки сразу (глава 5.2), а цикл выполняет по одному оператору на строку, и каждый проходит свой путь разбор→план→исполнение (глава 9.1). Поэтому правило: если задачу можно выразить одним множественным оператором SQL — выражайте её так; PL/pgSQL добавляйте для логики, которую SQL не выражает. Это не запрет, а ориентир цены решения: построчная обработка имеет смысл для сложных вычислений над каждой строкой, а не для замены UPDATE.

Как это исполняется

PL/pgSQL — интерпретируемый язык, и документация описывает это точно (41.11.2 Plan Caching, перевод дословный): «Интерпретатор PL/pgSQL разбирает исходный текст функции и создаёт внутреннее бинарное дерево инструкций при первом вызове функции (в каждой сессии). Дерево инструкций полностью переводит структуру операторов PL/pgSQL, но отдельные SQL-выражения и SQL-команды, используемые в функции, не переводятся немедленно. При первом выполнении каждого выражения или SQL-команды в функции интерпретатор PL/pgSQL разбирает и анализирует команду, создавая подготовленный оператор с помощью функции SPI_prepare менеджера SPI. Последующие проходы по этому выражению или команде переиспользуют подготовленный оператор». Отсюда следствия: повторный вызов rate_book в той же сессии не парсит тело заново; а «недостаток в том, что ошибки в конкретном выражении или команде нельзя обнаружить, пока эта часть функции не достигнута при исполнении» (41.11.2).

В исходном коде за это отвечают два файла src/pl/plpgsql/src/ на коммите 083ac033419f690758508e08c1736089384bbee8. Компиляция: plpgsql_compile (pl_comp.c, строка 136; «This is the slow part of plpgsql_compile()», строка 242 — построение дерева инструкций из текста). Исполнение: pl_exec.c — «Executor for the PL/pgSQL procedural language» (шапка, строки 3–4), входная точка — plpgsql_exec_function (строка 482): именно она получает дерево инструкций и выполняет их одну за другой, подставляя значения переменных. Сам вызов доходит сюда так же, как до SQL-функции из главы 10.1: менеджер функций определяет язык по pg_proc.prolang и передаёт управление обработчику языка. Разовая команда без создания функции — DO: «DO выполняет анонимный блок кода, или, другими словами, временную анонимную функцию на процедурном языке» (DO, /docs/17/sql-do.html); в коде её обрабатывает ExecuteDoStmt (functioncmds.c, строка 2066) — удобно для миграций и разовых скриптов.

Связь с теорией

Хранимые процедуры и функции — предмет § 5.2 Functions and Procedures учебника Silberschatz (7-е изд., гл. 5 Advanced SQL, с. 198): там же разобраны аргументы «за» (инкапсуляция логики в БД, целостность, переиспользование) и стандартный процедурный SQL/PSM. PostgreSQL выбрал собственный язык PL/pgSQL (диалект; влияние Oracle PL/SQL заметно в синтаксисе) — при переносе между СУБД это отличие надо учитывать. Курс CMU 15-445 хранимым функциям отдельной лекции не отводит; в этом модуле академический фундамент — Silberschatz. Русскоязычный разбор внутренностей PL/pgSQL — книга Рогова «PostgreSQL изнутри» (соответствующие главы о функциях); все утверждения здесь сверены с документацией 17.11 и кодом на базовом коммите.

Проверь себя

Вопрос 1. Чем PL/pgSQL-функция отличается от SQL-функции по выразимости и что у них общего в исполнении SQL-команд внутри?

Ответ. SQL-функция — «список SQL-операторов, разделённых точками с запятой» без ветвлений (36.5); PL/pgSQL «добавляет управляющие конструкции к языку SQL» (41.1) — переменные, IF/CASE, циклы. Общее: встроенные SQL-команды в обоих случаях идут через общий путь разбор→планирование→исполнение (глава 9.1), причём PL/pgSQL кэширует подготовленные операторы: «при первом выполнении... создаёт подготовленный оператор с помощью SPI_prepare. Последующие проходы... переиспользуют подготовленный оператор» (41.11.2).

Вопрос 2. Что делает переменная FOUND после SELECT INTO и после UPDATE? Как она используется в rate_book?

Ответ. «Оператор SELECT INTO устанавливает FOUND в true, если строка назначена, и в false, если строка не возвращена»; «UPDATE, INSERT, DELETE и MERGE устанавливают FOUND в true, если затронута хотя бы одна строка» (41.5.5). В rate_book после SELECT INTO проверка IF FOUND выбирает ветку: обновить существующий отзыв или вставить новый — без отдельного подсчёта строк.

Вопрос 3. Почему цикл FOR по строкам с UPDATE внутри хуже одного множественного UPDATE, и когда построчная обработка всё же оправдана?

Ответ. Один UPDATE затрагивает все строки одним оператором (глава 5.2); цикл выполняет по оператору на строку, каждый со своим разбором и планированием (глава 9.1) — накладные расходы растут с числом строк. Оправдана построчная обработка, когда над каждой строкой нужна логика, не выражаемая множественным оператором (сложные ветвления, коды результата); ориентир — «данные по возможности в SQL, а не в цикле».
