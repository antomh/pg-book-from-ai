Глава 1.3. Системный каталог и information_schema

Уровень: J+ · узел карты тем: T03 · PostgreSQL 17.11

Откуда приложение узнаёт, какие есть таблицы и столбцы

Задача из практики: миграция проверяет, что таблица books существует; форма в админке строится по списку столбцов; код вывода отчётов перечисляет таблицы схемы. Всем этим сценариям нужно одно и то же — получить описание базы самим SQL-запросом. Метакоманда \d это умеет, но она — часть psql, а приложению нужен SQL. Где сервер хранит ответы на вопросы «какие таблицы есть и каковы их столбцы» — тема этой главы.

Системный каталог: метаданные — это тоже таблицы

Ответ документации короткий: «Системные каталоги — это место, где СУБД хранит метаданные схемы: сведения о таблицах и столбцах, а также служебную информацию. Системные каталоги PostgreSQL — обычные таблицы» (дословно в переводе; глава «System Catalogs», /docs/17/catalogs.html). Из двух следствий второе — предостережение из той же главы: с каталогами можно делать всё, что с таблицами (DROP, INSERT, UPDATE), «и таким образом основательно сломать систему»; менять их вручную не нужно.

Где именно лежат каталоги: «в дополнение к public и пользовательским схемам каждая база содержит схему pg_catalog, в которой находятся системные таблицы, все встроенные типы данных, функции и операторы» — раздел 5.10.5 «The System Catalog Schema» (/docs/17/ddl-schemas.html).

Пример: pg_class — реестр таблиц

Самый известный каталог — pg_class: «каталог pg_class описывает таблицы и другие объекты, у которых есть столбцы или которые похожи на таблицу: индексы, последовательности, представления, материализованные представления, составные типы и TOAST-таблицы» — глава 51.11, /docs/17/catalog-pg-class.html. Какой именно это объект, сообщает столбец relkind; его документированные значения: r — обычная таблица, i — индекс, S — последовательность, v — представление, m — материализованное представление и другие.

Список обычных таблиц текущей базы:

SELECT relname, relkind
FROM pg_class
WHERE relkind = 'r'
  AND relnamespace = 'public'::regnamespace;

Для базы из главы 1.1 будет выведено:

 relname | relkind
---------+---------
 authors | r
 books   | r
(2 rows)

Что выведено и почему: в pg_class по строке на каждый объект базы; фильтр relkind = 'r' оставляет обычные таблицы (значение документировано в 51.11), relname — имя объекта. Второй фильтр обязателен: без него в вывод попадут и системные таблицы — pg_class, pg_attribute, pg_type и ещё сотня с лишним, их в любой базе больше, чем пользовательских, — поэтому отсекаем по схеме: relnamespace хранит OID схемы объекта, а конструкция 'public'::regnamespace переводит имя схемы в её OID (51.11). Именно эти данные показывает и \dt, но SQL-запрос работает из любого клиента и приложения.

Что ещё умеет psql

Метакоманды psql выводят те же метаданные в готовом виде. Например, структура таблицы books из главы 1.1:

bookshelf=# \d books
                Table "public.books"
  Column   |  Type   | Collation | Nullable | Default
-----------+---------+-----------+----------+---------
 book_id   | integer |           | not null |
 title     | text    |           | not null |
 author_id | integer |           |          |
Indexes:
    "books_pkey" PRIMARY KEY, btree (book_id)
Foreign-key constraints:
    "books_author_id_fkey" FOREIGN KEY (author_id) REFERENCES authors(author_id)

Что выведено и почему: столбцы и их типы совпадают с DDL из главы 1.1; book_id и title помечены not null, а author_id — нет: внешний ключ сам по себе не запрещает NULL. Документация прямо предупреждает об этом поведении: «ссылающаяся строка не обязана удовлетворять ограничению внешнего ключа, если хоть один из её ссылающихся столбцов равен NULL», и если это нежелательно — объявляйте столбец NOT NULL (раздел 5.5.5 «Foreign Keys», /docs/17/ddl-constraints.html; там же: внешний ключ может ссылаться только на первичный или уникальный ключ). Имена ограничений в этом выводе PostgreSQL сгенерировал сам — мы их в DDL не задавали.

Об именах сгенерированных ограничений

Имя вида books_author_id_fkey соответствует формату «таблица_столбец_fkey», показанному в документации: в примере нарушения внешнего ключа в туториале сообщение об ошибке называет ограничение weather_city_fkey — для таблицы weather и столбца city (/docs/17/tutorial-fk.html; подробнее — глава 4.2). Документация отмечает лишь, что при отсутствии явного имени «система выберет имя за вас» (5.5.1); полное правило выбора имён (обрезка длинных имён, разрешение коллизий) в документации не зафиксировано.

information_schema: стандартная альтернатива

Помимо pg_catalog, есть второй источник метаданных — схема information_schema. Различие принципиально и зафиксировано в документации: «информационная схема определена в стандарте SQL, поэтому её можно считать переносимой и стабильной — в отличие от системных каталогов, специфичных для PostgreSQL» (глава 35, /docs/17/information-schema.html). На практике: пишете код, который должен работать и на других СУБД, — запрашивайте information_schema; готовы к специфике PostgreSQL и нужны детали, которых нет в стандарте, — pg_catalog.

Список таблиц через стандартное представление:

SELECT table_schema, table_name, table_type
FROM information_schema.tables
WHERE table_type = 'BASE TABLE';

Вывод для той же базы:

 table_schema | table_name | table_type
--------------+------------+------------
 public       | authors    | BASE TABLE
 public       | books      | BASE TABLE
(2 rows)

Что выведено и почему: значение BASE TABLE документировано как «обычная постоянная таблица» (persistent base table, the normal table type); весь набор значений table_type (BASE TABLE, VIEW, FOREIGN, LOCAL TEMPORARY) документирован в описании представления information_schema.tables: /docs/17/infoschema-tables.html. Список столбцов конкретной таблицы — представление information_schema.columns (/docs/17/infoschema-columns.html), где столбец data_type показывает имя типа столбца, если тот встроенный:

SELECT column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'books';

Системные представления: метаданные о работе сервера

Кроме описания объектов, PostgreSQL публикует данные о собственном состоянии — в системных представлениях (глава 52, /docs/17/views.html). Классический пример — pg_stat_activity: «одна строка на каждый серверный процесс с информацией о его текущей активности» (глава 27, /docs/17/monitoring-stats.html). Это представление определено в исходном коде сервера в файле src/backend/catalog/system_views.sql, строка 865 на базовом коммите (оператор CREATE VIEW pg_stat_activity AS — номер строки проверен на этом коммите):

SELECT pid, state, query
FROM pg_stat_activity;

Систематический мониторинг сервера — тема уровня middle+ и в этот учебник не входит (правила проекта, 00_rules.md); здесь pg_stat_activity — лишь пример того, что «состояние сервера тоже таблица».

Проверь себя

Вопрос 1. Приложение должно работать на PostgreSQL и, возможно, на другой СУБД. Каким источником метаданных пользоваться и почему?

Ответ. information_schema: она определена стандартом SQL и позиционируется как переносимая и стабильная, тогда как системные каталоги pg_catalog специфичны для PostgreSQL — формулировка из главы 35: /docs/17/information-schema.html.

Вопрос 2. Напишите запрос, который перечислит обычные таблицы текущей базы, используя pg_catalog.

Ответ. SELECT relname FROM pg_class WHERE relkind = 'r' AND relnamespace = 'public'::regnamespace; — pg_class описывает таблицы и подобные объекты, relkind = 'r' документирован как «обычная таблица», а фильтр по схеме отсекает системные таблицы (глава 51.11: /docs/17/catalog-pg-class.html).

Вопрос 3. Чем опасно, что каталоги — «обычные таблицы»?

Ответ. Опасность в симметрии прав: с ними работают те же команды SQL (вставка, изменение, удаление строк), поэтому неосторожный запрос испортит сами метаданные. Документация предупреждает об этом прямо: «можно… основательно сломать систему» — /docs/17/catalogs.html. Читать каталоги — нормально, изменять их напрямую — нет.
