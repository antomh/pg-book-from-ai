Глава 3.5. JSON и JSONB

Уровень: J+ · узел карты тем: T16 · PostgreSQL 17.11

Настройки пользователя без колонки на каждый чих

У читательского профиля копятся разнородные настройки: тема оформления, лимит книг, набор тегов интересов. Колонку под каждую заводить жалко, а JSON из мобильного приложения уже приезжает готовым. PostgreSQL принимает такие данные в типы json и jsonb — «типы данных JSON предназначены для хранения JSON (JavaScript Object Notation) согласно RFC 7159. Такие данные можно хранить и как text, но JSON-типы дают преимущество: каждый сохранённый объект гарантированно валиден по правилам JSON» (раздел 8.14, /docs/17/datatype-json.html, перевод дословный). Вопрос главы: какой из двух типов выбрать, как по ним запрашивать и когда вместо JSON нужны обычные столбцы. Уровень J+.

json против jsonb: два формата хранения

Пометка о границах стандарта: сам тип json соответствует SQL:2016, а jsonb — расширение PostgreSQL, которого в стандарте нет. Разница сформулирована в 8.14 дословно: «json и jsonb принимают практически одинаковые множества значений на вход. Главное практическое различие — в эффективности. Тип json хранит точную копию входного текста, которую функции обработки обязаны заново разбирать при каждом выполнении; jsonb хранится в разобранном (decomposed) бинарном формате, который из-за дополнительной конвертации немного медленнее записывать, но значительно быстрее обрабатывать, так как повторный разбор не нужен. jsonb также поддерживает индексацию, что может стать значительным преимуществом». И решение: «в целом большинство приложений должны предпочитать хранить JSON-данные как jsonb, если нет весьма специфических потребностей».

Чем платит jsonb — потерей «текстуальности»: «jsonb не сохраняет пробелы, не сохраняет порядок ключей объекта и не хранит дубликаты ключей объекта. Если во входе заданы дубликаты ключей, сохраняется только последнее значение» (8.14). Демонстрация на данных:

CREATE TABLE reader_settings (
    reader_id integer PRIMARY KEY,
    prefs     jsonb NOT NULL
);

INSERT INTO reader_settings VALUES
    (1, '{"theme": "dark",
        "tags": ["sql", "classic"],
        "limits": {"max_books": 10}}'),
    (2, '{"theme": "light", "tags": ["sql"]}');

SELECT prefs FROM reader_settings WHERE reader_id = 1;
                                 prefs
------------------------------------------------------------------------
 {"tags": ["sql", "classic"], "theme": "dark", "limits": {"max_books": 10}}
(1 row)

Что выведено и почему: jsonb перезаписал документ в своём формате — пробелы исчезли, порядок ключей изменился (сортировка по длине и алфавиту), дубликаты ключей схлопнулись бы в последний. Содержательная часть не изменилась: это те же данные.

Операторы доступа: -> и ->>

Операторы из таблицы 9.45 (/docs/17/functions-json.html): -> «извлекает поле объекта JSON по ключу» (результат — json) или «n-й элемент JSON-массива (элементы индексируются с нуля, но отрицательные целые считаются с конца)»; ->> — то же, но результат — text. Примеры из таблицы: '[{"a":"foo"}, {"b":"bar"}, {"c":"baz"}]'::json -> 2 → {"c":"baz"}; '{"a": {"b":"foo"}}'::json -> 'a' → {"b":"foo"}. Осторожно с привычками из главы 3.4: массивы PostgreSQL индексируются с единицы, а JSON-массивы здесь — с нуля; tags[1] и -> 1 указывают на разные элементы.

SELECT prefs ->> 'theme'            AS theme_text,
       prefs -> 'tags'              AS tags_json,
       prefs -> 'tags' ->> 0         AS first_tag,
       prefs -> 'limits' ->> 'max_books' AS max_books
FROM reader_settings
WHERE reader_id = 1;
 theme_text |      tags_json      | first_tag | max_books
------------+---------------------+-----------+-----------
 dark       | ["sql", "classic"]  | sql       | 10
(1 row)

Что выведено и почему: ->> вернул текст 'dark'; -> вернул вложенное значение как json; для массива -> 0 — первый элемент (индексация с нуля); цепочка -> 'limits' ->> 'max_books' прошла вглубь документа. Выбор между операторами — выбор типа результата: json для дальнейшей навигации, text для вывода и сравнения.

Вложенность: @> и существование ключей

Раздел 8.14.3 jsonb Containment and Existence: «тест вложенности — важная возможность jsonb; для json аналогичных средств нет. Вложенность проверяет, содержит ли один jsonb-документ в себе другой». Семантика на примерах документации: «простые скалярные/примитивные значения содержат только идентичное значение»; «массив справа содержится в массиве слева» (порядок и дубликаты элементов не важны: '[1, 2, 3]'::jsonb @> '[3, 1]' и '[1, 2, 3]'::jsonb @> '[1, 2, 2]' — оба true); «объект с одной парой справа содержится в объекте слева». Операторы существования ?/?|/?& проверяют ключи верхнего уровня (таблица 9.46).

SELECT reader_id,
       prefs @> '{"tags": ["classic"]}' AS likes_classic,
       prefs ? 'limits'                  AS has_limits
FROM reader_settings;
 reader_id | likes_classic | has_limits
-----------+--------------+------------
         1 | t            | t
         2 | f            | f
(2 rows)

Что выведено и почему: у первого профиля массив tags содержит 'classic' (элемент множества, независимо от порядка), и ключ 'limits' существует; у второго — ни то, ни другое. Для jsonb есть и обычные операторы сравнения (9.16: «обычные операторы сравнения из таблицы 9.1 доступны для jsonb, но не для json») — ещё одно практическое отличие типов.

Индексация jsonb: GIN

Раздел 8.14.4 jsonb Indexing: «GIN-индексы можно использовать для эффективного поиска ключей или пар ключ/значение, встречающихся в большом числе jsonb-документов. Предоставляются два класса операторов GIN с разными компромиссами производительности и гибкости». Класс по умолчанию jsonb_ops поддерживает запросы с ?, ?|, ?&, @> и jsonpath-операторами; нестандартный jsonb_path_ops — только @> и jsonpath-операторы, зато «индекс jsonb_path_ops обычно значительно меньше индекса jsonb_ops на тех же данных, и специфичность поиска лучше» (8.14.4; детально индексы — глава 8.4 этого учебника):

CREATE INDEX reader_settings_prefs_gin
    ON reader_settings USING GIN (prefs);

Что произойдёт и почему: после создания GIN-индекса запросы вида WHERE prefs @> '{"theme": "dark"}' и WHERE prefs ? 'limits' смогут использовать индекс вместо разбора каждой строки — то самое «jsonb поддерживает индексацию» из 8.14.

JSON или реляционные столбцы?

Правило такое же, как с массивами из главы 3.4, но строже: JSON-документ — атрибут строки целиком. Внутри документа нет ссылочной целостности, типизированных столбцов и дешёвых ограничений — «документ валиден по правилам JSON», и только. Настройки профиля, payload вебхука, ответ внешнего API — типичные jsonb-сценарии. Как только полю нужна уникальность, внешний ключ, точный тип или статистика по значениям — это столбец таблицы (модуль 4). Документация предупреждает и об «обратном» дизайне: в 8.14.2 «Designing JSON Documents» данные должны быть адаптированы к модели вложенности jsonb, чтобы операторы @>/? работали эффективно (там же разбирается пример таблицы api с GIN-индексом по полю jdoc).

Проверь себя

Вопрос 1. Почему «большинство приложений должны предпочитать jsonb»? Назовите два свойства, которыми платит jsonb.

Ответ. jsonb быстрее обрабатывается («повторный разбор не нужен») и поддерживает индексацию (GIN); плата — «не сохраняет пробелы, не сохраняет порядок ключей объекта и не хранит дубликаты ключей: сохраняется только последнее значение» (8.14). json оставляют при «весьма специфических потребностях», например legacy-зависимости от порядка ключей.

Вопрос 2. Чем prefs -> 'tags' отличается от prefs ->> 'tags' и почему prefs -> 'tags' ->> 0 вернёт "sql", а не "classic"?

Ответ. -> возвращает json (вложенное значение, пригодное для дальнейшей навигации), ->> — text. Элементы JSON-массива индексируются с нуля (таблица 9.45: «array elements are indexed from zero, but negative integers count from the end»), поэтому индекс 0 — первый элемент 'sql'; 'classic' — индекс 1.

Вопрос 3. Верно ли, что '{"a": 1, "b": 2}'::jsonb @> '{"b": 2}' и '[1, 2, 3]'::jsonb @> '[3, 1]'? Какое из выражений с json-типом вместо jsonb так проверить нельзя?

Ответ. Оба верны: объект справа с одной парой содержится в объекте слева; для массивов порядок и дубликаты элементов не важны (примеры — 8.14.3). Любое из них: «тест вложенности — важная возможность jsonb; для json аналогичных средств нет» (8.14.3).
