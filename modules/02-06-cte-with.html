Глава 2.6. Общие табличные выражения (WITH)

Уровень: J · узел карты тем: T09 · PostgreSQL 17.11

Подзапрос в подзапросе: читаемость умирает на третьем уровне

Запрос из главы 2.5 — внешний SELECT, внутри подзапрос с GROUP BY. Добавьте ещё шаг (отфильтровать по количеству книг, потом посчитать средний рейтинг по отобранному, потом взять лучших) — и скобки начнут вкладываться в скобки, а имена псевдонимов будут жить только внутри своего фрагмента. SQL-конструкторы решают это последовательным уточнением: сначала «промежуточная таблица 1», затем «таблица 2 на её основе», затем итоговый запрос. Для этого в SQL есть конструкция WITH — общее табличное выражение (Common Table Expression, CTE). Цель главы — свободно переписывать вложенные подзапросы в цепочку CTE и наоборот.

WITH: именованные промежуточные результаты

Документация: «WITH даёт способ писать вспомогательные операторы для использования в большом запросе. Эти операторы, часто называемые общими табличными выражениями или CTE, можно рассматривать как определение временных таблиц, существующих только ради одного запроса» — раздел 7.8 WITH Queries, /docs/17/queries-with.html. «Базовая ценность SELECT в WITH — разбивать сложные запросы на более простые части» (раздел 7.8.1 там же). Внутри WITH могут быть SELECT, INSERT, UPDATE, DELETE и MERGE (7.8; изменяющие данные CTE — тема модуля 5, здесь о них только упоминаем).

Запрос из 2.5, переписанный на CTE:

WITH author_stats AS (
    SELECT a.name, avg(b.rating) AS avg_rating
    FROM authors a JOIN books b ON b.author_id = a.author_id
    GROUP BY a.name
)
SELECT name, avg_rating
FROM author_stats
WHERE avg_rating >= 4.5
ORDER BY avg_rating DESC;
     name      |     avg_rating
---------------+--------------------
 Лев Толстой  | 5.0000000000000000
 Александр Пушкин | 4.5000000000000000
(2 rows)

Что выведено и почему: результат тот же, что у версии с подзапросом в FROM (глава 2.5): сначала шаг «свернуть книги по авторам», затем шаг «отфильтровать». Отличие — у промежуточного результата появилось имя author_stats, и оба шага читаются сверху вниз. CTE существует до конца одного запроса: это не хранимый объект и не временная таблица между запросами.

Цепочки CTE: следующий видит предыдущие

В WITH можно объявить несколько выражений, и каждое следующее может использовать предыдущие — как в примере документации (regional_sales, затем top_regions, затем основной SELECT, раздел 7.8.1). Добавим к нашей задаче шаг «только плодовитые авторы»:

WITH author_stats AS (
    SELECT a.author_id, a.name,
           count(*) AS books_cnt,
           avg(b.rating) AS avg_rating
    FROM authors a JOIN books b ON b.author_id = a.author_id
    GROUP BY a.author_id, a.name
),
prolific AS (
    SELECT * FROM author_stats WHERE books_cnt > 1
)
SELECT name, avg_rating
FROM prolific
ORDER BY avg_rating DESC;
     name      |     avg_rating
---------------+--------------------
 Лев Толстой  | 5.0000000000000000
 Александр Пушкин | 4.5000000000000000
(2 rows)

Что выведено и почему: prolific ссылается на author_stats по имени — как на обычную таблицу; итог тот же, что в 2.5, но теперь каждый шаг — отдельная строка конвейера, и порядок шагов совпадает с порядком чтения. Обратное переписывание — «CTE в подзапрос» — механическое: тело CTE становится подзапросом в FROM следующего шага.

Материализация: вычислять CTE отдельно или влить в запрос

Полезное свойство CTE зафиксировано в разделе 7.8.3: «CTE обычно вычисляются один раз на выполнение родительского запроса, даже если на них ссылаются более одного раза. Таким образом, дорогие вычисления, нужные в нескольких местах, можно поместить в CTE, чтобы избежать лишней работы». Но у медали две стороны: «оптимизатор не может протолкнуть ограничения родительского запроса вниз в CTE, на которую ссылаются многократно, — такое CTE вычисляется как написано, без отбрасывания строк, которые родительский запрос потом отбросит» (там же).

Поэтому у оптимизатора есть выбор, описанный дословно: «если CTE нерекурсивная и без побочных эффектов (то есть это SELECT без волатильных функций), она может быть влита (folded) в родительский запрос, допуская совместную оптимизацию двух уровней запроса. По умолчанию это происходит, если родительский запрос ссылается на CTE ровно один раз, и не происходит при нескольких ссылках. Решение можно переопределить: MATERIALIZED — принудительно вычислить CTE отдельно, NOT MATERIALIZED — принудительно влить в родительский запрос» (раздел 7.8.3; сами слова-модификаторы MATERIALIZED / NOT MATERIALIZED — расширение PostgreSQL: в стандарте SQL таких опций нет), /docs/17/queries-with.html).

Показательный пример из документации (там же):

WITH w AS (
    SELECT * FROM big_table
)
SELECT * FROM w WHERE key = 123;

«Это CTE будет влито, давая тот же план выполнения, что и SELECT * FROM big_table WHERE key = 123. В частности, если по key есть индекс, он, вероятно, будет использован, чтобы прочитать только строки с key = 123». А вот при двух ссылках (FROM w AS w1 JOIN w AS w2 ...) CTE «будет материализовано: создастся временная копия big_table, которая затем соединяется сама с собой — без пользы индексов». Это конкретный пример прагматики: слово MATERIALIZED/NOT MATERIALIZED — инструмент управления, когда семантика «вычислить один раз» нужна гарантированно или, наоборот, мешает индексам.

Проверь себя

Вопрос 1. Чем CTE отличается от временной таблицы и от подзапроса в FROM?

Ответ. CTE — «временные таблицы, существующие только ради одного запроса» (7.8): никакой объект схемы не создаётся, данные не переживают конец запроса, имя видно только внутри этого оператора. От подзапроса в FROM отличается синтаксически и читабельностью: несколько шагов получают имена и идут цепочкой, каждый следующий видит предыдущие; семантически одиночный нерекурсивный CTE с одной ссылкой может вычисляться так же (вливание — 7.8.3).

Вопрос 2. Когда по умолчанию CTE вливается в родительский запрос, а когда материализуется? Как переопределить?

Ответ. Нерекурсивная CTE без побочных эффектов (SELECT без волатильных функций) при одной ссылке из родительского запроса по умолчанию вливается; при нескольких ссылках — материализуется. Переопределяют явно словами MATERIALIZED (принудительно отдельно) и NOT MATERIALIZED (принудительно влить) — раздел 7.8.3 /docs/17/queries-with.html.

Вопрос 3. Перепишите без WITH: WITH t AS (SELECT author_id, count(*) AS c FROM books GROUP BY author_id) SELECT a.name FROM authors a JOIN t ON t.author_id = a.author_id WHERE t.c > 1;

Ответ. SELECT a.name FROM authors a JOIN (SELECT author_id, count(*) AS c FROM books GROUP BY author_id) AS t ON t.author_id = a.author_id WHERE t.c > 1; — тело CTE стало производной таблицей в FROM с псевдонимом t (правила для подзапросов в FROM — 7.2.1.3). Результат идентичен: Пушкин и Толстой.
