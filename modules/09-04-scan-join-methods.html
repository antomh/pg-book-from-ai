Глава 9.4. Методы доступа и соединения в планах

Уровень: J · узел карты тем: T44 · PostgreSQL 17.11

Один запрос — три разных плана

Запрос «все книги Пушкина» на ноутбуке идёт миллисекунды, а на боевом сервере той же базы — секунды. Планы различаются ровно одним: методы доступа к таблицам и метод соединения выбраны другие. В плане это имена узлов: Seq Scan, Index Scan, Bitmap Heap Scan внизу; Nested Loop, Hash Join, Merge Join над ними. Что стоит за каждым именем, и почему планировщик выбирает разное на разных данных? Напомним общий принцип из 50.1: он «сначала создаёт все возможные пути... затем оценивается стоимость выполнения каждого пути, и выбирается самый дешёвый». Значит, имена узлов — это кандидаты, из которых стоимость отбирает победителя.

Три способа прочитать таблицу

«Узлы на нижнем уровне дерева — сканирующие узлы: они возвращают сырые строки из таблицы. Существуют разные типы сканирующих узлов для разных методов доступа к таблицам: последовательные сканирования, индексные сканирования и битовые индексные сканирования» (14.1.1 /docs/17/using-explain.html, перевод дословный). Смысл каждого вы уже знаете из модуля 8; здесь — сводка в терминах плана:

УзелКак читает таблицуКогда выгоден
Seq Scanвсе страницы по порядку (глава 7.2); условие — в строке Filterнужна большая доля строк, или таблица помещается в страницу: «на таблице, занимающей одну страницу, вы почти всегда получите план с последовательным сканированием» (14.1.3)
Index Scanспуск по B-tree (глава 8.1), затем чтение строки по t_tid; условие — в строке Index Condмало строк по условию; порядок из индекса вместо сортировки (глава 8.2)
Bitmap Heap Scan«система сканирует каждый нужный индекс и готовит в памяти битовую карту... затем строки таблицы посещаются» (11.5)многократные условия, «наличие элемента» в GIN (глава 8.4), средняя доля строк

Последовательное сканирование исполняет узел ExecSeqScan в src/backend/executor/nodeSeqscan.c (строка 108 на коммите 083ac033419f690758508e08c1736089384bbee8). Обратите внимание на строку Filter у Seq Scan: условие проверяется по каждой строке после чтения, — в отличие от Index Cond, который сужает чтение ещё в индексе.

Три способа соединить две таблицы

Nested Loop — вложенный цикл: для каждой строки внешнего входа — поиск совпадений на внутреннем («process a nestloop join of two plans» — интерфейсный комментарий к ExecNestLoop, nodeNestloop.c, строка 17; сигнатура — строка 60). В плане из 9.3 восемь отфильтрованных отзывов — восемь запусков внутреннего Index Scan; в EXPLAIN ANALYZE это видно как loops=8, потому что «внутреннее индексное сканирование будет выполнено один раз для каждой внешней строки» (14.1.2, дословно). Nested Loop хорош, когда внешний вход мал, а на внутреннем есть индекс по ключу соединения — тогда каждая итерация дешёвая.

Hash Join — сначала «the relation we build hash table on is the "inner", the other one is "outer"» (комментарий к ExecHashJoinImpl: «This function implements the Hybrid Hashjoin algorithm», nodeHashjoin.c, строки 207–220; обёртка ExecHashJoin — строка 678): внутренний вход целиком засыпается в хеш-таблицу по ключу соединения (в плане видна строка Hash Cond: и дочерний узел Hash), затем внешний вход читается один раз, и каждая его строка ищется в хеш-таблице. Это один проход по каждому входу — выгодно на больших таблицах без готового порядка.

Merge Join — слияние двух отсортированных входов: «merge-join выполняется соединением внутренних и внешних кортежей, удовлетворяющих условиям соединения вида ((= outerKey innerKey) ...). Однако исполнителю запроса нужно знать, "больше/меньше" ли внешний кортеж внутреннего, чтобы он мог "синхронизировать" два отношения» (комментарий NOTES к ExecMergeJoin, nodeMergejoin.c, строки 25–31; сигнатура — строка 599). Оба входа обязаны идти в порядке ключа соединения — отсюда в планах рядом с Merge Join часто живут узел Sort или Index Scan. Порядок соединений планировщик выбирает сам: «в простом запросе соединения планировщик свободен соединять таблицы в любом порядке» (14.3 /docs/17/explicit-joins.html, дословно).

Демонстрация: тот же запрос, разные данные

EXPLAIN
SELECT a.name, b.title
FROM authors a
JOIN books b ON b.author_id = a.author_id
WHERE a.name = 'Пушкин';
-- учебная база: 4 автора, 10 книг (5 из них — Пушкина)
 Nested Loop  (cost=0.00..2.15 rows=3 width=40)
   -> Seq Scan on authors a  (cost=0.00..1.05 rows=1 width=12)
         Filter: (name = 'Пушкин')
   -> Seq Scan on books b  (cost=0.00..1.10 rows=3 width=28)
         Filter: (author_id = a.author_id)

Теперь тот же JOIN без фильтра по автору — на схеме, где books разрослась до миллионов строк:

EXPLAIN
SELECT a.name, b.title
FROM authors a
JOIN books b ON b.author_id = a.author_id;
 Hash Join  (cost=1.10..41302.90 rows=2000000 width=40)
   Hash Cond: (b.author_id = a.author_id)
   -> Seq Scan on books b  (cost=0.00..30370.00 rows=2000000 width=28)
   -> Hash  (cost=1.05..1.05 rows=4 width=12)
         -> Seq Scan on authors a  (cost=0.00..1.05 rows=4 width=12)

Что выведено и почему (числа условны): на маленьких данных Nested Loop с Seq Scan по обеим таблицам дешевле построения хеш-таблицы — «на таблице, занимающей одну страницу, вы почти всегда получите план с последовательным сканированием» (14.1.3). Проверьте арифметику первого плана: 1.05 (внешний Seq Scan) + 1 × 1.10 (один запуск внутреннего) = 2.15 — «стоимость узла верхнего уровня включает стоимость всех его дочерних». Во втором запросе фильтра по автору нет — внешний вход — все два миллиона строк, и цена вложенного цикла растёт как «внешний × внутренний» (2 000 000 запусков внутреннего сканирования). Заметим: пока WHERE оставался селективным (внешний вход — один Пушкин), даже на большой таблице дешевле был бы Nested Loop с одним параметризованным сканированием books (~1.05 + 1 × 30370); Hash Join побеждает именно на «широком» внешнем входе — планировщик выбирает его: один проход по books, хеш из четырёх авторов. Заметьте: у Hash Join строки Hash Cond и дочерний узел Hash — хеш-таблица строится на внутреннем входе (authors), как описано в коде. Третий вариант — Merge Join — появился бы, если бы оба входа уже шли в порядке author_id (например, по индексу): тогда сортировать никого не нужно.

Связь с теорией

Все три соединения — классика Silberschatz (7-е изд., гл. 15, § 15.5 Join Operation): вложенный цикл (nested-loop join) и его блочный вариант, хеш-соединение (hash join, фаз build/probe) и сортировка-слияние (merge join) — с оценками стоимости каждого в зависимости от размеров входов. Выбор по стоимости — предмет гл. 16 (§ 16.1 Overview: перебор эквивалентных планов). PostgreSQL отличается от «учебникового» перебора: полный перебор порядков соединений заменён поиском по дереву путей (README каталога optimizer, глава 9.1), а стоимости выражены в условных единицах страниц (глава 9.5). Курс CMU 15-445 посвящает алгоритмам соединений лекцию #12 (Joins Algorithms); русскоязычный разбор методов доступа и соединений — в книге «PostgreSQL 18. Оптимизация запросов» (гл. «Методы доступа», «Способы соединений»); утверждения здесь сверены с 14.1, 11.5 и кодом на базовом коммите.

Проверь себя

Вопрос 1. В плане Seq Scan on reviews (Filter: (rating = 5)) и рядом в другом плане Index Scan ... (Index Cond: (rating = 5)). В чём разница между Filter и Index Cond?

Ответ. Index Cond — условие, по которому B-tree (глава 8.1) сужает диапазон просмотренных записей индекса; Filter — условие, проверяемое по каждой прочитанной строке: у Seq Scan условие из WHERE живёт именно в Filter, потому что «сканирующие узлы возвращают сырые строки из таблицы» (14.1.1), а фильтрация происходит после чтения.

Вопрос 2. Почему на маленькой внешней таблице с индексом по ключу соединения планировщик выбирает Nested Loop, а на двух больших — Hash Join?

Ответ. Nested Loop повторяет внутренний поиск «один раз для каждой внешней строки» (14.1.2): дёшево, если внешних строк мало, а внутренний вход ищется по индексу. На больших входах стоимость вложенного цикла растёт пропорционально произведению размеров, и дешевле Hash Join: внутренний вход один раз строится в хеш-таблицу («the relation we build hash table on is the "inner"», nodeHashjoin.c), внешний читается один проход. Планировщик сравнивает оба варианта по оценкам стоимости (50.1) и «выбирает самый дешёвый».

Вопрос 3. Что обязано выполняться для входов Merge Join и откуда этот порядок обычно берётся в плане?

Ответ. Входы должны идти в порядке ключа соединения: merge-join соединяет кортежи по условиям «(= outerKey innerKey)» и должен «синхронизировать» оба отношения, зная, какой кортеж «больше/меньше» (nodeMergejoin.c, NOTES, L25–31). Порядок приходит из индекса (Index Scan по ключу соединения, глава 8.2) или из явного узла Sort над входом; в плане рядом с Merge Join виден Sort или Index Scan.
