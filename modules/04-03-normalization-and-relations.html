Глава 4.3. Связи и нормализация

Уровень: J · узел карты тем: T20 · PostgreSQL 17.11

Одна большая таблица, которая разваливается

Первый проект «дневника чтения» кладут в одну таблицу: кто читал, что читал, кто автор, оценка. Через неделю администратору нужно: добавить нового автора, у которого ещё нет прочтений, — нельзя, вставка строки требует и читателя, и оценку; исправить опечатку «Толстй» в фамилии автора — нужно пройтись по всем строкам его книг и легко пропустить одну; удалить последнюю запись о «Войне и мире» — заодно исчезает факт существования книги и её автора. Это классические аномалии вставки, обновления и удаления. Теория реляционного проектирования объясняет их одним словом: в таблице смешаны несколько сущностей, и лечит — нормализацией. Глава — самая теоретическая в учебнике: она отвечает на вопрос «почему схема из четырёх таблиц с внешними ключами, а не одна удобная таблица».

CREATE TABLE reading_log (
    reader_email varchar(255) NOT NULL,
    reader_city  text,
    book_title   text NOT NULL,
    author_name  text NOT NULL,
    rating       smallint,
    read_on      date
);

INSERT INTO reading_log VALUES
    ('anna@example.com', 'Москва', 'Евгений Онегин', 'Пушкин', 5, DATE '2026-10-01'),
    ('anna@example.com', 'Москва', 'Война и мир', 'Толстой', 4, DATE '2026-10-15'),
    ('ivan@example.com', 'Казань', 'Война и мир', 'Толстой', 3, DATE '2026-11-02');

Сначала связи: 1:N, 1:1, M:N

Связи между сущностями в теории описываются кардинальностями (Silberschatz, гл. 6.4 «Mapping Cardinalities»). В реляционной схеме все три вида выражаются внешними ключами из главы 4.2, но по-разному:

  • 1:N («один автор — много книг»): FK на стороне N — books.author_id REFERENCES authors. Столбец внешнего ключа живёт в таблице «многих».
  • 1:1 («один читатель — один профиль»): тот же FK, но с ограничением уникальности на ссылающемся столбце (profile.reader_id UNIQUE REFERENCES readers) — уникальность не даст появиться второму профилю того же читателя.
  • M:N («читатели отмечают прочитанные книги с оценкой»): отдельная таблица соединения с двумя внешними ключами. Документация подтверждает паттерн: «у таблицы может быть более одного ограничения внешнего ключа. Это используется для реализации связей многие-к-многим» (5.5.5, /docs/17/ddl-constraints.html).

Функциональные зависимости

Инструмент анализа — функциональная зависимость (ФЗ): «X определяет A» (X → A), если каждому значению X соответствует ровно одно значение A (Silberschatz, гл. 7.2 и 7.4). В нашей таблице читаются три зависимости:

  • reader_email → reader_city (город — свойство читателя);
  • book_title → author_name (автор — свойство книги);
  • (reader_email, book_title) → rating, read_on (оценка и дата — свойство пары «читатель × книга»).

Ключ таблицы — (reader_email, book_title); именно он «определяет» строку. Теперь видно, что не так: reader_city зависит от части ключа, а author_name — от набора столбцов, который вообще не является ключом. Нормальные формы — это последовательные запреты на такие ситуации.

Первая нормальная форма: атомарные значения

1НФ требует, чтобы каждый столбец хранил атомарное значение, а не список или группу (Silberschatz, гл. 7.8 «Atomic Domains and First Normal Form»). Типичное нарушение 1НФ — ячейка вида 'Евгений Онегин, Война и мир': по такому столбцу нельзя ни фильтровать (WHERE book_title = 'Война и мир' ничего не найдёт), ни соединять с книгами. Ремонт — каждая книга отдельной строкой: так устроена и таблица reading_log выше, и вся реляционная модель из главы 1.1.

Уточнение для читателя модуля 3: массивы (text[]) и JSONB нарушают 1НФ формально, но это осознанное решение в тех случаях, когда элемент списка никогда не участвует в связях и ограничениях (теги, настройки). Критерий выбора — глава 3.4/3.5; здесь важно понимать цену: элементы массива не могут быть целью внешнего ключа.

Вторая нормальная форма: ничего от «части ключа»

2НФ запрещает зависимость неключевого атрибута от части составного ключа (Silberschatz, гл. 7.3). reader_city зависит только от reader_email — половины ключа. Именно из-за этого возникает аномалия обновления: город Анны размножен по всем её строкам, и исправление требует правки каждой. Ремонт — вынести читателя в собственную таблицу:

-- читатели уже описаны в главе 4.1: readers(reader_id, email,
-- display_name, is_active, city, registered_at)

CREATE TABLE reading_log2 (
    reader_email  varchar(255) NOT NULL REFERENCES readers(email),
    book_title    text NOT NULL,
    author_name   text NOT NULL,
    publisher     text,
    publisher_city text,
    rating        smallint,
    read_on       date,
    PRIMARY KEY (reader_email, book_title)
);

Третья нормальная форма: ничего транзитивного

3НФ запрещает транзитивные зависимости: неключевой атрибут, зависящий от другого неключевого (Silberschatz, гл. 7.3). В reading_log2 она уже есть: publisher_city зависит не от ключа, а от publisher — неключевого атрибута. Полный ключ (reader_email, book_title) определяет книгу, книга — издателя, издатель — город: цепочка «ключ → publisher → publisher_city» и есть транзитивная зависимость, и город издательства размножается по всем прочтениям всех книг этого издателя. Сюда же примыкает остаток нарушения 2НФ: author_name и сам publisher зависят от book_title — части составного ключа. Отсюда аномалии вставки и удаления: нельзя завести автора без прочтения; удалив последнее прочтение книги, теряем связь «книга → автор». Ремонт — вынести издательства, книги и авторов:

CREATE TABLE authors (
    author_id integer PRIMARY KEY,
    name      text NOT NULL
);

CREATE TABLE publishers (
    publisher_id integer PRIMARY KEY,
    name         text NOT NULL,
    city         text NOT NULL
);

CREATE TABLE books (
    book_id     integer PRIMARY KEY,
    title       text NOT NULL,
    author_id   integer NOT NULL REFERENCES authors,
    publisher_id integer NOT NULL REFERENCES publishers
);

-- таблица соединения — reviews из главы 4.2: book_id и reader_id
-- (два внешних ключа) плюс атрибуты связи (rating, comment)

Это и есть сквозная схема учебника: каждая таблица описывает одну сущность, каждая неключевая колонка зависит только от ключа своей таблицы. Аномалии ушли: автор заводится до прочтений (строка в authors), город правится в одном месте (readers), удаление прочтения не затрагивает книги и авторов.

Денормализация — осознанно

Нормализация — не догма, а инструмент устранения аномалий (Silberschatz начинает разбор с признаков хорошего и плохого дизайна — гл. 7.1 «Features of Good Relational Designs»). Обратный ход — денормализация — осознанно дублирует данные ради скорости чтения: например, столбец reviews_count прямо в books, чтобы не считать count(*) по отзывам на каждой странице. Цена — возврат аномалии обновления: счётчик надо поддерживать вручную (триггером — глава 10.3 — или приложением), и он может разойтись с истиной. Правило junior-уровня: сначала нормализуй до 3НФ; денормализируй точечно, когда измерения показали проблему (модуль 9 про планы и статистику), а не «на всякий случай». Дальше по теории — BCNF и старшие формы (Silberschatz, гл. 7.5–7.6) — за рамками учебника: на практике 3НФ покрывает почти все схемы приложений.

Проверь себя

Вопрос 1. Свяжи каждую аномалию с причиной в схеме reading_log: (а) нельзя добавить автора без книги; (б) опечатка в городе читателя размножена по строкам; (в) удаление последней записи о книге стирает сведения об авторе.

Ответ. (а) и (в) — author_name зависит от book_title — части составного ключа (нарушение 2НФ; а publisher_city из текста главы зависел бы ещё и от неключевого publisher — вот это уже 3НФ): автор существует только «внутри» строк прочтений. (б) — reader_city зависит от части составного ключа (нарушение 2НФ), город хранится многократно. Обе проблемы лечатся выносом сущностей: readers (2НФ), books/authors/publishers (2НФ и 3НФ).

Вопрос 2. Где живёт внешний ключ для связи «один автор — много книг» и какая конструкция превращает её в 1:1?

Ответ. В таблице «многих»: books.author_id REFERENCES authors (FK на стороне N). Для 1:1 ссылающийся столбец дополнительно ограничивают UNIQUE (profile.reader_id UNIQUE REFERENCES readers) — вторая строка с тем же reader_id будет отклонена уникальностью.

Вопрос 3. Почему M:N «читатель × книга» нельзя выразить одним внешним ключом, и что содержит таблица соединения?

Ответ. Один FK фиксирует связь строки ровно с одной строкой другой таблицы; M:N требует произвольные комбинации. Таблица соединения (у нас — reviews) хранит по паре внешних ключей на каждую сторону и атрибуты самой связи (rating, comment, created_at); «у таблицы может быть более одного ограничения внешнего ключа — это используется для реализации связей многие-к-многим» (5.5.5).
