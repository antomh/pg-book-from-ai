Глава 8.2. Составные, частичные индексы и индексы на выражениях

Уровень: J+ · узел карты тем: T38 · PostgreSQL 17.11

Один индекс — под один запрос

Индекс из главы 8.1 ускорял WHERE book_id = 13. Но в приложении ищут не просто отзывы книги, а «пятёрки этой книги», а по каталогу — книги по названию без учёта регистра. Класть по индексу на каждое условие нельзя: каждый индекс удорожает запись («система должна поддерживать его синхронным с таблицей» — 11.1). Значит, индексы надо проектировать под конкретные запросы. У PostgreSQL для этого четыре инструмента: несколько столбцов в одном индексе, индекс по выражению, индекс по части таблицы и небазовые (INCLUDE) столбцы. Замечание о стандартах: составной индекс и ORDER BY — стандартный SQL; индексы на выражениях, частичные индексы и INCLUDE — расширения PostgreSQL (в SQL-стандарте таких конструкций нет).

Составные индексы и правило левого префикса

Несколько столбцов в одном B-tree сортируются как кортежи: сначала по первому, при равенстве — по второму и так далее. Правило применимости (11.3 /docs/17/indexes-multicolumn.html, дословно): «составной B-tree индекс может использоваться с условиями запроса, включающими любое подмножество столбцов индекса, но индекс наиболее эффективен, когда есть ограничения на ведущие (крайние левые) столбцы. Точное правило таково: ограничения равенства на ведущие столбцы плюс любые ограничения-неравенства на первый столбец без ограничения равенства будут использованы для ограничения сканируемой части индекса». И контрольный пример оттуда же: «для индекса на (a, b, c) и условия запроса WHERE a = 5 AND b >= 42 AND c < 77 индекс придётся сканировать от первой записи с a = 5 и b = 42 до последней записи с a = 5. Записи с c >= 77 будут пропущены, но их всё равно придётся просканировать. Этот индекс в принципе мог бы использоваться для запросов с ограничениями на b и/или c без ограничения на a — но сканировать пришлось бы весь индекс, поэтому в большинстве случаев планировщик предпочтёт последовательное сканирование таблицы» (11.3). Порядок столбцов выбирается по запросам: столбцы равенства — левее, самый избирательный — первым.

CREATE INDEX reviews_book_rating_idx ON reviews (book_id, rating);

-- учебный приём: заставить планировщик показать индексный план
-- на маленькой таблице (см. пояснение ниже)
SET enable_seqscan = off;

EXPLAIN SELECT * FROM reviews
WHERE book_id = 13 AND rating = 5;

EXPLAIN SELECT * FROM reviews
WHERE rating = 5;
CREATE INDEX
                              QUERY PLAN
----------------------------------------------------------------------
 Index Scan using reviews_book_rating_idx on reviews
   (cost=0.29..8.30 rows=1 width=84)
   Index Cond: (book_id = 13 AND rating = 5)
(2 rows)

                     QUERY PLAN
-----------------------------------------------------
 Seq Scan on reviews  (cost=0.00..1.13 rows=3 width=84)
   Filter: (rating = 5)
(2 rows)

Что выведено и почему: в первом запросе «Index Cond» содержит оба условия — спуск по дереву сразу до диапазона «книга 13, оценка 5». Оговорка о честности: на таблице в одну страницу (наша — 11 строк) планировщик выбрал бы Seq Scan для обоих запросов, поэтому мы временно отключили последовательное сканирование параметром enable_seqscan = off — стандартный приём для изучения формы плана: по 20.7.1 «полностью подавить последовательные сканирования невозможно, но отключение этой переменной удерживает планировщика от использования такого плана, если доступны другие методы» (It is impossible to suppress sequential scans entirely, but turning this variable off discourages the planner from using one if there are the other methods available). SET действует до конца сессии; верните SET enable_seqscan = on; после опытов. Во втором запросе ограничения на ведущий столбец book_id нет, индекс пришлось бы читать целиком — и без SET планировщик честно выбирает Seq Scan (11.3: «в большинстве случаев планировщик предпочтёт последовательное сканирование»; на 11 строках — тем более, глава 8.1). Столбец rating попал в индекс вторым не случайно: если искать по нему одному придётся редко, а вместе с book_id — часто, это правильный порядок.

Составной индекс бесплатно закрывает и сортировку: «в дополнение к простому поиску строк индекс может выдавать их в определённом отсортированном порядке. Это позволяет выполнить ORDER BY запроса без отдельного шага сортировки» (11.4 /docs/17/indexes-ordering.html, дословно). Индекс (book_id, rating) вернёт отзывы книги уже упорядоченными по оценке — ORDER BY rating не нужен как отдельный узел плана. Но: «из типов индексов, поддерживаемых сейчас PostgreSQL, только B-tree может выдавать отсортированный вывод» (11.4). Смешанный порядок задаётся при создании: «рассмотрим двухстолбцовый индекс (x, y): при прямом сканировании он удовлетворяет ORDER BY x, y, а при обратном — ORDER BY x DESC, y DESC. Но приложение может часто нуждаться в ORDER BY x ASC, y DESC. Такого порядка из обычного индекса не получить, но можно, если индекс определён как (x ASC, y DESC)» (11.4). Для «топ-N» это особенно ценно: «явный особый случай — ORDER BY в сочетании с LIMIT n: явной сортировке пришлось бы обработать все данные, чтобы найти первые n строк, а при индексе, соответствующем ORDER BY, первые n строк извлекаются напрямую» (11.4).

Частичные индексы

Иногда нужна не вся таблица: «частичный индекс — это индекс, построенный над подмножеством таблицы; это подмножество определяется условным выражением (называемым предикатом частичного индекса). Индекс содержит записи только для тех строк таблицы, которые удовлетворяют предикату» (11.8 /docs/17/indexes-partial.html, дословно). Главный выигрыш: «одна из основных причин использования частичного индекса — избежать индексации частых значений. Поскольку запрос, ищущий частое значение (составляющее более нескольких процентов строк таблицы), всё равно не будет использовать индекс, нет смысла держать эти строки в индексе вообще. Это уменьшает размер индекса, что ускорит те запросы, которые индекс используют. Это также ускорит многие операции изменения таблицы, потому что индекс не нужно обновлять во всех случаях» (11.8). Пример из предметной области: модерацию интересуют отзывы без текста — читатель поставил оценку, но комментарий не написал, и таких строк немного:

CREATE INDEX reviews_no_comment_idx
    ON reviews (reader_id)
    WHERE comment IS NULL;

SET enable_seqscan = off;   -- как выше: показать форму плана

EXPLAIN SELECT * FROM reviews
WHERE comment IS NULL AND reader_id = 1;
CREATE INDEX
                              QUERY PLAN
----------------------------------------------------------------------
 Index Scan using reviews_no_comment_idx on reviews
   (cost=0.29..8.30 rows=1 width=84)
   Index Cond: (reader_id = 1)
(2 rows)

Что выведено и почему: Index Cond содержит только reader_id — условие comment IS NULL уже «вшито» в индекс его предикатом: планировщику достаточно знать, что индекс содержит только такие строки. Ещё применение: «использовать WHERE с UNIQUE для обеспечения уникальности над подмножеством таблицы» (CREATE INDEX, /docs/17/sql-createindex.html) — например, уникальность пары (reader_id, book_id) только среди видимых отзывов. Ограничения на предикат и выражения индекса одинаковы: «выражение в WHERE может ссылаться только на столбцы базовой таблицы... Подзапросы и агрегатные выражения в настоящее время также запрещены в WHERE. Те же ограничения применяются к полям индекса, являющимся выражениями. Все функции и операторы, используемые в определении индекса, должны быть "immutable", то есть их результаты должны зависеть только от их аргументов и никогда ни от какого внешнего влияния (такого как содержимое другой таблицы или текущее время)» (CREATE INDEX, дословно).

Индексы на выражениях

Пока индексировались столбцы. Но «столбец индекса — не обязательно просто столбец базовой таблицы: это может быть функция или скалярное выражение, вычисленное по одному или нескольким столбцам таблицы. Эта возможность полезна для быстрого доступа к таблицам на основе результатов вычислений. Например, обычный способ сравнения без учёта регистра — использовать функцию lower : SELECT * FROM test1 WHERE lower(col1) = 'value'; — этот запрос сможет использовать индекс, если он определён на результате функции lower(col1) : CREATE INDEX test1_lower_col1_idx ON test1 (lower(col1))» (11.7 /docs/17/indexes-expressional.html, дословно). Поиск по названию книги без учёта регистра:

CREATE INDEX books_lower_title_idx ON books (lower(title));

SET enable_seqscan = off;   -- как выше: показать форму плана

EXPLAIN SELECT * FROM books
WHERE lower(title) = 'война и мир';
CREATE INDEX
                            QUERY PLAN
------------------------------------------------------------------
 Index Scan using books_lower_title_idx on books
   (cost=0.29..8.30 rows=1 width=170)
   Index Cond: (lower(title) = 'война и мир'::text)
(2 rows)

Что выведено и почему: в Index Cond видно то же самое выражение lower(title), по которому построен индекс — планировщик сопоставил выражение запроса с выражением индекса. Синтаксис: «команда CREATE INDEX обычно требует писать круглые скобки вокруг индексных выражений... Скобки можно опустить, когда выражение — просто вызов функции, как в первом примере» (11.7). Цена такого индекса: «индексные выражения относительно дороги в сопровождении, так как производные выражения должны вычисляться для каждой вставки строки и non-HOT обновления. Однако индексные выражения не перевычисляются при поиске по индексу, так как они уже хранятся в индексе» (11.7). Поэтому lower(title) пишется один раз при вставке, а не при каждом поиске. Уникальность по выражению работает как ограничение: «если объявить такой индекс UNIQUE, он запретит создание строк, чьи значения col1 различаются только регистром, а также строк с идентичными col1. Таким образом, индексы на выражениях могут использоваться для обеспечения ограничений, не определимых как простые ограничения уникальности» (11.7).

INCLUDE: небазовые столбцы

Последний инструмент доводит индекс до «покрывающего»: «необязательное предложение INCLUDE указывает список столбцов, которые будут включены в индекс как небазовые столбцы. Небазовый столбец не может использоваться в условиях поиска по индексу и не учитывается для целей уникальности или исключающих ограничений, обеспечиваемых индексом. Однако index-only сканирование может вернуть содержимое небазовых столбцов без обращения к таблице индекса, поскольку они доступны напрямую из элемента индекса. Таким образом, добавление небазовых столбцов позволяет index-only сканированиям использоваться для запросов, которые иначе не могли бы их использовать» (CREATE INDEX /docs/17/sql-createindex.html, дословно):

CREATE INDEX reviews_book_cover_idx
    ON reviews (book_id) INCLUDE (rating, created_at);

SET enable_seqscan = off;   -- как выше: показать форму плана

EXPLAIN SELECT rating, created_at FROM reviews
WHERE book_id = 13;
CREATE INDEX
                            QUERY PLAN
----------------------------------------------------------------
 Index Only Scan using reviews_book_cover_idx on reviews
   (cost=0.29..8.30 rows=3 width=12)
(2 rows)

Что выведено и почему: запросу нужны только rating и created_at, и оба лежат в индексе — план «Index Only Scan» не обращается к таблице вовсе. Почему иногда обращение всё же случается — тема главы 8.3 (карта видимости и MVCC). Проектировочный итог главы: под запрос «пятёрки книги 13» оптимален один составной индекс (book_id, rating), под поиск без регистра — индекс на выражении, под редкие строки — частичный. Один индекс на всё сразу — не цель; цель — минимальный набор индексов, закрывающий частые запросы при приемлемой цене записи.

Связь с теорией

Составной индекс — это «доступ по нескольким ключам» из учебников: Silberschatz (7-е изд., гл. 14, § 14.6 Multiple-Key Access) описывает составные индексные ключи и лексикографический порядок поиска по ним — ровно то, что вы видели в правиле левого префикса (11.3). Частичные индексы и индексы на выражениях — специализированные конструкции PostgreSQL, выходящие за стандарт SQL: их стоит помечать как диалектные при переносе кода на другие СУБД. INCLUDE — реализация «покрывающего индекса» (covering index): индекс, содержащий все столбцы запроса, чтобы поиск не обращался к таблице. В документации PostgreSQL термин «covering» вводится в 11.9; в Silberschatz (7-е изд., гл. 14) покрывающие индексы отдельным параграфом не выделены — составным ключам и поиску по нескольким ключам посвящён § 14.6 Multiple-Key Access — среди параграфов главы 14 покрывающих индексов в оглавлении нет. Курс CMU 15-445 разбирает составные ключи в лекциях #08–09 (Tree Indexes).

Проверь себя

Вопрос 1. Индекс построен на (reader_id, book_id, rating). Какие запросы используют его эффективно: WHERE book_id = 1, WHERE reader_id = 2, WHERE reader_id = 2 AND book_id = 1?

Ответ. Эффективно — запросы с «ограничениями на ведущие (крайние левые) столбцы» (11.3): reader_id = 2 (ведущий столбец) и reader_id = 2 AND book_id = 1 (два ведущих). WHERE book_id = 1 без ограничения на reader_id потребовал бы «сканировать весь индекс», поэтому «в большинстве случаев планировщик предпочтёт последовательное сканирование таблицы» (11.3).

Вопрос 2. Чем частичный индекс ON reviews (reader_id) WHERE comment IS NULL лучше полного индекса по reader_id для запроса «отзывы без комментария»? Когда он хуже?

Ответ. «Индекс содержит записи только для тех строк таблицы, которые удовлетворяют предикату» (11.8): он меньше (быстрее поиск), не «толстеет» от строк с комментариями и «не нужно обновлять... во всех случаях» при изменении таблицы (11.8). Хуже он для запросов, выходящих за предикат: строки с непустым comment в нём просто отсутствуют — по ним поиск невозможен.

Вопрос 3. Почему нельзя построить индекс ON reviews (created_at::date), если нужно искать по дате без времени, а lower(title) — можно?

Ответ. Требование CREATE INDEX: «все функции и операторы, используемые в определении индекса, должны быть "immutable", то есть их результаты должны зависеть только от их аргументов и никогда ни от какого внешнего влияния». lower(text) — immutable. Приведение timestamptz::date зависит от настройки часового пояса сеанса — то есть от внешнего влияния, — и потому не является immutable; CREATE INDEX отвергнет такое выражение (ошибка «functions in index expression must be marked IMMUTABLE» — src/backend/commands/indexcmds.c, строка 1966 на базовом коммите). Выход — использовать в индексе само выражение без зависимостей от настроек, например индекс по created_at и условия с диапазонами времени.
