Глава 5.1. INSERT и ON CONFLICT

Уровень: J · узел карты тем: T25 · PostgreSQL 17.11

Ночная загрузка каталога падает на второй день

Скрипт каждую ночь заливает в books новые книги из внешнего каталога, указывая book_id из каталога. Первая ночь прошла чисто. Вторая оборвалась на первой же существующей книге: вставка нарушает первичный ключ books_pkey (имя ограничения PostgreSQL строит по конвенции «таблица_pkey» — как distributors_pkey в примерах (/docs/17/sql-altertable.html)). Пересматривать файл руками — не вариант: каталог приходит целиком. Нужен оператор, который сам решает: новая строка — вставить, существующая — обновить или пропустить. В SQL, «как inserts are performed, one row at a time» (Silberschatz, 7-е изд., § 3.9), конфликты уникальности — штатная ситуация, и PostgreSQL закрывает её предложением ON CONFLICT.

INSERT: строки, список столбцов, DEFAULT VALUES

Базовая форма — из главы 6.1 (/docs/17/dml-insert.html): «данные вставляются по одной строке за раз. Можно вставить более одной строки в одной команде, но невозможно вставить что-то, что не является полной строкой». Пропущенные в списке столбцы заполняются значениями по умолчанию (глава 4.1). Документация советует перечислять столбцы явно: «многие пользователи считают хорошей практикой всегда перечислять имена столбцов». Для строки целиком из значений по умолчанию есть форма INSERT INTO t DEFAULT VALUES — «все столбцы будут заполнены значениями по умолчанию, как если бы DEFAULT было явно указано для каждого» (/docs/17/sql-insert.html, Parameters). Мультивставка и вставка из запроса выглядят так:

INSERT INTO books (book_id, title, author_id) VALUES
    (7, 'Ночь перед Рождеством', 2),
    (8, 'Вий', 2);

INSERT INTO books (book_id, title, author_id)
SELECT 100 + n, 'Сборник №' || n, 1
FROM generate_series(1, 3) AS n;

Обе формы пригодятся в пакетной загрузке ниже. Теперь — конфликтная часть.

ON CONFLICT: альтернатива ошибке уникальности

Определение из справочника INSERT дословно: «необязательное предложение ON CONFLICT задаёт альтернативное действие вместо выдачи ошибки нарушения уникального ограничения или ограничения исключения. Для каждой отдельной строки, предлагаемой для вставки, либо выполняется вставка, либо — если нарушен арбитр (ограничение или индекс), указанный конфликтной целью, — выполняется альтернативное конфликтное действие». Действий два:

  • DO NOTHING — «просто не вставляет строку»;
  • DO UPDATE — «обновляет существующую строку, которая конфликтует со строкой, предлагаемой для вставки».

Ключевая гарантия: «ON CONFLICT DO UPDATE гарантирует атомарный исход INSERT или UPDATE; при отсутствии независимой ошибки гарантирован один из этих двух исходов, даже при высокой конкурентности. Это также известно как UPSERT — "UPDATE or INSERT"». Идёмпотентная ночная загрузка теперь — один оператор:

INSERT INTO books (book_id, title, author_id) VALUES
    (1, 'Евгений Онегин', 1),
    (11, 'Капитанская дочка', 1)
ON CONFLICT (book_id) DO UPDATE
    SET title     = EXCLUDED.title,
        author_id = EXCLUDED.author_id;
INSERT 0 2

Что выведено и почему: тег команды INSERT 0 N, где «количество N — это число вставленных или обновлённых строк» (Outputs, sql-insert). Строка с book_id 1 существовала — сработал DO UPDATE, строка с book_id 11 вставлена (новая книга каталога, которой в базе ещё не было); обе посчитаны в N=2. Повторный запуск того же оператора даст тот же результат — загрузка идемпотентна, ошибка books_pkey больше не возникает.

excluded и конфликтная цель

В DO UPDATE SET нужны обе стороны: старая строка и предлагаемая. Правило из Parameters (sql-insert): «предложения SET и WHERE в ON CONFLICT DO UPDATE имеют доступ к существующей строке по имени таблицы (или алиасу) и к строке, предлагаемой для вставки, — через специальную таблицу excluded». Поэтому EXCLUDED.title — это заголовок из VALUES, а title — текущее значение в таблице.

Конфликтная цель (book_id) — не украшение. Правило вывода (unique index inference): «все уникальные индексы таблицы, которые безотносительно порядка содержат ровно указанные в conflict_target столбцы/выражения, выводятся (выбираются) как арбитровые индексы. Если попытка вывода неуспешна, выдаётся ошибка». Для books арбитром станет B-tree-индекс первичного ключа. Разница между действиями жёсткая: «для ON CONFLICT DO NOTHING указывать конфликтную цель необязательно; когда она опущена, обрабатываются конфликты со всеми пригодными ограничениями (и уникальными индексами). Для ON CONFLICT DO UPDATE конфликтная цель должна быть указана». Вариант «просто не мешать» — без цели:

INSERT INTO books (book_id, title, author_id) VALUES
    (2, 'Руслан и Людмила', 1),
    (9, 'Нос', 2)
ON CONFLICT DO NOTHING;
INSERT 0 1

Что выведено и почему: book_id 2 уже существует в таблице — строка пропущена (в идемпотентной загрузке привозят те же данные, что уже лежат в базе), book_id 9 вставлена; N=1. Заметьте: здесь арбитром может стать любой уникальный индекс таблицы, а не только индекс первичного ключа.

Как это работает внутри

Почему ON CONFLICT может обещать атомарность без блокировки всей таблицы? Механизм — спекулятивная вставка (speculative insertion). Реализация — в исполнителе модификаций, файл src/backend/executor/nodeModifyTable.c на коммите 083ac033419f690758508e08c1736089384bbee8. Строка сначала вставляется в таблицу «под вопросом», с маркером: вызов table_tuple_insert_speculative (строки 1118–1121), затем для неё добавляются записи индексов, и лишь после проверки арбитров окончательный вердикт — table_tuple_complete_speculative (строки 1132–1134). Комментарий в коде объясняет цель: «Before we start insertion proper, acquire our "speculative insertion lock". Others can use that to wait for us to decide if we're going to go ahead with the insertion, instead of waiting for the whole transaction to complete» — конкурент не ждёт конца всей транзакции, а ждёт только решения об этой строке. Если конфликт найден и действие — DO UPDATE, вызывается функция ExecOnConflictUpdate (строка 2544): «Try to lock tuple for update as part of speculative insertion... Returns true if we're done (with or without an update), or false if the caller must retry the INSERT from scratch» — захват конфликтующей строки и её обновление либо повтор вставки.

Ловушка мультивставки: «affect row a second time»

Справочник INSERT фиксирует ограничение: «INSERT с предложением ON CONFLICT DO UPDATE — "детерминированный" оператор. Это значит, что команда не сможет воздействовать на одну и ту же существующую строку более одного раза; при возникновении такой ситуации будет выдана ошибка нарушения кардинальности». Поэтому, если в VALUES оказались две строки с одинаковым book_id (дубликат во входном файле), весь оператор упадёт — предочистка дублей по арбитровому столбцу нужна до вставки, например DISTINCT ON (book_id) из главы 2.2.

RETURNING: что вставилось

«Необязательное предложение RETURNING заставляет INSERT вычислить и вернуть значения на основе каждой фактически вставленной (или обновлённой, если использовалось ON CONFLICT DO UPDATE) строки. Это прежде всего полезно для получения значений, поставляемых умолчаниями, таких как номер последовательности» (sql-insert). Пример на identity-таблице из главы 4.6 (счётчик последовательности после примеров той главы дошёл до 3):

INSERT INTO reading_sessions (reader_id, book_id)
VALUES (2, 4)
RETURNING session_id, started_at;
 session_id |         started_at
------------+-----------------------------
          4 | 2026-11-20 10:15:33.172945+03
(1 row)

Что выведено и почему: session_id сгенерирован identity-последовательностью (следующий после трёх израсходованных значений — глава 4.6), started_at — умолчанием now() (глава 3.2); оба значения приложение получает без второго запроса.

Стандарт SQL и расширение

Раздел Compatibility справочника INSERT прямо отделяет диалект от стандарта: «INSERT соответствует стандарту SQL, за исключением того, что предложение RETURNING является расширением PostgreSQL... как и возможность указывать альтернативное действие с ON CONFLICT». Стандартная альтернатива там же: «если вы предпочитаете более соответствующий стандарту SQL оператор, чем ON CONFLICT, см. MERGE» — и в Notes: «возможно, вы захотите рассмотреть MERGE, поскольку он позволяет смешивать INSERT, UPDATE и DELETE в одном операторе». Для задачи «вставить или обновить по ключу» ON CONFLICT достаточно; MERGE в этом учебнике не разбирается.

Проверь себя

Вопрос 1. Чем ON CONFLICT DO UPDATE отличается от DO NOTHING по требованиям к конфликтной цели и по результату для существующей строки?

Ответ. Для DO UPDATE «конфликтная цель должна быть указана» (по ней выводятся арбитровые индексы), для DO NOTHING цель необязательна — «когда она опущена, обрабатываются конфликты со всеми пригодными ограничениями (и уникальными индексами)» (sql-insert, Parameters). DO NOTHING «просто не вставляет строку», DO UPDATE «обновляет существующую строку, которая конфликтует со строкой, предлагаемой для вставки».

Вопрос 2. В ON CONFLICT (book_id) DO UPDATE SET title = EXCLUDED.title — что именно означает EXCLUDED.title и откуда берётся арбитровый индекс для (book_id)?

Ответ. EXCLUDED — «специальная таблица», через которую SET/WHERE обращаются к «строке, предлагаемой для вставки», то есть значение из VALUES этого же оператора. Арбитровые индексы — «все уникальные индексы таблицы, которые безотносительно порядка содержат ровно указанные в conflict_target столбцы» (unique index inference); здесь это индекс первичного ключа books_pkey.

Вопрос 3. Почему INSERT ... VALUES (1, ...), (1, ...) ON CONFLICT (book_id) DO UPDATE завершится ошибкой, и что помогает избежать её при пакетной загрузке?

Ответ. Оператор «не сможет воздействовать на одну и ту же существующую строку более одного раза; при возникновении такой ситуации будет выдана ошибка нарушения кардинальности» (sql-insert): две строки VALUES претендуют на один book_id. Помогает дедупликация входных данных — например, DISTINCT ON (book_id) из главы 2.2 до вставки.
