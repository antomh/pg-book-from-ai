Глава 4.1. CREATE TABLE: столбцы, DEFAULT, идентификаторы

Уровень: J · узел карты тем: T18 · PostgreSQL 17.11

Таблица создана — а обратиться к ней нельзя

Разработчик пишет в миграции CREATE TABLE "Readers" (...) — ORM обрамляет идентификаторы кавычками и сохраняет заглавную букву, как принято в коде приложения. Затем выполняет вручную SELECT * FROM readers и получает ошибку «relation "readers" does not exist». Таблица существует, но под другим именем. Это первое, что глава объясняет: правила именования и фолдинг регистра в PostgreSQL. Второе: только что созданная таблица принимает любые данные — NULL в любом столбце, никаких значений по умолчанию. Как задать таблице «правила приёма» столбец за столбцом — вторая половина главы.

CREATE TABLE: минимальное определение

Справочник команд (/docs/17/sql-createtable.html) описывает команду так: «CREATE TABLE создаст новую, изначально пустую таблицу в текущей базе данных. Таблицей будет владеть пользователь, выпустивший команду» (перевод дословный). Имена и типы столбцов задаются в скобках; на типы ссылается модуль 3, на ограничения — глава 4.2. Создадим читателей нашего дневника:

CREATE TABLE readers (
    reader_id     integer PRIMARY KEY,
    email         varchar(255) NOT NULL UNIQUE,
    display_name  text,
    is_active     boolean NOT NULL DEFAULT true,
    city          text,
    registered_at timestamptz NOT NULL DEFAULT now()
);

Таблица живёт в схеме: «если указано имя схемы (например, CREATE TABLE myschema.mytable ...), таблица создаётся в указанной схеме. Иначе она создаётся в текущей схеме» (там же). По умолчанию текущая схема — public; устройство схем — глава 4.5. Повторное выполнение CREATE TABLE для существующей таблицы — ошибка; форма CREATE TABLE IF NOT EXISTS вместо ошибки «просто выдаёт замечание (notice)» (Parameters, там же).

DEFAULT: значение, которое вставится само

Раздел Parameters справочника фиксирует правила дословно: «предложение DEFAULT назначает столбцу значение данных по умолчанию. Это любое выражение без переменных (в частности, перекрёстные ссылки на другие столбцы текущей таблицы не допускаются). Подзапросы также не допускаются. Тип данных выражения по умолчанию должен соответствовать типу данных столбца. Выражение по умолчанию используется в любой операции вставки, которая не задаёт значения для этого столбца. Если у столбца нет значения по умолчанию, то по умолчанию используется null».

INSERT INTO readers (reader_id, email, display_name)
VALUES (1, 'anna@example.com', 'Анна');

SELECT * FROM readers;
 reader_id |      email      | display_name | is_active |        registered_at
-----------+-----------------+--------------+-----------+-----------------------------
         1 | anna@example.com | Анна         | t         | 2026-11-20 19:03:11.552618+03
(1 row)

Что выведено и почему: INSERT не упомянул is_active и registered_at, поэтому сработали DEFAULT — true и now() (момент выполнения INSERT; поведение now() разобрано в главе 3.2). Значение по умолчанию — это выражение: константа, вызов функции, арифметика; главное — без переменных и подзапросов.

NULL разрешён по умолчанию

Если для столбца не написано ни NOT NULL, ни DEFAULT, PostgreSQL вставит NULL. Формулировка из справочника CREATE TABLE, параметр NULL: «столбцу разрешено содержать null-значения. Это поведение по умолчанию». То же у ограничения NOT NULL (глава 4.2): без него столбец «просто принимает» отсутствующее значение. Практическое правило: в миграции у каждого столбца осознанно написано либо NOT NULL, либо осознанно допущен NULL — «молчаливых» столбцов быть не должно. Заметьте: в нашем примере display_name — осознанный NULL: не все читатели указывают имя.

Идентификаторы: регистр, кавычки, длина

Раздел 4.1.1 «Identifiers and Key Words» (/docs/17/sql-syntax-lexical.html) задаёт лексические правила. Идентификатор начинается «с буквы (a–z, но также букв с диакритикой и не-латинских букв) или подчёркивания; последующие символы могут быть буквами, подчёркиваниями, цифрами или знаками доллара», причём «знаки доллара не разрешены в идентификаторах по букве стандарта SQL, поэтому их использование может сделать приложения менее переносимыми». Длина: «система использует не более NAMEDATALEN-1 байт идентификатора; более длинные имена могут быть записаны в командах, но будут усечены. По умолчанию NAMEDATALEN равна 64, поэтому максимальная длина идентификатора — 63 байта».

Теперь — правило, которое сломало запрос из начала главы, дословно: «закавычивание идентификатора делает его регистрозависимым, тогда как незакавыченные имена всегда сворачиваются к нижнему регистру. Например, идентификаторы FOO, foo и "foo" считаются в PostgreSQL одинаковыми, но "Foo" и "FOO" отличаются от этих трёх и друг от друга». Проверим на живом примере:

CREATE TABLE "Readers" (reader_id integer);

SELECT * FROM readers;
ERROR:  relation "readers" does not exist

Что выведено и почему: незакавыченные Readers и readers оба свернулись к readers, но таблица была создана по правилам для кавычек — с точным именем «Readers». Запрос ищет readers, а такой таблицы нет; сообщение формируется в src/backend/catalog/namespace.c#L638 на базовом коммите (errmsg("relation \"%s\" does not exist", ...) внутри функции RangeVarGetRelidExtended). Обратиться к таблице можно только кавычками: SELECT * FROM "Readers";.

Кавычки позволяют и большее: «закавыченные идентификаторы могут содержать любые символы, кроме символа с кодом ноль» — имя с пробелом или кириллицей без кавычек уже не написать ("Мои читатели"). Наконец, важная пометка «стандарт против диалекта», дословно: «свёртка незакавыченных имён к нижнему регистру в PostgreSQL несовместима со стандартом SQL, который говорит, что незакавыченные имена должны сворачиваться к верхнему регистру. Если вы хотите писать переносимые приложения, вам советуют всегда кавычить конкретное имя или никогда его не кавычить». Ключевые слова (SELECT, TABLE) регистронезависимы; идентификатор, совпадающий с ключевым словом, требует кавычек («"select" может использоваться как имя столбца или таблицы, тогда как незакавыченный select будет понят как ключевое слово»).

Проверь себя

Вопрос 1. В миграции написали CREATE TABLE "Books" (...). Какие из обращений сработают: SELECT * FROM books, SELECT * FROM Books, SELECT * FROM "Books"? Почему?

Ответ. Сработает только третье. Таблица создана с регистрозависимым именем «Books» (кавычки). Первые два обращения — незакавыченные, они «всегда сворачиваются к нижнему регистру» (4.1.1), то есть ищут books; такой таблицы нет — ошибка «relation "books" does not exist» (namespace.c#L638 на базовом коммите).

Вопрос 2. Почему DEFAULT now() в столбце registered_at допустим, а DEFAULT (SELECT max(id) FROM t) — нет? Что будет, если INSERT не укажет столбец с DEFAULT?

Ответ. Выражение по умолчанию — «любое выражение без переменных»; «подзапросы также не допускаются» (Parameters, CREATE TABLE). now() — вызов функции без аргументов-переменных, допустим; подзапрос запрещён. Если INSERT не задаёт столбец, используется «выражение по умолчанию... в любой операции вставки, которая не задаёт значения для этого столбца»; без DEFAULT — «по умолчанию используется null».

Вопрос 3. Чем varchar(255) отличается от text в определении email, и что ограничит длину строки, если тип безразличен к длине?

Ответ. Для хранения — ничем: «нет различия в производительности» между character varying(n) и text, оба хранят строки до ~1 ГБ (глава 3.1, 8.3). Длину в varchar(255) ограничивает сам тип. Если нужен программный инвариант, не покрытый типом (например, формат email), его задают ограничением CHECK — глава 4.2.
