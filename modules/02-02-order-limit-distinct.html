Глава 2.2. Сортировка, LIMIT/OFFSET, DISTINCT

Уровень: J · узел карты тем: T05 · PostgreSQL 17.11

«Топ-3 книги» работает через раз

Задача: вывести три лучшие книги по рейтингу. Первая попытка обычно такая:

SELECT title, rating FROM books LIMIT 3;

Запрос возвращает три строки — но это «какие-то» три строки, а не лучшие. Разработчик добавляет сортировку, получает рабочий вариант, а затем на продакшене сталкивается со вторым сюрпризом: пагинация (LIMIT + OFFSET) выдаёт повторяющиеся или пропадающие строки. Оба сюрприза — не баги PostgreSQL, а следствие одного правила, которое эта глава фиксирует: без ORDER BY порядок строк не определён, и любые «первые N» — случайность.

ORDER BY: единственный способ гарантировать порядок

Документация формулирует жёстко: «если сортировка не выбрана, строки возвращаются в неопределённом порядке. Фактический порядок в этом случае зависит от планов сканирования и соединения и порядка на диске, но полагаться на него нельзя. Конкретный порядок вывода гарантируется, только если шаг сортировки выбран явно» (раздел 7.5 Sorting Rows, /docs/17/queries-order.html). Справочная страница SELECT повторяет: «если ORDER BY не задан, строки возвращаются в том порядке, который системе дешевле всего произвести» (/docs/17/sql-select.html).

Правильный запрос на «топ-3»:

SELECT title, rating
FROM books
ORDER BY rating DESC NULLS LAST
LIMIT 3;
     title      | rating
---------------+--------
 Евгений Онегин|      5
 Война и мир   |      5
 Мёртвые души  |      4
(3 rows)

Что выведено и почему: строки отсортированы по rating по убыванию (DESC); LIMIT 3 оставляет первые три из отсортированного результата. Зачем здесь NULLS LAST: без него «топ-3» возглавила бы «Анна Каренина» с отсутствующей оценкой — NULL в сортировке «больше любого не-NULL-значения», и для DESC действует NULLS FIRST; правило разобрано ниже, в разделе «Где NULL в сортировке». Тонкость: «Евгений Онегин» и «Война и мир» равны по рейтингу — кто из них первым, решает уже не этот ORDER BY: «если две строки равны по всем указанным выражениям, они возвращаются в порядке, зависящем от реализации» (раздел ORDER BY Clause справочника SELECT). Для полной детерминированности добавляют третий ключ сортировки, например ORDER BY rating DESC NULLS LAST, book_id.

Где NULL в сортировке

У_NULL_в ORDER BY есть отдельное правило: «по умолчанию NULL сортируется так, будто он больше любого не-NULL-значения; то есть NULLS FIRST — значение по умолчанию для DESC, а NULLS LAST — иначе» (раздел 7.5, /docs/17/queries-order.html). На наших данных:

SELECT title, rating FROM books ORDER BY rating DESC;
      title       | rating
------------------+--------
 Анна Каренина    |
 Евгений Онегин  |      5
 Война и мир     |      5
 Мёртвые души     |      4
 Руслан и Людмила |      4
 Детектив XXI века|      3
(6 rows)

Что выведено и почему: «Анна Каренина» без рейтинга оказалась первой — при DESC «NULL больше всего» и NULLS FIRST применяется автоматически. Хотите управлять этим явно — пишите ORDER BY rating DESC NULLS LAST (синтаксис NULLS FIRST/LAST документирован там же).

Сортировать можно выражениями и алиасами

«Выражения сортировки могут быть любыми выражениями, допустимыми в списке выборки запроса» — пример из документации: ORDER BY a + b, c (раздел 7.5). Кроме того, «каждое выражение [ORDER BY] может быть именем или порядковым номером выходного столбца (элемента списка SELECT) либо произвольным выражением из значений входных столбцов» (ORDER BY Clause справочника SELECT). Отсюда удобный шаблон — сортировать по алиасу из списка выборки:

SELECT title, 2026 - year AS age_years
FROM books
ORDER BY age_years;

LIMIT и OFFSET: порции результата

«LIMIT и OFFSET позволяют получить только часть строк, порождаемых остальной частью запроса... Если задан предел, будет возвращено не больше этого числа строк (но, возможно, меньше, если сам запрос даёт меньше строк). LIMIT ALL равнозначен отсутствию LIMIT, как и LIMIT с аргументом NULL. OFFSET означает пропуск указанного числа строк до начала возврата» (раздел 7.6 LIMIT and OFFSET, /docs/17/queries-limit.html).

Почему LIMIT без ORDER BY — лотерея, документация объясняет прямо: «используя LIMIT, важно применять ORDER BY, который задаёт строкам уникальный порядок. Иначе вы получите непредсказуемое подмножество строк запроса. Вы можете просить строки с десятой по двадцатую — но десятые по двадцатые в каком порядке? Порядок неизвестен, если вы не указали ORDER BY. Оптимизатор запросов учитывает LIMIT при генерации планов, поэтому разные значения LIMIT/OFFSET с большой вероятностью дадут разные планы (и разный порядок строк). Выбор разных порций одного результата через разные LIMIT/OFFSET даст несогласованные результаты, если не обеспечить предсказуемый порядок через ORDER BY» (там же).

Стандарт SQL: FETCH FIRST вместо LIMIT

«SQL:2008 ввёл другой синтаксис для того же результата, который PostgreSQL тоже поддерживает» — OFFSET start { ROW | ROWS } FETCH { FIRST | NEXT } [ count ] { ROW | ROWS } { ONLY | WITH TIES }. В стандарте start и count обязаны быть литеральной константой, параметром или именем переменной; «как расширение PostgreSQL допускаются другие выражения, но обычно их нужно заключать в скобки». Формулировки — справочная страница SELECT, раздел LIMIT Clause. То есть LIMIT 3 — удобная запись PostgreSQL; FETCH FIRST 3 ROWS ONLY — стандартная. Прочие свойства: FETCH ... WITH TIES возвращает также строки, равные последней по ORDER BY (ORDER BY при этом обязателен).

DISTINCT и DISTINCT ON

DISTINCT убирает полные дубликаты строк результата (раздел 7.3.3, /docs/17/queries-select-lists.html; напомним из главы 1.1: SQL-выдача без DISTINCT — мультимножество). Пример из главы 1.1: SELECT DISTINCT author_id FROM books вернул множество авторов, включая NULL:

SELECT DISTINCT author_id FROM books ORDER BY author_id;
 author_id
-----------
         1
         2
         3

(4 rows)

Что выведено и почему: четыре строки при шести книгах — Пушкин и Толстой встречаются дважды и сворачиваются в одну строку каждая; отдельной строкой остаётся NULL (два NULL считаются дубликатами при DISTINCT — «Null values are considered equal in this comparison» — раздел 7.3.3 там же). Пустая ячейка между «3» и «(4 rows)» — это и есть строка NULL: psql рисует отсутствующее значение пустым местом, и её легко не заметить; NULL идёт последним при возрастающей сортировке — NULLS LAST по умолчанию, раздел «Где NULL в сортировке» выше. Строк стало меньше, чем книг, потому что DISTINCT сворачивает полные дубликаты — то есть превращает мультимножество в множество, как обсуждалось в главе 1.1.

Расширение PostgreSQL — DISTINCT ON (выражение, ...): «множество строк, у которых все выражения равны, считаются дубликатами, и в выводе остаётся только первая строка множества». При этом «"первая строка" множества непредсказуема, если запрос не отсортирован по достаточному числу столбцов, гарантирующему уникальный порядок строк, приходящих на фильтр DISTINCT. (Обработка DISTINCT ON происходит после сортировки ORDER BY.)» — раздел 7.3.3, /docs/17/queries-select-lists.html. Типовой шаблон «одна строка на автора — его лучшая книга»:

SELECT DISTINCT ON (author_id) author_id, title, rating
FROM books
ORDER BY author_id, rating DESC;
 author_id |      title       | rating
-----------+------------------+--------
         1 | Евгений Онегин  |      5
         2 | Мёртвые души     |      4
         3 | Война и мир     |      5
           | Детектив XXI века|      3
(4 rows)

Что выведено и почему: сортировка внутри author_id по рейтингу по убыванию расставила книги автора; DISTINCT ON оставил первую строку каждой группы. Групп четыре, а не три: NULL тоже образует свою группу — «два NULL считаются равными» и в DISTINCT ON, — и «Детектив XXI века» (пустая ячейка author_id в последней строке) возглавляет её: при возрастающей сортировке по author_id NULL-группа идёт последней (NULLS LAST, раздел выше). Убейте вторую часть сортировки (rating DESC) — «первая» строка автора станет непредсказуемой. Документация предупреждает и об этом, и о том, что «DISTINCT ON не является частью стандарта SQL и иногда считается плохим стилем из-за потенциально недетерминированного характера результатов; при аккуратном использовании GROUP BY и подзапросов в FROM этой конструкции можно избежать» (там же) — эквивалентный способ появится в главе 2.5.

Проверь себя

Вопрос 1. На тестовых данных SELECT title FROM books LIMIT 3 вернул одни и те же строки десять раз подряд. Значит ли это, что порядок стабилен?

Ответ. Нет. Без ORDER BY порядок не определён («строки возвращаются в неопределённом порядке... полагаться нельзя» — 7.5) и может меняться при смене плана, объёма данных, настроек, параллельности. Повторяемость в одной серии запусков — не гарантия. Ссылки: разделы 7.5 queries-order.html и 7.6 queries-limit.html.

Вопрос 2. Куда попадёт книга с rating = NULL при ORDER BY rating и при ORDER BY rating DESC? Как вынести NULL-строки в конец при убывающей сортировке?

Ответ. По умолчанию NULL «больше любого не-NULL»: при возрастающей сортировке NULL уходит в конец (эквивалент NULLS LAST), при убывающей — в начало (эквивалент NULLS FIRST). Явно управлять положением можно опциями NULLS FIRST/NULLS LAST: ORDER BY rating DESC NULLS LAST (7.5, /docs/17/queries-order.html).

Вопрос 3. Чем DISTINCT ON отличается от GROUP BY и почему его результат может «плавать»?

Ответ. DISTINCT ON оставляет первую строку каждого множества строк с равными значениями выражений; какая строка «первая», решает сортировка — поэтому без ORDER BY, делающего порядок уникальным, результат непредсказуем (обработка DISTINCT ON идёт после ORDER BY). GROUP BY сворачивает каждую группу в одну строку детерминированно, но требует агрегатов для прочих столбцов. DISTINCT ON — расширение PostgreSQL, не входящее в стандарт SQL (7.3.3, /docs/17/queries-select-lists.html).
