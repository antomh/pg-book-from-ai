Глава 3.2. Дата и время

Уровень: J · узел карты тем: T13 · PostgreSQL 17.11

«Запишите встречу на 15:00» — в Москве, Лондоне или везде?

Приложение пишет в базу «2026-11-15 15:00:00». Через полгода выясняется, что часть событий записана в московском времени, часть — в серверном, у заказчика из другой зоны отчёты съехали на часы. Разбор таких аварий всегда упирается в один вопрос: что хранит значение времени — момент на оси времени или показание часов? PostgreSQL даёт на него точный ответ, и эта глава показывает, какие типы под какую задачу.

Набор типов

«PostgreSQL поддерживает полный набор типов даты и времени SQL, показанный в таблице 8.9. Даты считаются по григорианскому календарю, даже в годах до его введения» (раздел 8.5, /docs/17/datatype-datetime.html; перевод дословный). Выжимка из таблицы 8.9:

ТипХранениеОписаниеРазрешение
timestamp [(p)] [without time zone]8 байтдата и время, без пояса1 микросекунда
timestamp [(p)] with time zone8 байтдата и время, «с поясом» (формулировка таблицы 8.9 документации; фактически хранится момент в UTC, а пояс — свойство показа, см. следующий раздел)1 микросекунда
date4 байтадата, без времени1 день
time [(p)]8 байтвремя дня, без даты1 микросекунда
interval [fields] [(p)]16 байтвременной интервал1 микросекунда

Три детали из примечаний 8.5:

  • «Стандарт SQL требует, чтобы запись timestamp означала timestamp without time zone, и PostgreSQL соблюдает это поведение. timestamptz принимается как сокращение для timestamp with time zone; это расширение PostgreSQL»;
  • «time, timestamp и interval принимают опциональную точность p — число дробных цифр в поле секунд. По умолчанию явной границы точности нет. Допустимый диапазон p — от 0 до 6»;
  • про time with time zone: «тип time with time zone определён стандартом SQL, но его определение имеет свойства, приводящие к сомнительной полезности. В большинстве случаев комбинация date, time, timestamp without time zone и timestamp with time zone закрывает все потребности приложения».

Ключевой механизм: timestamptz хранит момент, пояс — свойство показа

Раздел 8.5.3 Time Zones формулирует точно (перевод дословный): «PostgreSQL предполагает ваш местный часовой пояс для любого типа, содержащего только дату или время. Все значения даты-времени, знающие пояс, хранятся внутренне в UTC (всемирное координированное время). Они преобразуются к местному времени в зоне, заданной параметром конфигурации TimeZone, перед показом клиенту». Имена зон — из данных IANA, полный список виден в представлении pg_timezone_names (там же, см. раздел 52.32).

Проверяется напрямую (представим сессию с TimeZone = Europe/Moscow):

CREATE TABLE meetings (
    meeting_id integer PRIMARY KEY,
    title      text NOT NULL,
    held_at    timestamptz NOT NULL
);

INSERT INTO meetings VALUES
    (1, 'Планирование', '2026-11-20 15:00:00+03');

SELECT meeting_id, held_at FROM meetings;
 meeting_id |       held_at
------------+---------------------
          1 | 2026-11-20 15:00:00+03
(1 row)

Что выведено и почему: во вводе пояс задан явно (+03); внутри сервер хранит момент в UTC, а при выводе конвертирует в зону сессии — Europe/Moscow даёт +03. Смените зону сессии — показ изменится, хранимое значение нет:

SET timezone = 'Europe/London';
SELECT meeting_id, held_at FROM meetings;
 meeting_id |       held_at
------------+---------------------
          1 | 2026-11-20 12:00:00+00
(1 row)

Что выведено и почему: это тот же момент (15:00 по Москве = 12:00 UTC в ноябре — зимнее время), показанный в другой зоне: «пояс — свойство показа, не значения». Именно поэтому timestamptz — тип для меток событий: заказов, встреч, платежей. А timestamp without time zone — для «показаний часов», не привязанных к точке на оси времени: расписание «каждый день в 09:00» в зоне клиента.

Замечание: ввод без пояса

Если во вводе timestamptz пояс не указан, PostgreSQL интерпретирует его в зоне сессии и конвертирует в UTC — «PostgreSQL предполагает ваш местный часовой пояс» (8.5.3). Явное +03 в примере выше снимает эту неоднозначность. Практика: в значениях, приходящих из других систем, всегда указывайте смещение.

interval: длительность, а не момент

Интервал — «временной интервал»; синтаксис ввода по 8.5.4: «interval-значения записываются подробным синтаксисом [@] количество единица [количество единица ...] [direction], где количество — число (возможно со знаком), единица — microsecond, millisecond, second, minute, hour, day, week, month, year и т.п., direction — ago или пусто». Интервал складывается и вычитается с датами:

SELECT held_at + interval '2 weeks' AS two_weeks_later
FROM meetings
WHERE meeting_id = 1;
   two_weeks_later
---------------------
 2026-12-04 15:00:00+03
(1 row)

Что выведено и почему: interval '2 weeks' — длительность; сложение сдвинуло момент на 14 дней. Даты «считаются по григорианскому календарю» (8.5), поэтому 20 ноября + 14 дней = 4 декабря — без ошибок длины месяцев, которые пришлось бы учитывать вручную.

Функции текущего времени: транзакция, оператор, мгновение

Раздел 9.9.5 Current Date/Time (/docs/17/functions-datetime.html): «эти функции стандарта SQL возвращают значения, основанные на времени начала текущей транзакции: CURRENT_DATE, CURRENT_TIME, CURRENT_TIMESTAMP, LOCALTIME, LOCALTIMESTAMP». Рядом — PostgreSQL-функции с разной семантикой: «now() — традиционный PostgreSQL-эквивалент transaction_timestamp()»; «transaction_timestamp() эквивалентен CURRENT_TIMESTAMP, но имя отражает, что он возвращает»; «statement_timestamp() возвращает время начала текущего оператора... statement_timestamp() и transaction_timestamp() равны в первом операторе транзакции, но могут различаться в последующих»; «clock_timestamp() возвращает фактическое текущее время, и его значение меняется даже внутри одного оператора SQL» (9.9.5, перевод дословный).

SELECT now() AS transaction_start,
       clock_timestamp() AS right_now;

Что будет выведено и почему: оба значения — timestamptz; now() фиксирован на старте транзакции (в psql каждый оператор — своя транзакция, поэтому вне явного BEGIN разница видна только в микросекундах), а clock_timestamp() — «тикающие» часы. Для журналов аудита берите now() — все записи одной транзакции получат одинаковую метку; для измерения длительностей — clock_timestamp().

Проверь себя

Вопрос 1. Приложение записало '2026-11-20 15:00:00+03'. Что именно хранится в столбце timestamptz и что изменится при SET timezone = 'Asia/Yekaterinburg'?

Ответ. Хранится момент времени в UTC (12:00 UTC); «все знающие пояс значения даты-времени хранятся внутренне в UTC» (8.5.3). Смена TimeZone меняет только показ: вывод станет 17:00+05. Само значение и все сравнения/индексы — про один и тот же момент.

Вопрос 2. Расписание «звонок каждый день в 09:00» хранится для пользователей из разных поясов. Какой тип выбрать и почему не timestamptz?

Ответ. time или timestamp without time zone — это показание часов без привязки к моменту; в 9:00 по Москве и 9:00 по Лондону — разные моменты, а расписание описывает локальное время. timestamptz превратил бы каждое «09:00» в конкретный момент, зависящий от того, чей пояс подставили при записи. (Классификация «момент vs показание» — 8.5.3; про timetz — «сомнительная полезность», 8.5.)

Вопрос 3. Чем now() отличается от clock_timestamp() и что взять для audit_log.created_at?

Ответ. now() (и CURRENT_TIMESTAMP) — время начала транзакции, фиксировано; clock_timestamp() — фактическое текущее время, «меняется даже внутри одного оператора» (9.9.5). Для audit_log обычно now(): все строки, записанные одной транзакцией, получают согласованную метку начала операции.
